## 1. 对方项目是什么

`midas-nx` 是 MIDAS NX Open API 的 Python + TypeScript 双语言 SDK，作者为 MIDAS IT 在职员工，
明确声明**非官方产品**。它的真实价值不在 SDK 本身，而在其**工程方法**：

```
E:\AI Study\MIDAS-API  (手册仓库，本机不存在)
        │  手册是唯一"文档"来源
        ▼
contracts/endpoints/*.yaml   ← 384 份语言中立契约（真源）
        │  契约驱动生成
        ▼
src/midas_nx/  +  packages/typescript/src/generated/
        ▲
        │  三条许可来源
schema/info-baseline.json    ← GET /info{endpoint}，305 端点 × 2 产品
docs/live_verification_notes.md ← 实测发现
contracts/verification/ledger.yaml ← 249 条会话级实测记录，覆盖 397 端点
```

**与我们的关系**：两边吃的是**同一份官方手册**（对方 `Dennis5882/MIDAS-API`，我方
`MIDAS_API_Online_Manual_*`），但走了两条不同的验证路线 —— 我方以**真实 MIDAS 实例逐端点实测**
（`verified` 503 / `untested` 110 / `unverified` 23），对方以 **`/info` 自述 Schema + 契约化人工复核**
（397 端点有实测记录，其中 278 条 write 级）。**两条路线的交集，就是本报告的查漏补缺面。**

**证据链（四条独立证据同向）**：

1. **我方自己的 `instances.yaml` 第 16 行**已写明：`gen-local`「**缺 21 个 Hyper-S 变体**」——
   而这 21 个端点又**全部**带 `unavailable_on: ["gen-local"]`。即我方数据**同时**记录了
   「GEN_NX 实例上没有它」与「`products: [GEN_NX]`」。
2. 对方 `docs/CLAUDE.md` 明载：**"Hyper-S (`-M1`) endpoints are Civil NX only — it's the solver
   MIDASIT shipped with Civil NX. They 404 under Gen."** 并在 `db/base.py` 设 `HYPER_S_ONLY` 常量，
   明言"Hyper-S is expected to reach Gen NX eventually, and that constant is the one place to widen
   when it does"——即**当前**确认是 Civil-only。
3. 对方 `docs/live_verification_notes.md` 的产品可得性结论（本轮经子代理通读 12,213 行后提取）：
   **"all 21 Hyper-S `-M1` are Civil-only (still, at Gen v2.2)"** —— 明确带上了
   "still"（在 Gen NX 2026 v2.2 上**仍然**如此），排除了"旧构建缺失"这一替代解释。
4. 对方专门为这族端点单独抓了一份 `schema/hyper-s-info.json`（`product: "civil"`，
   `method: "GET /info/db/{endpoint}"`）—— **只在 Civil NX 上抓取**；且 384 份契约中
   18 个 `-M1` 端点全部写 `products: [civil]`，**无一写 gen**。

**⚠️ 一个必须讲清的区分**：我方 §8.2 的既定口径是「`products` 声明的产品，其**实例**上路由 404
⇒ 摘除该产品」，但该口径有一条**明确的例外** —— `DB.UFTR`/`DB.UTBL` 声明 `[CIVIL_NX]` 却在
`civil-cloud` 上 404，§8.2 记载为「本来已如实记录 ⇒ **不动**」，因为摘除会让 `products` 变空。
因此本报告**不主张**这 21 条违反了 §8.2 的规则（同形的还有 `DB.UFTR`/`DB.UTBL`/`OPE.STORPROP`，
共 24 条，见 `docs/nxsdk_review/`）。

**本报告的主张是**：这 21 条与 `DB.UFTR`/`DB.UTBL` 的**关键差别**在于 —— 对外部证据而言，
Hyper-S 是**明确归属 Civil NX 的求解器特性**（对方在 Gen v2.2 上复测仍为 Civil-only），

**(a) 🔴 `Assign` 键被服务端静默重编号 —— 写路径删除的隐患**

对方 **A-79**：`Assign` 的键在下列端点上会被服务端**重新编号**：

> `/db/STLD`、`/db/TDME`、`/db/SPFC`、`/db/MVHL`、`/db/FIMP`、`/db/SMPT`、`/db/FBLD`、`/db/PNLD`

**(b) 🔴 写操作的响应体不是存储后的记录（echo ≠ store）**

对方 **E-19**：`/db/CONS` 的写响应回显 8 个字符，读回只有 7 个；

## 附录 A：比对口径与可复现性

本报告全部数字由 [`docs/nxsdk_review/scripts/`](scripts/) 下的 `p01`–`p59` 脚本机械产出，
无手工计数（`p01`–`p21` 为比对，`p22`–`p59` 为落地与复核）。关键口径：

- **端点配对**：我方 `manifest.endpoints[].uri` 去前导斜杠后大写，与对方 `info-baseline.json`
  的键（小写）配对。
- **ITEM 提取**：服务端 `/info` 的根键是 `Argument`，其内容是**单条记录**的 Schema；
  我方对应内容是 `properties.Assign.additionalProperties`（`Assign` 包装）或
  `properties.Assign.patternProperties["^[0-9]+$"]`（`patternProperties` 包装）或 `properties.Argument`。
