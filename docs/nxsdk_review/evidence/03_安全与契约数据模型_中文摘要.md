## 1. 安全与破坏性操作（来自 safety.md）

> safety.md 开篇声明：本页全部内容是 **MIDAS NX 产品与 API 的实测行为**（recorded from real sessions），
> **不是本包的缺陷**。完整复现记录在 `docs/live_verification_notes.md`。"Read this before your first write."

### 1.1 风险等级方案（Risk levels）

原文用一张 `Level | Meaning | Examples` 表给出 0–4 五级。未标注等级的内容，应按"可能适用的最高等级"处理，直到核实为止。

| Level | Meaning（原文） | Examples（原文） |
| --- | --- | --- |
| 0 | Connection / local check only | 检查已安装版本、`verify_connection()` |
| 1 | Read-only | 任意 `/db/*` 资源上的 `.items()`、`.get()` |
| 2 | Limited addition | 针对一次性测试模型（disposable test model）的 `.create()` |
| 3 | Modifies existing data | 对 materials、sections、loads… 的 `.update()` |
| 4 | High risk | `.delete()`、`delete_all()`、`doc.new_project()`、`doc.open_project()`、`doc.save_as()`、`doc.analyze()` |

配套规则（原文）：
- **3 级与 4 级** 必须：针对副本运行、发送前预览变更、发送后**读回数据**核实。
- **4 级** 尤其**绝不能放在自动重试循环里**（见"超时不等于回滚"）。

### 1.2 破坏性操作 / 崩溃 / 阻塞会话的危险（逐条）

每条给出：端点或调用、现象、触发条件、规避方式。

- **`delete_all()`（底层为手册记载的 `DELETE {endpoint}` + ID 键控 `{"Assign": {...}}` 体）**
  - 现象：**忽略 id、清空整张表**；对 `/db/NODE` 会连带删除挂在这些节点上的所有单元（every element attached to those nodes）。一次调用、模型消失、API 无撤销。
  - 触发条件：发送手册所记载的 `DELETE {endpoint}` 形式（或调用 `delete_all()`）。
  - 规避方式：`delete_all()` 必须 `confirm=True`，否则在**发送任何请求之前**抛 `DestructiveOperationError`——误调用零成本；删除指定记录用 `delete([4, 5])`，它按 id 逐个发出 **`DELETE {endpoint}/{id}`**（手册未记载的形式，精确删除单条记录）。原文明确：**不要把它"简化"回单次请求**。

- **`doc.new_project()` / `/doc/NEW`**
  - 现象：**丢弃当前打开文档中未保存的工作**；并且当打开的是大型真实模型时，**已导致 Gen NX 崩溃**（"Failed to disconnect the work session" 许可对话框，必定杀掉进程，并一直占用许可直到进程被正确重启）。
  - 触发条件：对打开着有未保存内容的文档（尤其大型真实模型）调用 `/doc/NEW`。
  - 规避方式：**先把文档弄成空状态并确认**（safety.md 原文）。补充（来源为 `CLAUDE.md`，非上述五文件）：绝不把 `scripts/live_smoke.py`、`scripts/live_crud_check.py`、`packages/typescript/scripts/live-crud.mjs` 指向装着要紧模型的会话；让用户先按 **New Project** 并确认文档为空。

- **模态对话框阻塞整个会话（modal dialog）**
  - 现象：任何对话框——确认提示、access-denied 错误、崩溃恢复通知——会阻塞该会话中**每一次** API 调用，而不只是触发它的那次调用，直到有人类手动关闭。
  - 触发条件：任何弹窗；另外**读操作也会触发**——一次普通的 `GET /db/CAMB` 就弹出了 access-denied 对话框，原因仅是打开文档位于 `Program Files`（标准账户无法写入该调用产生的辅助文件）。
  - 规避方式：工作文档**不要**放在 `Program Files` 一类位置。**没有 API 可见的信号**能表示会话被阻塞；唯一可靠的检查是"用短超时做一次廉价真实调用"。

- **`verify_connection()` / `/mapikey/verify` 的假阳性**
  - 现象：对话框挂起期间，`/mapikey/verify` 仍持续回答 `"connected"`（由 relay 提供），而每个 `/db/*` 调用都超时。
  - 触发条件：模态对话框挂起（或进程已死）。
  - 规避方式：把连接检查健康理解为"key 有效、且进程片刻之前还活着"，**不是**运行破坏性操作的许可。

- **已使产品崩溃的端点（Calls that have crashed the product）**
  - 现象：某些端点直接把活动会话杀死——进程死亡，**许可被占用直到被正确重启**。可识别的特征签名：`verify_connection()` 持续报 `"connected"`，而每个 `/db/*` 调用超时，随后进程死亡，后续调用抛 `MidasNotFoundError`（`"client does not exist"`）。
  - 触发条件：特定端点（凡复现成功处均已上报 MIDAS IT）。补充（来源为 `CLAUDE.md`，非上述五文件）：`*-ANAL` 设计检查调用在 Gen NX 2026 v2.1（build 06/23/2026）上可复现地挂死，随后在**同一 build** 上又运行正常——不是厂商修复，触发条件未查明。
  - 规避方式：使用**每次调用的短超时**，并**另行读回结果**，不要阻塞在一个可能永不返回的响应上。示例代码用 `perform_column_check({...}, client, timeout=25.0)` 捕获 `MidasConnectionError` 后仍执行 `get_column_check_table({...}, client)`。若只需要工程师已在 GUI 里算出的结果，**只读 `*-TABLE` 端点即可，无需任何 `*-ANAL` 调用**，也就不承担这类风险。

- **路径解析在 NX 所在机器上，不是你的机器上**
  - 现象：`EXPORT_PATH`、`/doc/SAVEAS`、`/doc/OPEN` 以及每个报告/图像路径都解析在**那台机器**上。在那台机器上不存在的路径会在**那台机器上**弹出模态对话框、阻塞会话，而你的 HTTP 调用仍然返回与成功无法区分的东西。
  - 触发条件：调用经过 MIDASIT relay，产品常运行在另一台 PC 上；路径指向那台机器上不存在（或账户不可写）的位置。
  - 规避方式：**用 `/doc/OPEN` 验证写入，绝不用 `os.path.exists()`**；让调用方显式给出 NX 机器上的可写目录。
  - ⚠️ **须注意的冲突**：safety.md 第 84–86 行建议 `user = client.verify_connection()["user"]   # build paths from this`。但 `CLAUDE.md`（同一仓库、2026-08-31 实测）明确记载该规则**已被推翻**：该字段是 MAPI 账户的邮箱（`sjj0507@midasit.com`），不是 NX 主机的 Windows 用户配置目录，据此拼出的路径恰好会触发上述阻塞对话框。下游项目**不应**采用 safety.md 的这一行。CLAUDE.md 的结论是：要求显式提供 NX 机器上的可写目录（`--save-dir`）。

- **`/doc/SAVEAS` 的失败形态**
  - 现象：对一次**从未发生**的保存回答 `"... command complete"`；Gen NX 则**完全不回答**——调用一直挂起直到对话框被关闭。（形态随**产品**而非仅随路径变化，见 §2。）
  - 触发条件：写入账户不可写的目录等。
  - 规避方式：读回并**阅读消息本身**；不要用 `os.path.exists()`。

- **`/doc/ANAL`**
  - 现象：失败的求解被报告为 `{"message": "... Analysis failed."}`，**没有 `error` 键**。
  - 规避方式：不要依赖 `MidasResultError` 覆盖这种情况；另见下面的"读回验证"。

- **超时不等于回滚（Timeouts are not rollbacks）**
  - 现象：客户端超时只表示你停止等待，**不表示服务器停止工作**——操作很可能在之后完成。
  - 触发条件：任何写操作超时。
  - 规避方式：任何写超时后，**先重读状态**再判断发生了什么。本 SDK **从不自动重试**（正是这个原因）：对已成功的端点重发 `POST` 是第二次写入，不是恢复。

- **连接故障排查（Connectivity troubleshooting）**
  - `MidasConnectionError` 几乎总是意味着 MIDAS Gen/Civil NX 没在运行、没通过 Open API 连接，或连接在会话中途死掉。`client.verify_connection()` 是区分它们最快的方式。
  - 应用在跑却连不上，通常是企业防火墙拦了到 MIDAS relay 的出站流量。给网络/安全团队的信息：

    | Item | Value |
    | --- | --- |
    | Protocol | `https`, `wss` |
    | Port | `443` |
    | IP | `121.157.60.1/32`（MIDAS public NAT IP） |
    | URI | `https://moa-engineers.midasit.com` |

  - 若网络对所有出站流量做 SSL 检查/拦截，`moa-engineers.midasit.com` 必须被排除；已有多起静默连接失败专门由 SSL 检查造成。当某台设备代替产品作答时，会得到 `MidasServerError`，内容为 `response body is not JSON: '<html>...'`——这条消息就是"你与 MIDAS 之间有人在拦截"的标志。

- **会写入的脚本（Scripts that write）**
  - 原文：本仓库 7 个实况脚本中，**只有 2 个**可以指向你在意的模型，**另外 5 个不行**。

    | Script | Safe against an open model? |
    | --- | --- |
    | `scripts/live_readonly_sweep.py` | ✅ GET only |
    | `packages/typescript/scripts/live-readonly.mjs` | ✅ GET only，npm 等价物 |
    | `scripts/live_smoke.py` | ❌ 调用 `/doc/NEW` —— **丢弃未保存工作** |
    | `scripts/live_crud_check.py` | ❌ 调用 `/doc/NEW`，随后创建、更新、删除真实记录 |
    | `packages/typescript/scripts/live-crud.mjs` | ❌ 同上，来自 npm 包 |
    | `scripts/live_manual_feedback.py` | ❌ 每次探针调用一次 `/doc/NEW`（调查文档缺陷期间） |
    | `packages/typescript/scripts/live-analysis.mjs` | ❌ 不调用 `/doc/NEW`，但会**向你打开的模型**加一列并跑一次求解，然后删掉它加的东西 |

  - 五个脚本都会把 checkpoint 写到**运行 NX 的那台机器**上由 `--save-dir` 指定的目录；没有一个会去猜路径（猜的路径在那台机器上不存在 → 那边弹对话框阻塞会话，而 HTTP 调用仍像成功一样作答）。
  - 自 **2026-09-21** 起，四个调用 `/doc/NEW` 的脚本以完全相同的方式询问，并且在你什么都没指定时**拒绝启动**——规则与理由在 `scripts/harness_save_path.py`。`--save-dir` 接收**目录**，文件名由产品推导，因此 NX 扩展名（Gen `.mgbx`、Civil `.mcbz`）不可能写错。`--no-save-before` 免除 checkpoint，**不**免除 `/doc/NEW`。两处明示的例外：`scripts/live_crud_check.py` 还接受 `--save-as` 指定精确路径；`scripts/live_manual_feedback.py` 完全没有豁免项，因为它的逐探针保存是这次运行产出的证据，而非安全网。

### 1.3 "HTTP 200 响应不等于成功" 规则与错误模型事实

原文称之为"本页最重要的一件事"：

- 若干端点会在 **2xx** 状态码下用 `{"error": {...}}` 体报告一次拒绝。本 SDK 对此抛 `MidasResultError`；想要原始响应体可用 `MidasClient(raise_on_result_error=False)` 退出该行为。
- **有些连 `error` 键都没有**：`/doc/ANAL` 把失败的求解报告为 `{"message": "... Analysis failed."}`；`/doc/SAVEAS` 对一次从未发生的保存回答 `"... command complete"`。
- **错误体也曾出现在 `201` 之下，而不只是 200**。
- 也就是说：**可以携带错误体的 HTTP 状态**是 **200 与 201**（原文的表述为"2xx 状态码下"、"也曾在 201 之下"）。
- 真正保护你的规则（原文以 tip 框强调）：**写操作要用读回来验证**。不是靠信任响应；对任何与文件有关的事情，也**不是**靠 `os.path.exists()`。

### 1.4 恢复指引（Recovery）

原文：只要恢复方式正确，这些崩溃在**两个产品上均未观察到数据丢失**。

1. 关闭对话框（Dismiss the dialogs）。
2. 重新启动 Gen NX / Civil NX（Relaunch）。
3. 按 **New Project**。
4. **正确关闭应用**（这样才会释放许可）。
5. 用同一个 MAPI key 重新连接。

之后通过**对比记录数与崩溃前的数量**来核实模型。

## 4. 契约数据模型（来自 contracts/README.md）

### 4.1 契约文件是什么

`contracts/` 目录中的一切描述的是 **MIDAS NX Open API 本身**，而不是任何包装它的 SDK。Python 包与 npm 包是这里所写内容的**两个平等实现**；两者谁都不比谁高，也谁都不是对方的来源。

它存在的直接原因（原文 "Why this exists"）：`POST /db/NMAS` 在省略可选字段 `rmX`/`rmY`/`rmZ` 时会崩溃 MIDAS NX。该问题于 **2026-07-29** 定位根因并在 `NodalMass.create()` 中绕过。npm 包于 **2026-08-26**（一个月后）从同一份 Python 源码生成，**没有带上这个绕过**，因此任何经它到达 `/db/NMAS` 的调用者仍可能挂死并杀掉一个活动 NX 会话。原因不是疏忽：生成器把元数据和 docstring 搬了过去，而绕过是**方法内部的行为**，行为无处可放。**只存在于一个实现里的安全规则，只能到达那个实现的用户。** 所以规则被移到这里，成为关于端点的事实，而不是某语言绑定的属性，并由 `scripts/validate_contracts.py` 在实现不遵守时让 CI 失败。

**布局（原文 Layout 一节）**：

```
contracts/
  README.md                          this file
  schema/
    endpoint-contract.schema.json    JSON Schema for contracts/endpoints/*.yaml
  endpoints/
    db-node.yaml                     one file per endpoint; file name == `id`
    db-nmas.yaml
    db-grup.yaml  db-rigd.yaml  db-offs.yaml  db-co-m.yaml
  drafts/                            git-ignored; `draft: true`, not contracts
  safety/
    known-product-risks.yaml         cross-endpoint client rules + product defects
  verification/
    gen-nx.yaml                      dated, build-specific live findings
    civil-nx.yaml
```

另有 `contracts/tables/*.yaml`（结果表契约）、`contracts/verification/ledger.yaml`（实况证据账本）、`contracts/schema/table-contract.schema.json`。验证记录**按产品拆分**是有意为之：产品支持是**观察事实**而非手册主张，且两个产品会分叉——`/db/REBW` 只在 Gen 上作答，Hyper-S（`-M1`）家族只在 Civil 上作答，手册框定为 Civil-only 的 47 个端点中有 **32 个**在 Gen 上也作答。单一份共享记录无法承载按产品区分的日期与 build。

### 4.2 顶层字段模式（`additionalProperties: false`）

`required`：`contractVersion`、`id`、`endpoint`、`name`、`products`、`source`、`verification`、`operations`。

| 顶层键 | 结构 / 取值（精确拼写） | 含义 |
| --- | --- | --- |
| `contractVersion` | `const: 1` | 本契约文件的格式版本。仅在模式发生不兼容变化时才提升 |
| `draft` | `const: false` | `contracts/drafts/` 下的机器草稿带 `draft: true`，它们**不是契约**。审查草稿就是移除这个标记；在此之前文件无法通过校验——这正是阻止"未经审查的转写被移进 `contracts/endpoints/` 并被当作事实"的机制 |
| `id` | `^[a-z0-9]+(-[a-z0-9]+)*$` | 稳定 slug；**必须与去掉 `.yaml` 的文件名一致** |
| `endpoint` | `^/` | 追加到产品 base URL 的路径，例如 `/db/NODE` |
| `name` | string, minLength 1 | 手册标题所用的可读端点名 |
| `surface` | `className` / `exportName` / `modulePath` / `payloadTypeName` / `nestedTypes[]` | **已发布 SDK 对这个端点的称呼**。文件里其他一切都记录产品与手册说了什么；这里记录**包把它命名成了什么**，使名字不再是某个 Python 模块所在位置的偶然产物，而成为生成器会校验的契约事实。**可选**：没有契约 surface 的端点继续走已审查的 Python fallback（与 `name`、`products` 同样的安排） |
| `summary` | string | 一到两句话说明该端点做什么 |
| `products` | `["gen"｜"civil"]`，minItems 1，uniqueItems | **实际提供该路由的产品**。产品支持是**观察事实，不是手册主张**：手册的 Civil-only 框定对 47 个端点中的 32 个是错的 |
| `productsEvidence` | string | 当 `products` 偏离手册框定时，说明它为什么这样读 |
| `recordKey` | `{kind: 枚举, description}`，`kind` 必填 | **对 ID 键控端点，`Assign` 映射的键意味着什么**。`kind` 取值：`record_id`、`node_id`、`element_id`、`index`、`singleton`（`singleton` = 该端点持有**一条设置记录**，不是一张表） |
| `source` | `{manual, liveSchema, liveNotes}`，`manual` 必填 | 契约事实的来源记录（见下） |
| `verification` | `{status, records[]}`，`status` 必填 | 这份契约对照运行中产品检查到了什么程度。`status` 取值：`manual_only`、`verified_gen`、`verified_civil`、`verified_both`；`manual_only` 表示**已转写但从未调用过**。`records[]` 每项 `{product: gen｜civil, ref}`，`ref` 是 `contracts/verification/{gen,civil}-nx.yaml` 中某条目的 `id` |
| `operations` | 每个 HTTP 方法一项，必填 `method`、`risk`、`request`、`response` | 见 §4.3 |
| `fields` | `field[]` | **记录载荷的逐字段契约**（ID 键控 `Assign` 映射的值侧，或请求 `Argument` 对象） |
| `variants` | `variant[]` | **由单一显式判别字段选择的、互斥的手册字段表**。条件未被陈述的表留在 `extraction.unmergedTables` 下，而不是被猜进这个结构 |
| `sdkRules` | `sdkRule[]` | **每个 SDK 实现都必须在请求到达产品之前应用的行为。这些是契约的牙齿**：漏掉一条的实现就是不合规的，无论它把载荷类型写得多好 |
| `manualDefects` | 对象数组，必填 `describes`/`manualSays`/`actual`/`evidence` | **官方手册在这个端点上的错误之处**，与契约本体分开保存，使一次手册重新同步无法悄悄把它们带回来 |
| `extraction` | `{source, table, mergedSections, missingColumns, unmergedTables, prose, structuralTables, note}` | `scripts/extract_contracts.py` 从手册章节起草这份契约时留下的溯源。**提升之后仍然保留**：知道一份字段表来自哪里，才能让 `--check` 分辨漂移与有意更正 |
| `infoOnly` | `[{path, reason}]` | **`GET /info{endpoint}` 声明了、而本契约有意不发布为字段的属性**，各带理由 |
| `sdkOnly` | `[{name, reason}]` | **Python SDK 发布了、而本契约有意不发布的线上名**，各带理由 |
| `knownDefects` | `[{ref, note}]`，`ref` 必填 | 影响本端点的产品缺陷。`ref` 指向 `contracts/safety/known-product-risks.yaml` 中某个风险的 `id` |

### 4.3 重要嵌套键

**`source`**：
- `manual.status`：`documented`（手册描述了该端点且实况行为相符）、`absent`（不存在手册章节，**需要 justification**）、`contradicted`（存在手册章节但实况行为证伪了它，**需要 justification**；契约记录实况行为，`manualDefects` 记录手册错在哪）。
- `manual` 其余键：`repo`（通常 `Dennis5882/MIDAS-API`）、`chapterFile`（`docs/manual/` 下的章节文件，如 `03_DB_Node_Element.md`，pattern 要求 `.md$`）、`section`（章节内的节标识，如 `"1. /db/NODE"`）、`url`（该端点的官方 MIDAS API Online Manual 文章 URL）、`justification`。
- 条件必填（`allOf`）：`status: documented` → 必填 `chapterFile` 与 `section`；`status: absent｜contradicted` → 必填 `justification`。
- `liveSchema`：`{checked: date, products[], note}`——`GET /info{endpoint}` 模式自省，**在被用作来源时**才记录。
- `liveNotes`：仓库相对路径的散文证据数组，通常 `docs/live_verification_notes.md`。

**`operations[]`**：
- `method`：`GET`、`POST`、`PUT`、`DELETE`。
- `variant`：区分共享同一方法的两个操作，例如 DELETE 按 id 删除 vs DELETE 整表删除。
- `path`：当操作使用不同路径时覆盖 `endpoint`，例如 `/db/NODE/{id}`。
- **`risk`（描述端点）**：`read_only`（不能改变模型数据）、`write`（改变模型数据或在 NX 主机上写文件）、`destructive`（删除无法通过 API 恢复的数据）、`product_crash_risk`（曾被观察到结束或挂死一个活动 NX 会话）。
- **`mitigation`（描述 SDK 做什么）**：`none`、`normalized`、`confirmation_required`、`opt_in_required`、`warn_only`。模式层条件必填：`risk` 为 `destructive` 或 `product_crash_risk` 时 **`mitigation` 必填**。
- `request` / `response`：`$defs/message`（见下）。无体请求用 `wrapper: none`。
- `surface`（操作级）：`exportName`、`modulePath`、`argumentTypeName`、`argumentParts`、`takesArgument`、`documentation`、`nestedTypes`。
- `notes`。

**`$defs/message`**：
- `wrapper`：`none`、`assign`、`argument`、`table`、`message`、`raw`、`unknown`。模式原文：`assign = {"Assign": {id: payload}}`；`argument = {"Argument": payload}`；`table` = 单个承载 HEAD/DATA 或记录映射的对象；`message = {"message": ...}`；`raw` = 载荷本身；`none` = 无体；`unknown` = 许可来源既未确立响应体、也未确立其形状。
- `keyStability`：`stable`、`unstable`。`unstable` 表示顶层键在多次调用间变化，必须**按形状匹配、绝不按键名匹配**；已在 `/post/TABLE` 响应上观察到（`"Result Table"`、`"empty"`，或请求的 `TABLE_NAME`）。配套 `keyNote`。
- `itemSchema`：`fields`、`none`、`scalar`、`empty`。`scalar` = 整个参数是一个原始值而非带字段的对象（`/doc/OPEN` 发送一个裸路径字符串），其类型在 `scalarType` 中命名；`empty` = 参数是一个手册记载为空的对象；`scalar` 与 `empty` **都不是**未记录载荷的简写——来源未描述的体用 `none`。
- `scalarType`：`string`、`number`、`integer`、`boolean`。当 `itemSchema` 为 `scalar` 时必填，否则不得出现（模式用 `if/then/else + not` 强制）。
- `errorShapes[]`：`{httpStatus: integer[], shape, meaning}`——**该操作已知会返回的失败体。模式原文：A 200 or 201 does not mean success on this API.**
- `description`。

**`$defs/field`**（`required`: `key`、`type`、`requirement`、`documentedOptional`、`safeToOmit`、`provenance`）：
- `key`：`^[A-Za-z0-9_]+$`——**一个**字面线上属性名。命名多个键的手册行必须拆分，或保持未提升状态。
- `type`：`string`、`number`、`integer`、`boolean`、`array`、`object`、`unstated`。`unstated` 表示手册未给类型；**它不是被推断出来的 string，也不是未知的 JSON 形状**。
- `items`（`$defs/valueType`）、`properties`（嵌套 `field[]`，`type` 为 object 或数组元素为对象时）。
- **`requirement`**：`required`、`optional`、`conditional`、`read_only`、`create_only`、`unstated`。`read_only` = 服务器返回它、写入时忽略它；`create_only` = 手册说服务器在创建时尊重它、修改时忽略它，且**与这里每个取值一样，它记录的是文档**——2026-09-03 测得手册对该值的两处使用中有一处为假，所以携带它的契约应说明是否有人核实过；`unstated` = 手册未给出必填性主张。
- `condition`：`requirement` 为 `conditional` 时必填——手册条件原文逐字保留。**这是来源陈述**；`appliesWhen` 是它单独维护的结构化翻译。
- `appliesWhen`：`condition[]`，minItems 1——为生成与调用者文档而对手册条件做的结构化翻译。每一项必须命名一个**已存在的契约字段路径**；各项以逻辑 **AND** 组合。它**不替代** `condition`。
- `documentedDefault` / `documentedDefaultNote`：见 §4.5。
- **`documentedOptional`**：boolean 或 null。是否官方手册把该字段标为可选。**仅当 `requirement` 为 `unstated` 时才允许为 null**，因此不会凭空造出文档主张。**这是关于文档的陈述，绝不是关于观察行为的陈述。**
- **`safeToOmit`**：`true`、`false`、`"unverified"`。**省略该字段对照运行中的产品是否真的安全。** 模式原文：`unverified` 对大多数字段是诚实答案，不是较差状态——它说的是没有人对照运行中的产品省略过它。`true` 是关于**产品**的主张，需要 `omissionEvidence`；`false` 需要 `omissionEffect`，且若该字段同时是 `documentedOptional`，它必须被某条 `sdkRule` 覆盖。
- `omissionEffect`（`safeToOmit: false` 时必填）、`omissionEvidence`（`safeToOmit: true` 时必填）。
- `enum`、`enumNote`（手册自相矛盾时，列出所有候选并用 `enumNote` 说明先试哪个）。
- `minimum`、`exclusiveMinimum`、`maximum`、`exclusiveMaximum`、`notEqual`、`const`、`minItems`、`maxItems`、`minLength`、`maxLength`、`unit`。
- **`provenance`**：`manual`、`live_verified`、`live_corrected`、`info_schema`。模式原文：`manual` = 从手册章节转写；`live_verified` = 手册与实况检查相符；`live_corrected` = 手册错了、由实况检查取代（把不一致记录到 `manualDefects` 下）；`info_schema` = 取自 `GET /info{endpoint}`。**这里没有任何取值表示 SDK 实现，而 SDK 永远不是许可来源。** 另有 `provenanceNote`。
- 模式层条件（`allOf`）：`safeToOmit: false` → 必填 `omissionEffect`；`safeToOmit: true` → 必填 `omissionEvidence`；`requirement: conditional` → 必填 `condition`；出现 `documentedDefaultNote` → `documentedDefault` 必须为 `null`；`requirement: unstated` → `documentedOptional` 必须为 `null`；`documentedOptional: null` → `requirement` 必须为 `unstated`（**双向强制**）。

**`$defs/variant`**（必填 `when`、`source`、`fields`）：
- `when`：`condition[]`，minItems 1——选择本变体的条件，以逻辑 **AND** 组合。与字段的 `appliesWhen` 同形，因此嵌套判别（`STR.SPEC_CODE`）、多值表（`FLOOR_DIST_TYPE = 1 or 2`）与两级选择器（先 `TYPE` 后 `STYPE`）都无需第二套构造即可表达。
- `source`：`{table, line}`，line ≥ 1。
- `fields`：`field[]`。

**`$defs/sdkRule`**（必填 `id`、`kind`、`appliesTo`、`reason`）：
- `id`：`^[a-z0-9]+(-[a-z0-9]+)*$`。
- **`kind`**：`normalize_defaults`（发送前用 `values` 填充所列字段）、`require_confirmation`（除非调用者传入显式确认标志，否则拒绝）、`reject_request`（抛校验错误而不发送）、`per_id_request`（按 id 逐个、顺序发出请求，首次失败即停止）、`unwrap_table_by_shape`（按 HEAD/DATA 对象形状定位不稳定的结果表载荷，**绝不按顶层响应键**）、`warn`（大声记录文档；不改变行为）。
- `appliesTo`：`GET`/`POST`/`PUT`/`DELETE` 数组，minItems 1。另有 `variant`。
- `fields`：该规则覆盖的载荷字段（用于 `normalize_defaults` 与 `reject_request`）。
- `rejects`：`empty_value`（字段存在但携带一个服务器接受并丢弃的值，如 `/db/MVHL` 的空 `VEH_DEFAULT`）、`omission`（字段缺失，于是服务器应用一个它随后拒绝的文档默认值，如 `/db/PRES` 的 `DIRECTION`）、`forbidden_combination`（各字段单独有效但不能一起发送，如 `/ope/GSBG` 的批处理组与单组）。模式原文：三者需要不同的检查，而单凭 `kind` 说不出是哪一个，所以要写明而不是从规则的散文里推断。
- `values`：`normalize_defaults` 的字段→值映射。**取值必须与文档默认值相符；该规则存在的目的是把默认值显式化到线上，而不是发明一个默认值。**
- `responseCases`：`table_name`（请求的 `TABLE_NAME` 键）、`result_table`（实况 `'Result Table'` 键）、`empty_with_table`（实况 `'empty'` 键且承载真实表格）、`no_table`（没有表形状的值）。用于 `unwrap_table_by_shape`，此时**必须恰好 4 项**（minItems 4 / maxItems 4）。
- `reason`：规则为何存在，详细到未来的维护者不会把它误当仪式而删掉。
- `riskRef`：`contracts/safety/known-product-risks.yaml` 中某风险的 `id`。`alternative`：对 `require_confirmation` 与 `reject_request`，调用者应改做什么。
- 模式层条件：`kind: normalize_defaults` → 必填 `fields` + `values`；`kind: unwrap_table_by_shape` → 必填 `responseCases`（恰好 4 项）；`kind: reject_request` → 必填 `fields` + `rejects`。

**`$defs/condition`**：必填 `path`（`^[A-Za-z0-9_]+(?:\.[A-Za-z0-9_]+)*$`，点号记法、含嵌套对象或数组项属性），并且 `equals`（手册记载的单一字面值）与 `in`（两个或更多字面值，minItems 2、uniqueItems）**二者恰有其一**（`oneOf`）。`equals` 与 `in` 互斥。

**`manualDefects[]`**：
- `describes`：`field_name`、`field_value`、`default`、`requiredness`、`enum`、`method`、`products`、`behaviour`。
- `manualSays`、`actual`、`evidence`。
- `reportedToVendor`：厂商报告条目标识，例如 `"A-1"`。**模式原文：No internal tracker IDs here; this file is public.**

**`extraction`** 子键：
- `source`（读出该字段表的章节文件与行号）、`table`（产出 `fields` 的那张表的标题）。
- `mergedSections[]`（minItems 2）：因为记录同一路由而被折进这份契约的手册章节，`{heading, line}`。RC 与 SRC 设计章节为每个结果表各描述一次 `/DESIGN/.../TABLE`，并声明只有 `Argument.TABLE_TYPE` 能区分它们；把每一节列出来使这次折叠可被审查，而不是让某一节默默代表其余。
- `missingColumns[]`：**整张手册表都缺失的列**。这是**完整溯源，不是逐字段的不确定性**：`documentedDefault: null` 诚实地记录一个缺失的 Default 列。
- **`unmergedTables[]`**（必填 `heading`、`line`、`resolution`）：同一节中**未被合并**的参数表，通常是按某个类型或代码字段选择的**条件变体**。列出来而不是合并或丢弃：**一份被当作完整的残缺字段表，本身就是一种错误答案。** 契约可以携带它们并仍被提升，但每个条目都需要一个 `resolution` 说明审查决定了什么；并且**只要还存在任何一个这样的条目，npm 生成器就不把本契约的字段表当作已发布载荷类型**——在自认不完整的字段表上收窄一个已发布的类型，恰恰是最错的答案。
  - `fields`（整数，计数）与 `fieldNames`（minItems 1，线上名数组，按表序、含嵌套行）。模式原文：`fields` 只给出计数，**而计数不能作为豁免**——它说存在一个缺口，却不说缺口里是什么。在它存在之前，`validate_contracts.py` 的字段一致性检查会因为任何 `unmergedTables` 条目而整份跳过该契约，于是 **214 个** SDK 发布而契约未记录的线上名未被检查；有了名字后豁免被**逐项化**：这里出现的名字是已声明缺口，既不在契约里也不在这些列表里的名字才是缺陷。
  - `resolution`：审查对这张表的决定——并入 `fields`、建模为嵌套属性、拆成自己的契约，或因为手册未命名线上判别字段而有意排除。**在已提升的契约上必填：一个未解释的缺口与一个被忽略的缺口无法区分。**
  - `excluded`：boolean。为 true 表示审查已带证据地判定（证据记在 `resolution`）这张表**根本不属于本 API 的请求**——`/db/TDME` 的两张 Japan 代码表属于 iGen，其代码在两个 NX 产品上都回答 Wrong Field。此时该契约的字段表对本 API 是完整的，并成为已发布载荷类型；**没有这个标志的条目仍然意味着列表不完整**。
- `prose[]`（必填 `line`、`quote`、`paths`）：手册**在参数表行之外**陈述的字段——在一句话里，或在另一张表的单元格里。`scripts/extract_contracts.py` 读的是行，看不到这些，否则它的漂移检查会把每一个都报成契约发明的字段。**这不是 `manualDefect`**：手册记录了它们，只是没写成一行。`/db/GRDP` 是"一句话"的范例（一句话说出 `GROUP_DAMPING_ITEMS` 的十五个成员就是不带后缀的 `_DEFAULT` 字段）；`/db/ELNK` 是"单元格"的范例（第二张表在它的 추가 키 列里列出每种 `LINK` 类型的额外键，这正是该记录全部八个条件字段被陈述的地方，也是 `quote` 可以逐字保存表格行的原因）。
- `structuralTables[]`（必填 `heading`、`line`、`paths`，另有 `note`）：具名对象或数组目的地已被提取器转写的补充手册表。**这是结构化合并的证据，不是条件变体的豁免。**
- `note`：当本契约的字段并非来自 `source` 命名的那张手册表时，说明为什么。手册章节本身出错时需要它：`/db/REBW` 的提取草稿被**丢弃而非审查**，因为提升它的任何部分都会把一个服务器并未实现的模式放进真源。

### 4.4 许可来源，以及契约可以/不可以主张什么

**许可来源（Permitted sources）**：

| Source | Use it for |
| --- | --- |
| `Dennis5882/MIDAS-API` 的 `docs/manual/*.md` | 字段名、类型、默认值、必填性、枚举、方法 |
| `docs/live_verification_notes.md` | 一次真实 Gen NX / Civil NX 会话实际做了什么 |
| `GET /info{endpoint}` | 服务器自己的模式，用于手册描述很差的端点——**仅限 `/db/*`** |

- `/info` 并非每个端点都有。2026-09-01 从两个 SDK 扫描：它为 **402 个 `/db/*` 资源-产品对中的 399 个**作答，而为 **147 个 `/DESIGN/*` 对中的 0 个**作答（设计端点本身对普通 GET 有响应）。**三个 `/db/*` 例外**是 Civil Hyper-S 三件套 `/db/IEHG-GL-M1`、`/db/IEHG-PSS-M1`、`/db/IEHG-TRUSS-M1`。因此**设计规范契约只有两个许可来源，不是三个**，且 `provenance: info_schema` 对它不可用——**不要把那里的 404 读成回退到某个 SDK 的理由**。
- **被禁止的来源：`src/midas_nx/` 与 `packages/typescript/src/`。** 不是因为它们不可信，而是因为**从实现推导出的契约无法发现那个实现是错的**。`validate_contracts.py` 读这两个 SDK，并把它们读作**被测对象**：当契约与某个 SDK 不一致时，结论是 **SDK 缺陷**。通过编辑契约来"修复"它，会摧毁整个安排。
- 每个字段都在 `provenance` 里记录它来自哪里（四个取值见 §4.3）。**刻意没有一个取值表示"从 SDK 读来的"。不要凭猜测让一个字段或行为存在：手册没有描述、也没人观察到的东西，不属于契约。**

**`info_schema` 的两条规则**（`scripts/contract_from_info.py` 强制执行，因为"没人能交叉核对的来源，恰恰最需要它们"）：
- **沉默不是许可（Silence is not permission）。** `/info` 不声明 `required` 数组，所以每个字段都是 `unstated`。**不是 `optional`**——那是一个没有任何文档做出的、关于文档的主张。
- **`description` 里的取值集合不是 `enum`，更绝不是变体。** `/info` 模式是平的、任何地方都不陈述分支，所以从散文里读出的判别字段会是一个**被装扮成关于这次抓取的事实**的、关于端点的推断。`/db/MATL` 的契约从手册的相同散文起草，也把它的取值留在 description 里。**门控必须来自手册或一次实况观察。**

**契约可以 / 不可以主张什么**：
- `request.wrapper` 与 `response.wrapper` **只描述许可来源支持的形状**。当手册确立了路由与方法、但对响应体只字未提时，响应用 `unknown`。**它不是 `table`、`message` 或空体的简写，也不得从某个 SDK 实现收窄而来。** 这对若干非 `/db` 设计资源 DELETE 示例很重要：手册展示了无体的 `requests.delete(...)` 调用，但未陈述其删除范围或响应。
- **`variants` 仅在每一张附加手册表都命名同一个线上判别字段及一个精确值时使用**，例如 ``TYPE = "EIGEN"``。每个变体保留其来源表与行号，其字段**不并入**公共字段列表。像 "LINEAR only" 这样的标题**不确立选择器取值**；它留在 `extraction.unmergedTables` 里，直到手册陈述得足以在不做推断的情况下建模。
- **`in`** 转写的是一个标题为**同一张表**命名多个取值的情况（`/db/FBLA` 的 `FLOOR_DIST_TYPE = 1 or 2`、`LOAD_MODEL=2/3`）。**它绝不是对枚举其余部分的猜测：其中的每个取值都写在了手册里。** 这样的表是手册的**共享**表，不是又一个分支：`/db/FBLA` 为 `= 1` 描述一张表、为 `= 2` 描述一张表、为 `= 1 or 2` 描述一张表，第三张对两者都适用。因此 **`in` 命名的每个取值都必须已经拥有自己的单值分支**，而 TypeScript 生成会把共享字段折进它所覆盖的每个分支，而不是发出一个会对同一判别字段匹配两次的联合成员。
- `in` **刻意不解决**的问题：两张表主张**同一个单值**。`/db/NLNK` 把 `REF_SYSTEM=1` 拆成 Angle/3Points/Vector，`/db/HSFC` 按是否使用混凝土数据拆 `TYPE="FUNC"`——两者的第二选择器都是真实存在的，但手册从未把它命名为线上字段。**这些保持未合并。一个没有被写下来的判别字段无法被转写。** 同一规则也会抓住只命名了门控**一半**的标题：`/db/ELEM` 跨四种单元类型把五张表标题写作 `STYPE: 1` 到 `STYPE: 3`，所以 `STYPE: 1` 同时标题一个只受拉的桁架和一个只受压的桁架；判别字段是与 `TYPE` 组成的**一对**，其线上取值放在章末脚注代码表里而非标题中。**重复的取值就是证据**，因此提取器把每一张以重复字段为门控的表都留在未合并状态，而 `validate_contracts.py` **拒绝任何——包括手写的——变体把一个条件主张两次的契约**。
- **未合并的表不再阻塞契约。** 手册不完美，产品也不完美，所以一份说"这些字段，外加一张我无法建模的表"的契约，比根本没有契约更有用。把每张这样的表记到 `extraction.unmergedTables` 下并附一个 `resolution`——"the manual names no wire discriminator; left unmerged" 就是一条正当的 resolution，重点在于**说出来**而不是"已经解决了"。`promote_contract.py --resolution` 会写入它，因为草稿是重新生成的构建产物、不能手改。**这样一份契约不可以做的是收窄一个已发布的类型**：只要存在任何 `unmergedTables` 条目，npm 生成器就忽略本契约的字段表并保留已审查的 fallback 载荷，因此提升一份不完整的契约**绝不会**破坏一个设置了那张没人合并的表里字段的调用者。其他一切——products、methods、risk、`sdkRules`——照常由契约拥有。
- **一条路由就是一份契约。** 一个端点可以被描述不止一次：RC 与 SRC 设计章节为 `/DESIGN/RC/KDS-41-20-2022/TABLE` 和 `/DESIGN/SRC/AIK-SRC2K/TABLE` 各描述一次**每个结果表**——两条路由五个节——而每一节都明说它与兄弟节共享 URI、**仅**靠 `Argument.TABLE_TYPE` 区分；第 17 章同样有意为桥梁章的读者重复第 15 章的 `/ope/GSBG`。`scripts/extract_contracts.py` **仅当**手册自己的主张成立时才折叠这些节：它们的字段表处处一致，或除一个字段外处处一致。被折的那个字段保留各节命名的每个取值（章节给了枚举就用 `enum`），并保留各节描述拼接后的结果，因为每一节都称**它自己**的取值是固定的，而"三者之一"是手册从未说过的话。`extraction.mergedSections` 列出所有并入的节，使这次折叠可对照章节审查而不必凭信。**更宽的折叠会被拒绝**，emit 运行会说明它拒绝了哪些节：`/ope/GSBG` 的两章对同一端点的转写不同（一章把 `Required (BATCH=true)` 写在行内，另一章用粗体变体表头），把它们平均会发布一个两章都没陈述过的请求形状。反过来把一个共享路由拆成每节一个 id 同样错：那会发明手册没有描述的路由。**响应列不参与折叠**，它们属于 `contracts/tables/` 下按 `TABLE_TYPE` 键控的表契约。
- **不是字段列表的参数**：`request.itemSchema` 说明参数携带什么——`fields`（本契约的字段列表）、`scalar`（一个原始值，在 `scalarType` 中命名）、`empty`（手册记载为不携带任何内容的对象）、`none`（无体）。九个 `/doc/*` 节有 JSON Schema 而无 Specifications 表，**这是文档而不是缺口**：`/doc/OPEN` 与 `/doc/SAVEAS` 接收一个裸路径字符串；`/doc/NEW`、`/doc/CLOSE`、`/doc/SAVE` 接收 `{}`。对它们而言**空 `fields` 列表就是正确的转写**，所以提升与手册漂移检查在请求显式如此说明时都接受它。`scalar` 与 `empty` 是**关于文档的主张，不是逃生舱**：许可来源未描述的体仍然是 `none`。
- **`documentedOptional` 与 `safeToOmit`**（原文：这两个分开建模，**这个区别是本模式里最重要的一件事**）：前者是关于**文档**的陈述，后者是关于**产品**的陈述。`/db/NMAS` 的 `rmX` 是 `documentedOptional: true` 且 `safeToOmit: false`——手册说该字段可选是对的，**照着手册做却会杀掉会话**。把两者合成一个布尔量，恰好丢掉那个会伤人的情形：读了文档并照做的调用者。`safeToOmit` 有三个取值，且 **`unverified` 不是较次的一个**：

  | Value | Means | Requires |
  | --- | --- | --- |
  | `true` | 一次实况调用省略了它并成功 | `omissionEvidence`，引用那次调用 |
  | `false` | 有人省略了它并且出了事 | `omissionEffect`，且若该字段同时是 `documentedOptional` 还需一条 `sdkRule` |
  | `unverified` | 没有人对照运行中的产品省略过它 | 无 |

  **大多数字段是 `unverified`，而说出来正是重点。** "手册说 Optional" **不是** `true` 的证据——那正是 `documentedOptional` 已经记录的内容，把它当作答案恰恰是 `/db/NMAS` 惩罚的推理。最早手写的两份契约弄错了这点并被更正：它们的坐标与平动质量现在读 `unverified`，因为 `scripts/live_crud_check.py` 的已确认载荷会发送它们全部。有证据时，证据是机械的：该检查器有 **116** 个用例标记 `confirmed=True`，意味着有人看着那个精确载荷完成了一次实况往返；一个已记录字段不出现在这样的载荷里，就说明它被省略了而调用仍然成功。`scripts/extract_contracts.py` 读取这些载荷，并填入 `safeToOmit: true` 并引用该用例——**437 个字段，跨 72 个端点**。
- **文档默认值**：`documentedDefault` **只携带手册无歧义陈述的字面线上值**。当 Default 单元格含有像 `System`、`Auto` 或 `ADD, REPLACE` 这样的散文时，保持 `documentedDefault: null` 并在 `documentedDefaultNote` 里保留手册单元格原文。该注记记录的是手册的措辞；**它不是关于服务器的主张，也永远不是某字段可安全省略的证据。** 同一节的 JSON Schema `default` 只有在陈述完全相同的字面值时才可以替换该注记。
- **手册未陈述的列**：`requirement: unstated` 与 `documentedOptional: null` 表示手册未说明该字段是否必填。**它们必须同时出现**：`null` 不是第三种可选性状态，也完全不说明省略该字段是否可行。同样，`type: unstated` 记录一个缺失的 Value Type 单元格，而不是猜成 `string`。同一节的 JSON Schema 仍可提供这两个事实，但**仅当手册在那里显式给出**；否则这种缺失就是契约的一部分。
- **风险与缓解是两条独立的轴**：`risk` 描述端点，`mitigation` 描述 SDK 对它做了什么。`/db/NMAS` 的 POST 保持 `risk: product_crash_risk` 且 `mitigation: normalized`：服务器缺陷是真实的、存在于已发布的 build 上，而 SDK 规则让那个会崩溃的载荷不可达。**因为已被缓解就下调风险，会抹掉规则存在的理由，下一个读契约的人就会把规则当仪式删掉。** 缓解措施按对调用者的代价大致排序：

  | `mitigation` | Meaning |
  | --- | --- |
  | `normalized` | SDK 静默修正载荷。调用者无需知道任何事 |
  | `confirmation_required` | 没有显式确认标志就拒绝该调用 |
  | `opt_in_required` | 除非调用者选择进入一个已知危险，否则拒绝该调用 |
  | `warn_only` | 大声记录文档；不改变行为 |
  | `none` | 什么都不做 |

  **在正确载荷可知的地方优先用 `normalized`。** 要求调用者选择进入一个 SDK 本可以简单避开的危险，是更差的结果，而不是更安全的结果。

**其他应当照抄的约定**：
- **契约是语言中立的真源**；契约与任一 SDK 之间的不一致是 **SDK 缺陷**，永远不是编辑契约的理由。
- **安全规则属于契约，而不属于某一种语言。**（CLAUDE.md 的步骤 7 原文：只活在 `NodalMass.create()` 里的规则只能到达 Python 的用户——npm 包就是这样发布了一个月、能崩溃一个活动 NX 会话的版本。）
- 一处 `surface` 的取值自 2026-09-02 起播种自生成器自己已提交的输出，所以两个已发布 API 在这次变更前后逐字节相同；**这些是公开 API 锚点，改一个是破坏性变更——现在是一个你必须有意做出的破坏性变更。**
- 305 个 npm 资源中有 **302** 个带 `surface`；**没有**契约 surface 的 3 个继续从 Python 取名（即 IEHG 三件套，它没有许可来源，因此**永远无法被契约化**）。`payloadTypeName` 单独可选：`/db/DRLS` 类型为 `JsonObject` 且没有自己的载荷类型，**在那里没有名字是一个事实，不是缺口**。
- **生成器拒绝不一致**，与其他每条契约事实一样。
- **契约可以拥有嵌套类型**（`surface.nestedTypes`）：`path` 是 `fields` 内的字段（数组的条目命名其元素类型）；`name` 与 `namespace` 是包**已经发布**的名字——命名空间是公开名字的一部分，因为每个命名空间都在包根被重新导出。生成器随后从契约子树构建该类型，包含挂在那里的变体联合。它**拒绝三件事而不是猜测**：多个契约声明为不同形状（撇开描述）的名字；形状被**上层**变体重申的路径（`/db/SECT` 的每个 `SECTTYPE` 分支都重申 `SECT_BEFORE`，不存在单一子树）；以及（2026-09-22 之前的）包尚未发布的某个名字。三处扩展在不放松任何一条的前提下拓宽了可声明范围：只由一个分支声明的对象；条目上的 `branch`（命名该路径属于哪个变体的版本，**必须与某个变体的 `when` 完全相等**）；嵌套类型内部的条件从其自身根陈述（成员顺序也不算差异）。**携带 `unmergedTables` 的契约不得声明任何 `nestedTypes`**：它的载荷不是从契约生成的，没有子树可构建。
- **函数端点的 surface 挂在操作上**：一个 `/db/*` 资源发布**一个** npm 导出、承载每个方法，所以它的名字属于端点；函数端点（`/doc/*`、`/ope/*`、`/view/*`、设计规范调用）**每个方法发布一个导出**，所以名字属于操作。`/ope/STORY_PARAM` 是逼出这个形状的案例：一个端点、两个导出、不同名字与不同参数——单一顶层 `surface` 说不出来。`argumentTypeName` 不带限定符，因为命名空间由 `modulePath` 推导（生成器从同一组模块部件构建两者，存下命名空间只会造出可能不一致的东西）；它在操作发布联合时取列表（两个 `/ope` 荷载组合调用如此）；`takesArgument: false` 标记一个调用者不传任何东西的 POST——SDK 发送契约 `request` 记录的空 `{"Argument": {}}`——它生成的 npm 操作种类与"参数只是未类型化"的那个不同，而这个区别在类型名里看不见，所以需要自己的字段。
- 结果表契约（`contracts/tables/*.yaml`）同样有 `surface`：`exportName`、`modulePath`、默认 `tableType`（对 `directional` 包装器是前缀）、`factory`（`fixed`｜`variable`｜`directional`）、`optionNames`、`documentation`。表**自己的请求字段**放在 `requestFields.additional`，条目可以嵌套（`properties`、`items`、`enum`、`appliesWhen`）。命名两个键的一行（`LCOMS[].NAME` / `LCOMS[].FACTOR`）**是两个字段**。共享请求对象 `UNIT` 与 `STYLES` 属于 `/post/TABLE` 本身：它的 POST 操作带一个含 `nestedTypes` 而**没有 `exportName`** 的 `surface`——这就是一个操作"命名类型但不发布生成的导出"的方式（npm 的 `post.getTable` 是手写的）。一处共享名没有搬家：`PostStoryTypes.StorySetAngle` 是四张 story 表的 `SET_ANGLE` 对象，手册让它的 `ANGLE` 在其中两张必填、两张可选；一个已发布类型无法同时满足两者，所以它留在 Python 上，每张表自己的 `ADDITIONAL` 类型内联它记载的那个版本。
- **`products: [civil, gen]` 说的是该路由在两者上都作答，从来不是说记录相同。** 178 个双产品端点中有 **12 个**声明了不同模式（2026-09-27 前是 10 个，那天 `/db/RPSC` 开始在 Civil 上单独声明 `CONTRIBUTION_FACTOR`；2026-10-11 前是 11 个，那天 Civil NX 有了自己的 `/db/POSP`），所以一个没有自己 `products` 的字段是对**两个**产品的主张，而这个主张有时是假的；要给它打标签（MD-46）。
- **`/info` 既不是服务器所接受内容的超集也不是子集。** 它在 Civil NX 上声明 `/db/POSL` 的 `CODE`，而实况连空字符串都拒绝（2026-09-21 重测，仍然带它 `Wrong Field`、不带它就被接受）；另一方向的 `/db/STBK` 的 `LCNAME` 比这条曾主张的更弱：调用在两个产品上都不报错地被接受，但读回的记录不携带该字段，所以确立的是服务器**容忍**它而非存储它。**`/info` 与一次实况往返不一致时，往返胜出。** 它是一份有自己的错误的模式文档——像手册一样，只是产生得离代码更近、正确率高得多。
- `infoOnly` 的用途**仅限**：`scripts/info_baseline.py --against-contracts` 的豁免。没有它，扫描会永远报同一个属性，下一个人就得重新调查。**只在"发布该属性会误导调用者"时使用它**——`/db/DRLS` 的 `DUMMY` 就是它存在的理由：一个占位符，服务器因为该记录被记载为空对象而声明它（JSON Schema 不能没有属性）。**一个真实但只读的属性是一个 `requirement` 为 `read_only` 或 `unstated` 的字段，不是这里的一个条目。**
- `sdkOnly` 的用途**仅限** `validate_contracts.py` 字段一致性检查的豁免。**只在"SDK 的名字不是服务器接受的名字"时使用它**——TypedDict 为了组织自己的文档而发明的一个分组键就是这种情形。**服务器确实接受的名字是缺失字段，修法是从手册、实况记录或 `/info` 取它。TypedDict 本身永远不是来源：它是该检查所测量的对象。**
- `extraction.unmergedTables` 的 `fieldNames` 使豁免**逐名化**：这里记录的名字是已声明缺口，既不在契约、也不在任何这些列表里的名字是缺陷。

### 4.5 `scripts/validate_contracts.py` 强制执行的校验规则

运行顺序（`main()` 中依次调用）：

1. **`check_schema`** —— 模式一致性（对照 `contracts/schema/endpoint-contract.schema.json`）。
2. **`check_cross_references`** —— 每一个 `riskRef` 与验证 `ref` 都能解析。
3. **`check_variant_discriminators`** —— 拒绝任何——**包括手写的**——变体把一个条件主张两次的契约。
4. **`check_safety`** —— `product_crash_risk` 操作必须携带 `mitigation`、一条规则（`sdkRule`）和一个风险引用（`riskRef`）；unsafe-to-omit 的可选字段（`documentedOptional: true` 且 `safeToOmit: false`）必须被某条规则覆盖；一条 `normalize_defaults` 的值必须等于该字段的文档默认值（**规则可以把默认值显式化，永远不能发明一个**）。
5. **`check_manual_source`** —— 手册来源相关校验。
6. **`check_tables`** —— 结果表契约（对照风险、验证记录、已知端点集合）。
7. **`check_parity`** —— 每份契约声明的 **endpoint、products、methods 与 normalization rules** 必须与**两个** SDK 相符；并执行可执行规则种类探针（Python 与 npm 各自的 rule-kind probe）。
8. **`check_field_parity`** —— 与上述四项并列的**第五项一致性检查**，因为前四项**从不比较字段名**。它把 `surface.payloadTypeName` 解析到**该端点资源所在模块**中同名的 Python TypedDict（名字本身不唯一——RC 与钢结构设计章各有一个 `SRDF` 和一个 `LENG`），跟随嵌套 TypedDict，并在**任何 SDK 发布而契约哪里都没记录的线上名**上失败。**只有一个方向**：契约比 TypedDict 命名更多是预期状态，反过来才是缺陷。`unmergedTables.fieldNames` 提供**逐名**豁免；`sdkOnly` 豁免服务器不接受的名字。

- `--no-parity` 跳过第 7、8 两项 SDK 一致性检查（README 把它描述为 "schema + refs only"）。
- 其他工作命令：`pip install -e ".[dev]"`（带入 pyyaml + jsonschema）、`pytest tests/test_contracts.py`。
- 输出会打印契约/操作/`product_crash_risk`/已知风险/验证记录计数，结果表计数与未解决的手册矛盾数，以及字段省略安全性分布（`proven safe` / `proven unsafe` / `unverified`），并明确说明 **`unverified` 是诚实的缺口、不是失败**。
- 添加契约的流程：`scripts/extract_contracts.py`（可解析的部分）→ `--emit /db/STLD`（起草一个端点，写入 `contracts/drafts/`，**git-ignored 且被校验器忽略**，每个草稿带 `draft: true`，而模式禁止该标记，所以一个没被读过就被移进 `contracts/endpoints/` 的文件会让 CI 用一条无歧义的消息失败，而不是作为事实通过）→ `scripts/promote_contract.py db-stld` → `extract_contracts.py --check`（提升版 vs 手册）。`promote_contract.py` **拒绝的多于它接受的**，且是故意的：它不会提升仍带审查注记的草稿、其章节有没人合并的条件变体表的草稿、手册从未陈述其方法的草稿、仍有一行命名多个线上属性的关键行的草稿，或是**文档载荷已被实况测得有误的八个端点之一**（把手册版本的 `/db/SECF` 键放进真源会比没有契约更糟）。用 `--all --dry-run` 取当前实测集合，不要依赖抄来的数字。

- 提升后的五步：① 自己读该端点在手册仓库里的章节（草稿是起点，不是审查；字段保持 `provenance: manual`）；② 查 `docs/live_verification_notes.md`，实况行为与手册矛盾时，契约记录实况行为、`manualDefects` 记录不一致、该字段 `provenance` 变为 `live_corrected`；③ 诚实设置 `verification.status`（**`manual_only` 意味着已转写但从未调用——它不是较低的状态，它是真实的那一个**）；④ 为任何调用者可能合理做出、却会破坏产品的行为添加 `sdkRules`；⑤ 从 `packages/typescript/` 跑 `npm run generate` 并跑 `python scripts/validate_contracts.py`——两个 SDK 都必须满足该契约，契约才能落地。

## 5. AI 编码上下文包要点（来自 context-pack.md）

原文定位：把对应语言的方框复制进 AI 编码助手（作为系统提示，或新会话的第一条消息）再让它写 `midas-nx` 代码。两个方框**只贴一个**（Python 版 `pip install midas-nx`；JavaScript/TypeScript 版 `npm install midas-nx`）。它是给 AI 读的、不是给人读的；用英文写是因为 AI 编码工具对英文的遵循最可靠。

### 5.1 API 请求/响应信封形状

- **客户端构造**：Python `from midas_nx import MidasClient, Product`；`MidasClient(mapi_key="...", product=Product.GEN)`（或 `Product.CIVIL`）。npm `import { MidasClient } from "midas-nx"`；`new MidasClient({ mapiKey: "...", product: "gen" })`（或 `"civil"`）。省略 `mapi_key`/`base_url`（npm 为 `mapiKey`/`baseUrl`）时，构造函数从环境变量 **`MIDAS_MAPI_KEY` / `MIDAS_BASE_URL`** 读取。浏览器中要显式传凭据，**绝不要把长期有效的 key 放进公开客户端代码**。npm 每个调用都是 async——要 `await`。
- **两种不同的 API 形状**：
  - `/db/*` 端点是资源类（如 `midas_nx.db.node_element.Node`、`midas_nx.db.properties.material.Material`、`midas_nx.db.properties.section.Section`）。每个都有 `.get(client=)`、`.items(client=)`、`.create(items: dict, client=)`、`.update(items: dict, client=)`、`.delete(ids: list, client=)`、`.delete_all(client=, confirm=True)`。
  - npm 侧挂在 `resources` 树上（如 `resources.db.nodeElement.node`、`resources.db.properties.material.material`、`resources.db.properties.section.section`、`resources.db.project.unit`），方法是 `.get(client)`、`.items(client)`、`.create(items, client)`、`.update(items, client)`、`.delete(ids, client)`、`.deleteAll({ confirm: true, client })`。
  - **写体如何包装 / id 如何键控记录（原文关键句）**：**`items` 是一个以记录 id 为键的对象：`{ 1: { X: 0, Y: 0, Z: 0 } }`。载荷内部的字段名是官方大写线上名（official uppercase wire names）。** 这就是 `/db/*` 的 ID 键控 `Assign` 映射在上下文包里的表述方式。
  - `/doc/*`、`/ope/*`、`/view/*` 端点是**普通函数**（Python：`midas_nx.doc.new_project`、`midas_nx.doc.save`、`midas_nx.doc.analyze`、`midas_nx.ope.get_project_status`、`midas_nx.view.capture`）。npm：`/doc/*` 端点是 `doc` 上的函数——`doc.newProject({ client })`、`doc.save({ client })`、`doc.analyze({ client })`、`doc.openProject(path, { client })`；`/ope/*`、`/view/*`、`/post/*` 与设计端点位于 `operations.ope`、`operations.view`、`operations.post`、`operations.design` 之下。
  - **结果表**位于 `tables` 下（如 `tables.result1.getReactionTable`）：它们接收**一个选项对象**，选项名为 **camelCase**，响应应当用 **`unwrapTable(raw)`** 读取，**而不是对顶层键做索引——那个键不稳定**。
- **`Assign` vs `Argument` 的显式表述不在本文件中**：context-pack.md 通篇没有出现 `Assign` 或 `Argument` 这两个词。它对"普通函数"的参数形状只以 `{ client }` / `{ confirm: true, client }` 这类选项对象呈现。这两个包装名及其区分（`/doc/*`-style 端点是被包在 `"Argument"` 里、而不是 ID 键控的 `"Assign"`）出现在 **`contracts/README.md`**（§4.3 的 `wrapper` 枚举与"函数端点的 surface 挂在操作上"一节）与 **`CLAUDE.md`**（`doc.py`/`ope.py`/`view.py` — `/doc/*`-style endpoints as plain functions, wrapped in `"Argument"`, not ID-keyed `"Assign"`）中。下游若需要 `Assign`/`Argument` 的精确语义，应以 `contracts/README.md` 与契约模式为准。
- 产品作用域注意事项（原文写在"Two different API shapes"一节里）：**Gen NX 与 Civil NX 对同一端点并不总是接受同一条记录。** TypedDict 字段的注释有时会说明它或其某个取值是 Gen NX only 或 Civil NX only——要读清楚：**对某个取值的注记（`"WALL"(Gen NX only)`）并不会使该字段变为可选**；只被一个产品声明的字段可能被另一个产品拒绝，所以在那边要**不要**发它，除非用户自己的模型显示该产品接受它。npm 版：文档注释以 `Gen NX only.` 或 `Civil NX only.` 结尾的成员只由该产品的模式声明、可能被另一个拒绝，在那边就别发；当它写 `Gen NX only; required there.`（或 Civil NX）时，它被类型化为可选**只是因为另一个产品不声明它**——面向那个产品时仍然要发。

### 5.2 错误模型

- **Python**：**一切都会抛出（Everything raises）；没有任何东西会静默返回错误字典。** 所有异常都继承 `MidasAPIError`（从 `midas_nx` 导入），共列出 **7 个**：`MidasAuthError`、`MidasNotFoundError`、`MidasConnectionError`、`MidasResultError`（**一个仍然携带 `{"error": ...}` 体的 HTTP 200——200 状态不是成功的证明**）、`MidasServerError`、`ProductMismatchError`、`DestructiveOperationError`（由 `delete_all()` 抛出，除非显式传入 `confirm=True`）。
- **JavaScript/TypeScript**：**一切都会 reject（Everything rejects）；没有任何东西会静默 resolve 成一个错误对象。** 所有错误都继承 `MidasAPIError`（从 `midas-nx` 导入），共列出 **9 个**：`MidasAuthError`、`MidasNotFoundError`、`MidasRequestError`、`MidasConnectionError`、`MidasResultError`（同样是"仍携带 `{"error": ...}` 体的 HTTP 200——200 状态不是成功的证明"）、`MidasServerError`、`ProductMismatchError`、`UnsupportedMethodError`、`DestructiveOperationError`（由 `deleteAll()` 抛出，除非显式传入 `confirm: true`）。
- 两处差异（下游须注意）：npm 的列表比 Python 多出 **`MidasRequestError`** 与 **`UnsupportedMethodError`**；`DestructiveOperationError` 在 Python 由 `delete_all()` 抛出、在 npm 由 `deleteAll()` 抛出。

### 5.3 它列出的危险（"Safety facts you must not get wrong"）

1. **`doc.new_project()` / `doc.open_project()`（npm `doc.newProject()` / `doc.openProject()`）会丢弃 MIDAS NX 中当前打开的**任何**文档里未保存的工作——甚至与你正在写的脚本无关的工作。**没有用户对**那一次具体运行**的明确同意，绝不要调用其中任何一个，也绝不要放在重试循环里。**
2. **`DbResource.delete_all()` / `.deleteAll()` 清空的是整张表，不只是选中的 id**——这正是它要求 `confirm=True`（npm `confirm: true`）的原因。删除指定记录请用 `.delete(ids)` / `.delete(ids, client)`。
3. **一个 200 HTTP 响应不表示请求成功。** `MidasResultError` 捕获常见情形，但某些端点（例如 `/doc/ANAL`、`/doc/SAVEAS`）可以在一个消息字符串里报告 "complete"，而工作实际上并没有发生。
4. **超时的请求不是回滚。** HTTP 调用放弃等待之后，操作仍可能在 MIDAS NX 侧完成。**超时后绝不要自动重试写操作**——告诉用户先核实模型状态。
5. **每个路径（`EXPORT_PATH`、`/doc/SAVEAS`、`/doc/OPEN`、报告/图像路径）都解析在运行 MIDAS NX 的那台机器上，而不是运行你脚本的那台机器上**——它们经常是不同的计算机。
6. **MAPI-Key 是机密。** 绝不打印、记录到日志、提交进仓库，也不要在你的输出里回显它。
7. （写在 Client 一节）**`client.verify_connection()` / `await client.verifyConnection()` 检查 key 与连接是否活着，但它不是每次调用的前置检查：一个阻塞 MIDAS NX 会话的模态对话框仍可以让每一个真实请求超时而它却报告 `"connected"`。**
8. （写在开篇）**不要因为一个函数、类或端点听起来合理、或你在训练数据里记得它，就假定它存在。** 先确认已安装版本（Python：`python -c "import midas_nx; print(midas_nx.__version__)"`；npm：`npm list midas-nx`），把你不能确定的一切当作未经验证。npm 包带完整 TypeScript 声明，**一个不能通过类型检查的名字就不是真实存在的**。

### 5.4 它规定的编码工作流（4 步）

1. **先写并运行任务的只读版本**（Python：只用 `.items()` / `.get()` / `verify_connection()`；npm：只用 `.items()` / `.get()` / `verifyConnection()`）。
2. 在调用任何 `create` / `update` / `delete` / `delete_all`（npm：`deleteAll`）/ `new_project`（`newProject`）/ `open_project`（`openProject`）/ `analyze` 之前，**精确打印它将瞄准和改变什么**——ids、payload、计数——作为预览。
3. **只有在用户确认预览之后**才运行写操作，最好先针对一个一次性测试项目。
4. **写后重读数据**以确认它真的落地了，而不是只信任 HTTP 响应（npm：不要只信任 resolve 的 promise）。
