## 逐条详情

### MD-01 — `/db/STYP-M1` DELETE

- **端点**: `/db/STYP-M1`，`DELETE`。
- **手册原文**: `02_DB_Project_Structure.md` 在**三处**声明该端点有 GET、PUT、DELETE。
- **实际行为**: 三种 DELETE 形式在两个产品上、从非默认状态且打开模型时**全部被拒**。原文强调这是"产品能力发现，不是请求包装推断"，要求把该端点已文档化的 GET/PUT 事实与已被否证的 DELETE 主张分开。
- **证据来源**: 两个产品上的 live 检查。
- **状态**: open。**列入 `Suggested follow-up` 第 3 条** —— 需升级给 MIDASIT 文档负责人（官方来源问题，手册仓库只能加注）。修正归属方为 **MIDASIT 文章**（`activeMethods`）。
- **对我们的影响**: 端点注册表不要暴露 DELETE；SDK 侧保持 `_GET_PUT_ONLY`。

### MD-02 — `/db/POLC-M1` POST

- **端点**: `/db/POLC-M1`，`POST`。
- **手册原文**: `14_DB_Pushover.md` 的 ⚠️ callout 称 POST **不被提供**，且该文章的表格行是"未裁剪的模板"。
- **实际行为**: live POST **创建了记录**，随后的 GET 把它取回。原文提出的修正不是发明 payload schema，而只是**停止声称 POST 不存在**。
- **证据来源**: live POST + 后续 GET。
- **状态**: open。**列入 `Suggested follow-up` 第 2 条** —— 由**手册仓库**自行修正（其自己的 callout）。原文明确：没有证据表明官方文章也这么说，所以这条是手册仓库自己的。
- **对我们的影响**: 不要把 POST 从该端点能力中删除；也不要为此编造请求体 schema。

### MD-11 — 被同节 JSON Schema 否证的 Value Type

- **端点**: 九行，跨 `/db/SBDO`、`/db/MATL`、`/ope/AUTOMESH`、`/db/RCHK`。
- **手册原文**: Specifications 表的 Value Type 单元格。
- **实际行为**: 同一节自己的 JSON Schema 把该属性类型写得**不同**。MD-08 ~ MD-10 都是"一种呈现比另一种少"，这九条不同：两种呈现对同一属性说了**不相容**的话，谁都不能被读成另一方的缩写。

  | 端点 | 路径 | 表说 | schema 说 |
  | --- | --- | --- | --- |
  | `/db/SBDO` | `AXIS_VECTOR` | Number | `array` of `number` |
  | `/db/MATL` | `PARAM` | Object | `array` |
  | `/ope/AUTOMESH` | `MESH_SIZE.LENGTH` | Number | `integer` |
  | `/ope/AUTOMESH` | `MESH_SIZE.DIV` | Number | `integer` |
  | `/db/RCHK` | `BEAM.vSUB_BAR.dSUB_BARNUM` | Integer | `number` |
  | `/db/RCHK` | `COLM.vLAYER.vPOSITION.BAR_NUM` | Number | `integer` |
  | `/db/RCHK` | `COLM.SUB_BAR.SUBBAR_NUM` | Integer | `number` |
  | `/db/RCHK` | `COLM.SUB_BAR.SUBBAR_NUM_Y` | Integer | `number` |
  | `/db/RCHK` | `COLM.SUB_BAR.SUBBAR_NUM_Z` | Integer | `number` |

  七条是数值宽度（两种读法都接受对方接受的值，调用者发的值不会因差异被拒）；**上面两条不是**：相信表格的调用者会发标量，而服务器要的是向量。

- **证据来源**: 表 vs 同节 JSON Schema；`/db/SBDO` 与 `/db/MATL` 已按此修正。
- **状态**: **`/db/SBDO` 与 `/db/MATL` 已在各自契约中修正；其余 7 条 open**。归属方：手册仓库转写。
- **对我们的影响**: `AXIS_VECTOR` 必须是数字数组（破坏性修正）；`PARAM` 是 array 而非 Object。

  1. **JSON 字符串里的撇号被反斜杠转义。** `/db/MATL-M1` 与 `/db/EPMT-M1` 上共八个 `description` 值：

     | 端点 | 路径 | 服务端返回的 `description` |
     | --- | --- | --- |
     | `/db/MATL-M1` | `PARAM[].USER_DEFINED.POISN` | `" Poisson\'s ratio"` |
     | `/db/MATL-M1` | `PARAM[].USER_DEFINED.POISN_M` | `" Poisson\'s ratio [xy,xz,yz]"` |
     | `/db/EPMT-M1` | `MASONRY.{BM,BED_JOINT,HEAD_JOINT}.YOUNG_S_MODULUS` | `" Young\'s Modulus"` |
     | `/db/EPMT-M1` | `MASONRY.{BM,BED_JOINT,HEAD_JOINT}.POSSIONS_S_RATIO` | `" Poisson\'s Ratio"` |

     `\'` 在 JavaScript 与 PHP 字符串字面量里合法，但**不是 JSON 转义**。严格解析器会拒绝它；宽容解析器会保留反斜杠，于是文本以 `Poisson\'s ratio` 到达读者。这些对象还把键拼成 `POSSIONS_S_RATIO` —— 那是服务器自己对 "Poisson's" 的拼错，无论如何都是 wire 名。
  2. **`maxItems` 挂在了错误的 schema 上。** `/db/MATL-M1` 上四个数组属性：
     ```json
     "ELAST_M": {"description": " Modulii of elasticity [X,Y,Z]", "type": "array",
                  "items": {"type": "number", "maxItems": 3}}
     ```
     `maxItems` 约束数组；这里它坐在描述每个元素的 `number` 子 schema 上，JSON Schema 会忽略它。意图无疑（三个分量，description 里写明了），但如所服务的那样该边界**什么都不约束**。`ELAST_M`、`THERMAL_M`、`SHEAR_M`、`POISN_M` 都有。

- **对我们的影响**: 不要照抄 `\'` 或 `maxItems` 的位置；三个 404 端点目前无法契约化。

### MD-15 — 一个 Required 值，两个端点，两种不同含义

- **端点**: `/db/SECT`（`SECTTYPE: "VALUE"`）与 `/db/SPFC`（KDS 41-17-00:2019）的 `CALC_OPT`。
- **手册原文**: `Create Only` 在整本手册里只出现在**两个** Required 单元格中，都属于名为 `CALC_OPT` 的字段：

  | 章节 | 端点 | 行 | Default |
  | --- | --- | --- | --- |
  | `04_DB_Properties.md:1148` | `/db/SECT`（`SECTTYPE: "VALUE"`） | Calculation Options | `true` |
  | `09_DB_Dynamic_Loads.md:131` | `/db/SPFC`（KDS 41-17-00:2019） | 계산 옵션 | `false` |

- **实际行为**: 2026-09-03 在 Gen NX 上测得：对第一行**成立**，对第二行**为假**。
  `/db/SECT` 完全吻合：同一个 POST 拒绝的 body（`CALC_OPT: false` 且没有 `SECT_I.STIFF` 可回退，答 `[Error] Section input data contain errors.`）作为 PUT 被接受，而一个改变 `vSIZE` 的 PUT **从不重算** `STIFF`，即使显式发 `CALC_OPT: true` 也不。

  ```text
  [Error] Spectrum Function Data (Name:KDS_2019_func) contains errors.(Item:Spectrum Data)
  ```
  设计谱函数要么需要 `CALC_OPT: true`（服务器据 `STR`/`OPT`/`VAL` 构建曲线），要么需要显式 `aFUNC`。文档化默认值 `false` 是正确的 —— **不能运行的是 worked example**，而这更严重，因为读者照抄的就是 worked example。

- **证据来源**: Gen NX 2026-09-03 live 测量（含上述错误串）。
- **状态**: open。归属方：**MIDASIT 文章**（一个值用于两份契约，以及一个无法运行的示例）。
- **对我们的影响**: 两个端点分别建模；不要泛化 `Create Only` 的语义；`/db/SPFC` 示例需补 `CALC_OPT` 或 `aFUNC`。

  这是 MD-16 的形状 —— 必填性陈述未参照管辖它的开关 —— 能调和二者的读法是其余四个只在 `OPT_USE` 为 true 时适用。**该读法未被记作事实**：没有人把任一种形式交给运行中的产品，所以契约把表格的主张保留在 `requirement` 里，并让这五个的每个 `safeToOmit` 留在 `unverified`。测量它也不是只读扫描能做到的：`/db/THGC-M1` 只提供 GET、PUT、DELETE 而无 POST，唯一能问的方式是一次 PUT 重写模型的全局求解器设置 —— 那属于针对已确认一次性文档的 write harness，而不是在旁边有开放工作时跑的扫描。该节的另外三张子参数表是干净的：`INCREMENT_STEP`、`ITER_PARAM`、`HINGE_OPT` 在契约审查时都并入了各自命名的对象字段，且该节自己的 request example 把每一个都嵌套在其父下放在单个 payload 里，所以它们都不是条件变体。
- **证据来源**: **无 live 证据**；只有同节 Python 示例与表格的自相矛盾。
- **状态**: open, unmeasured。归属方：手册仓库转写。
- **对我们的影响**: 保留表格的 `requirement`，`safeToOmit` 保持 `unverified`；不要照抄 Required。

### MD-20 — 一个陈述路径而非属性名的 Key 列

- **端点**: `/db/THGC-M1`，"ITER_PARAM 서브 파라미터" 表。
- **手册原文**: 该表命名十八行，其中两组无法从 Key 列所印内容寻址：

  | 该行印出 | 含义 |
  | --- | --- |
  | `` `DISP` → `{OPT_USE, VALUE}` ``（`FORCE`、`ENERGY` 同） | `NORM_CTRL.DISP` 是一个带两个成员的对象；该单元格命名的是**一条路径和一个集合**，不是属性 |
  | 五个行键为 `OPT_USE`、`LINE_SEARCH_OPT`、`START_ITER_NO`、`MAX_LINE_SEARCH_ITER`、`LINE_SEARCH_TOL`，仅在 설명 列前缀 "-" | 它们是 `LINE_SEARCH` 的子项，而 `LINE_SEARCH` 本身是同一张表的一行 |

- **实际行为**: 完全照写解析，该表会产生一个**字面名为 `{OPT_USE, VALUE}`** 的字段，并把十个子项放成两个拥有它们的父对象的兄弟。这不是微妙的不匹配 —— 得到的 payload 根本没有合法形状。该节在两段之后自行解决：其 Request Body 示例把它们全部嵌套：
  ```json
  "ITER_PARAM": {
    "NORM_CTRL": {
      "DISP":   {"OPT_USE": true, "VALUE": 0.001},
      "FORCE":  {"OPT_USE": true, "VALUE": 0.001},
      "ENERGY": {"OPT_USE": true, "VALUE": 0.001}
    },
    "LINE_SEARCH": {
      "OPT_USE": true, "LINE_SEARCH_OPT": 1, "START_ITER_NO": 3,
      "MAX_LINE_SEARCH_ITER": 4, "LINE_SEARCH_TOL": 0.5
    }
  }
  ```

  **已做的处理**：该节另外两张子表（`INCREMENT_STEP`、`HINGE_OPT`）完全没有这个问题 —— 每个标题都命名其目标对象且表是扁平的 —— 两者都加入了 `scripts/extract_contracts.py` 的 `_STRUCTURAL_TABLE_SPLITS`，现在无需判断即可合并。`ITER_PARAM` **有意排除**在该注册表之外，其子树在 `contracts/endpoints/db-thgc-m1.yaml` 中手工解决，因为对该表做机械合并会把**损坏的形状**而非已文档化的形状编码进去。
- **证据来源**: 同节 Request Body 示例。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 按示例嵌套；不要机械合并该表。

### MD-21 — 一节、五个多键单元格、一张键在 Key 列之外的表

- **端点**: `/db/STCT-M1`。
- **手册原文**: 这是目前发现的 MD-20 家族最密集的实例。它的六张补充表描述一条记录，其中五个 Key 单元格不命名单一 wire 属性：

  | 位置 | 该单元格印出 | 含义 |

  | 顶层行 5 | `` `"bSDLE"` / `"vSDLE"` ``（Value Type `Boolean / Array [String]`） | 两个根属性 |

### MD-23 — 一个单元格里两个键，判别符在上一行

- **端点**: `/db/THIS-M1`，`FREQ1`/`PERIOD1` 与 `FREQ2`/`PERIOD2`。
- **手册原文**: 该节 `COEF_INPUT=1` 分支的阻尼表：

  | No. | 설명 | Key | Value Type |
  | --- | --- | --- | --- |
  | 2 | 계산 기준 (0=Frequency, 1=Period) | `COEF_CALC` | Integer(enum) |
  | 3 | 모드1 주파수(COEF_CALC=0) / 주기(COEF_CALC=1) | `` `FREQ1`/`PERIOD1` `` | Number |

- **实际行为**: 与本家族其余条目不同，**答案就在问题正上方**：`COEF_CALC` 是同一张表的第 2 行，且第 3 行自己的 description 陈述了映射。契约声明四个字段，各自 `conditional` 于其行所命名的 `COEF_CALC` 取值。`FREQ2`/`PERIOD2` 的 description 不够仔细 —— "모드2 주파수(FREQ1≠FREQ2)" 是两个模态之间的约束，不是"哪个键适用"的陈述 —— 但第 3 行为两者确立了模式，且同一个 `COEF_CALC` 管辖。

### MD-24 — 有 조건부 却无条件的章节，而同章别处都写了条件

- **端点**: `/DESIGN/RC/KDS-41-20-2022/BRD-TABLE` 与 `/DESIGN/RC/KDS-41-20-2022/CD-TABLE`，`ELEMS` / `SECTIONS`。
- **手册原文**: 两节都在 필수 列把 `ELEMS` 与 `SECTIONS` 标为 조건부，却从不说条件是什么。`ELEMS` 在整个 BRD-TABLE 节里只出现两次：一次在 JSON Schema（把它列为属性，只 require `TABLE_TYPE`，任何地方都没有 `if`/`then`），一次在参数行。两个端点都没有能了结它的 Request Example。
- **实际行为**: 让这成为缺陷而非空白的，是**同一章知道怎么写这个条件**：`26_Design_RC_KDS41202022.md` 中有十五行把条件写在单元格本身：
  > `| (3) | 요소 번호 입력 (CREATE_SUB_SECTION=true 일 때 필수) | "ELEMS" | Object | — | 조건부 |`

  并在同节 JSON Schema 里用匹配的 `"then": { "required": ["ELEMS"] }` 支撑。两节用了同样的 조건부 标记却两者都没有。
  **两份契约都保持未 promote。** 本条目部分是为了阻止用改写把空白填上：설명 列写的是"요소 지정 — KEYS/TO/STRUCTURE_GROUP_NAME 중 하나"，描述的是 `ELEMS` **自身的内部形状**（该用它的三个子键中的哪一个），对"`ELEMS` 本身何时必需"只字未提。把它变成 `condition: 요소 지정 시` 会产生一句既循环又无来源的话，而 2026-09-04 对这两份契约的第一遍就正是这么做的，随后被抓住。诚实的状态是提取器已经报告的那个："手册把它标为条件但未陈述条件"，这是一条未解决的审查提示并阻断 promote —— 本该如此。
- **证据来源**: 同章十五处对照；两节自身无示例可定。
- **状态**: **部分被 MD-33 取代** —— 被拒的改写仍被拒，但条件在章内别处已陈述，两份契约现已 promote。归属方：手册仓库转写。
- **对我们的影响**: 不要用 설명 列改写条件（循环、无来源）；条件应从同章兄弟节取。

### MD-25 — 一个 Value Type 与两个 item 形状，同一节自己就了结了

- **端点**: `/db/MVLDeu`，`OPT_COMB`、`STL_LIST`、`SUB_LOAD_LIST`。
- **手册原文**: Specifications 表低估了三行，而每次同一节都在几行之后带着答案：

  | 行 | 表说 | 该节自己的 Request Body |
  | --- | --- | --- |
  | 12 `OPT_COMB` | `String`，描述为 "Loading Effect (Combined: `0` / Independent: `1`)" | `"OPT_COMB": 1` —— 不带引号，在两个设置它的示例里都是 |

### MD-26 — 兄弟章节记录了而本节没记录的两个成员

- **端点**: `/db/REBR`，`ID` 与 `ELEMS`。
- **手册原文**: 该节的 파라미터 表自称是整个 ITEMS item。它把六个成员编号 `(1)` 到 `(6)`，而直接印在它上方的该节 JSON Schema 声明了**八个**：

  | JSON Schema 属性 | 파라미터 行 |
  | --- | --- |
  | `CREATE_SUB_SECTION` | `(1)` |
  | `ID` | **无** |
  | `ELEMS` | **无** |
  | `MAIN_BAR` | `(2)`，带 `(2)a`/`(2)b`/`(2)c` |
  | `SHEAR_BAR_END` | `(3)` |
  | `SHEAR_BAR_CEN` | `(4)` |
  | `DO` | `(5)` |
  | `HOOP_TYPE` | `(6)` |

  该节并未把这两个留作未文档化：它的第三张表标题为 "**`CREATE_SUB_SECTION == true` 일 때 — `ELEMS` (KEYS / TO / STRUCTURE_GROUP_NAME 중 택1)**"，JSON Schema 也把同一条件作为 `ELEMS` 自己的 description。该表**没有说**的是它的四行属于**两个不同层级**：

  | No. | Key | 实际归属 |
  | --- | --- | --- |
  | `(1)` | `"ID"` | ITEMS item，与 `CREATE_SUB_SECTION` 并列 |
  | a | `"KEYS"` | 在 `ELEMS` 内 |
  | b | `"TO"` | 在 `ELEMS` 内 |
  | c | `"STRUCTURE_GROUP_NAME"` | 在 `ELEMS` 内 |

  `(1)` 与 a/b/c 的编号差别是唯一区分它们的东西，且没有任何行命名 `ELEMS` 本身。按解析结果合并，`KEYS`/`TO`/`STRUCTURE_GROUP_NAME` 会坐在 item 级 `ID` 旁边，而 `ELEMS` 根本不存在。
- **实际行为**: **chapter 26 正确记录了同样的形状**：`/DESIGN/RC/KDS-41-20-2022/REBC` 与 `.../REBR` 在其 Parameters 表里把 `ID` 与 `ELEMS` 给成普通编号行，`ELEMS` 的条件写在它自己的 description 单元格里。所以这是 chapter 24 漏掉了它兄弟章对近乎相同 payload 的陈述，不是 MIDASIT 知识上的空白。与 MD-22 同形：一个表没有行的成员，由同一节内的第二条陈述补上。**两个 SDK 都不受影响**（两者都已发送 `ELEMS`），所以这只是文档缺陷。

- **证据来源**: 同节 JSON Schema + chapter 26 对照。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: `ID` 在 item 级；`KEYS`/`TO`/`STRUCTURE_GROUP_NAME` 在 `ELEMS` 内；`(2)a` 是路径段。

### MD-27 — 一张表与它自己的 schema，在五个字段上双向不一致

- **端点**: `/db/RCHK`，五个计数字段。
- **手册原文**: 该节把请求陈述了两次，两种呈现对每个数钢筋的字段在 integer 与 number 上都不一致：

  | 字段 | 파라미터 表 | JSON Schema |
  | --- | --- | --- |
  | `BEAM.vSUB_BAR.dSUB_BARNUM` | Integer | `number` |
  | `COLM.SUB_BAR.SUBBAR_NUM` | Integer | `number` |
  | `COLM.SUB_BAR.SUBBAR_NUM_Y` | Integer | `number` |
  | `COLM.SUB_BAR.SUBBAR_NUM_Z` | Integer | `number` |
  | `COLM.vLAYER.vPOSITION.BAR_NUM` | Number | `integer` |

- **实际行为**: 最后一行方向相反，而它正是该节能了结的那个。同一个键、同一个 description（철근 개수）也出现在 `POS_TOP_LAYERS` / `POS_BOT_LAYERS` 的 보 철근 레이어 表中，那里表格类型为 **Integer** 而 schema 类型为 `integer`。所以三条陈述说 integer、一条说 number，契约记 `integer`。其余四个没有第三条陈述：该节的 POST/PUT Request Body 发 `"SUBBAR_NUM": 12` 与 `"dSUB_BARNUM": 2` —— 整数，两种读法都满足，所以示例无法打破平局。契约保留表格的 `Integer` 作为**两种已文档化类型中较窄的那个**：它接受的值都是 schema 读法也接受的，所以遵循契约的调用者不会被引到一个另一种呈现会拒绝的请求里；反过来选则没有这种保证。
  值得明说：**没有任何已发布界面能区分这两者**。TypeScript 只有单一 `number` 类型，且这五个都不是 Python TypedDict 成员 —— 它们住在 `RebarCheckPayload` 的嵌套对象里，由该契约生成。所以本条目记录的是一处文档矛盾与解决它的推理，不改变调用者能看到的任何东西。只有一次发送小数计数的 live POST 才能把它变成事实，而没有人做过。匈牙利前缀在此不构成任何证据，也未被当作证据：`dSUB_BARNUM` 带 `d`（double）前缀却被表格类型为 Integer，`SUBBAR_NUM` 不带前缀却被同样类型。
- **证据来源**: 同节双渲染对照（示例发整数无法定案）。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 契约取较窄类型（integer）；已发布接口不受影响。

### MD-28 — 两个互斥的 Required 字段，以及一个指向别处而非列出成员的行

- **端点**: `/ope/AUTOMESH`，`MESH_SIZE` 与 `INCLUDE_INTERIOR_LINES`。
- **手册原文**: 本节汇集三处独立发现。
  **一个互斥对的两半都被标为 Required**：

  | No. | 설명 | Key | 필수 |
  | --- | --- | --- | --- |
  | 2-1 | 길이 기준 (`DIV`와 동시 사용 불가) | `MESH_SIZE.LENGTH` | **Required** |
  | 2-2 | 분할수 기준 (`LENGTH`와 동시 사용 불가) | `MESH_SIZE.DIV` | **Required** |

  没有任何 payload 能同时满足两个单元格，而该节自己的两个 Request Body 就证明了：一个发 `"MESH_SIZE": { "LENGTH": 1 }`，另一个发 `"MESH_SIZE": { "DIV": 3 }`。
- **实际行为**: 每个都记作 `conditional`，携带其所在行的措辞作为条件，且**没有 `appliesWhen`** —— 手册没有命名任何判别字段，因为该发哪一个是一个建模选择，不是 payload 声明的分支。`documentedOptional` 保持 `false`：手册确实说了 Required，那个标志记录的是**文档**。
  **同样这两个字段还被两种方式类型化，且不按同一方向解决。** 表对两者都说 Number，JSON Schema 对两者都说 `integer`。
  - `DIV` 是 분할수，一个划分数。保留 `integer` —— 两种已文档化类型中较窄的那个，且 Request Example 的 `3` 满足任一读法，所以收窄没有代价。
  - `LENGTH` 是模型长度单位下的网格尺寸。这里较窄的读法会排除该行自己 description 承认的值，且没有第三条陈述支持它，所以保留表格的 `Number`。

  这就是 MD-27 的规则**不再是机械的**之处：那里五个争议字段都是计数且五个都同一方向。规则不是"偏好较窄类型"，而是"**当收窄无法排除该字段自己 description 承认的值时**偏好较窄类型"。长度不通过该测试，计数通过。
  **一个指向另一行而非列出其成员的行。** 行 1-6 声明 `MESHER.INCLUDE_INTERIOR_LINES` 并在本该放成员行的位置写 구조는 1-5와 동일。于是该表比请求实际拥有的字段少命名了三个：`OPT_CHECK`、`OPTION`、`VALUE`。JSON Schema 在 `INCLUDE_INTERIOR_LINES` 下声明了完全相同的一组三个，第二个 Request Body 发 `{ "OPT_CHECK": true, "OPTION": "User", "VALUE": [2] }`。它们被**转写而非略去**，因为只从表格构建的 payload 类型会拒绝手册自己印出的调用。`VALUE` 的条件植根于**本**对象的 `OPTION`，而不是兄弟对象的 —— 两个对象形状相同，不是共享实例。与 MD-22、MD-26 同族。
  > **提取器在这里学到的东西**：行 1-5-a 到 1-5-c 与 3-2-a/3-2-b 写的是相对于对象而非请求根的路径（`INCLUDE_INTERIOR_NODES.OPT_CHECK`，不是 `MESHER.INCLUDE_INTERIOR_NODES.OPT_CHECK`），所以提取器为每一个建了第二个根级容器，并报告两者都"没有自己的行"。两者现已在 `_STRUCTURAL_ROOT_MOVES` 中，与 `/ope/GUSTFACTOR` 并列（后者以同样方式缩短路径）。
- **证据来源**: 同节两个 Request Body + JSON Schema。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 二者记 conditional 且无 `appliesWhen`；`DIV` 取 integer、`LENGTH` 保留 Number；补 `OPT_CHECK`/`OPTION`/`VALUE`。

### MD-30 — 正确的数字写在错误的关键字下

- **端点**: `/DESIGN/RC/KDS-41-20-2022/REBR`，`MAIN_BAR.NUM`。
- **手册原文**: 该节 JSON Schema：
  ```json
  "NUM": { "type": "integer", "description": "철근 총 개수", "minItems": 4 }
  ```
- **实际行为**: `minItems` 约束数组长度。用在 integer 上它是**惰性的** —— JSON Schema 校验器会忽略它，所以如所写的 schema 完全不设边界。边界是多少毫无疑问：该节对同一字段的 Parameters 行写 철근 총 개수 (min 4)，chapter 24 的兄弟 `/db/REBR` 在其行里写 개수 (min 4) 并在其 schema 的 `description` 里重复。两份契约现在都带 `minimum: 4`，那是三条陈述共同的意思。很小，但值得记录的理由只有一个：**机器读这些 schema 得不到边界，人读能得到正确的那个**。
- **证据来源**: 同节 Parameters 行 + chapter 24 兄弟 `/db/REBR` 对照。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 转写为 `minimum: 4`，不要照抄 `minItems`。

### MD-32 — 一个 404 的已文档化 URL，背后是一条会杀死会话的路由

- **端点**: `/DESIGN/SRC/AIK-SRC2K/OCHECK`，路由本身。
- **手册原文**: chapter 27 的 section 21 像记录其他一切那样记录 `OCHECK`：一个 Input URI、Active Methods、JSON Schema、Parameters 表、worked example。**没有任何东西把它标为不同。**
- **实际行为**: 两件事错，而且叠加。
  **URL 不应答。** MIDASIT 于 2026-08-06 把路由移到 `/TEMP/DESIGN/SRC/AIK-SRC2K/OCHECK`，文档化的路径现在干净 404。`/TEMP/` 前缀是状态标记：它说明这是非官方 API 且开发已暂停。照手册走的读者得到一个 404，没有任何提示说该端点存在于别处，或说它存在于别处本身就是警告。

  | 日期 | 产品 / build | 结果 |
  | --- | --- | --- |
  | 2026-07-31 | Civil NX，旧路径，真实生产桥梁模型 | 会话死亡 |
  | 2026-08-07 | Gen NX v2.1，`/TEMP/` 路径 | 完全相同的崩溃 |
  | 2026-08-13 | Civil NX v2.2 build 08/12/2026，专门构造的 dummy 模型 | 完全相同的崩溃 |
  | 2026-08-24 | Civil NX v2.2 build 08/24/2026，同一 dummy 模型 | 完全相同的崩溃 |

  路径迁移**不是修复**，崩溃**不依赖 build**。

- **证据来源**: 四次 live 复现（2026-07-31 / 08-07 / 08-13 / 08-24）+ 无截面文档对照。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 记录产品实际路由并标 `contradicted`，加 warn 规则；不要调用该端点。

### MD-33 — 两节丢掉了它们七个兄弟都陈述的东西

  | --- | --- | --- |

- **证据来源**: chapter 26 七节对照（行 + schema `oneOf`）。
- **状态**: open（并更正 MD-24 的结论；两份契约现已 promote）。归属方：手册仓库转写。
- **对我们的影响**: 记为 conditional，条件 `ELEMS/SECTIONS 중 하나`，无 `appliesWhen`。

### MD-34 — 这个家族里第三节把端点描述错的章节

- **端点**: `/db/REBR`，整个 item 形状。
- **手册原文**: chapter 24 描述 `/db/REBR` 的方式与描述 `/db/REBC` 一样 —— 每个 `ITEMS` 条目有单个 `MAIN_BAR` 对象、一个顶层 `DO`、一个默认 `"Ties"` 的字符串 `HOOP_TYPE`，以及一个带 `ELEMS` 的可选 `CREATE_SUB_SECTION`。
- **实际行为**: 服务器对两者的处理方式相同，而那**不是**章节描述的方式：

  | 章节 | `GET /info/db/REBR` |
  | --- | --- |
  | `MAIN_BAR`，一个 `{NAME, NUM, ROW}` 对象 | `vMAIN_BAR`，一个**数组** |
  | item 上的 `DO`，一个 Number | 每个数组条目内的 `D0` —— 一个**零**，不是字母 O |
  | `HOOP_TYPE`，字符串 `"Ties"` / `"Spirals"`，默认 `"Ties"` | `HOOP_TYPE`，**integer**，`1=Tied, 2=Spiral` |
  | `CREATE_SUB_SECTION` 与 `ELEMS` | 两者都不存在 |

  `/db/REBW` 是本章第一个被发现对自己字段名说错的端点（2026-07-29），`/db/REBC` 是第二个（2026-08-27）。这是第三个，也是三者中最容易确立的：`/db/REBC` 的结论是靠把两种候选形状 POST 到同一个 live 会话定下的 —— 文档化形式答 `Wrong Field`，数组形式答一个命名缺失目标截面的**领域**错误 —— 而本节对兄弟端点提出了**每一个**同样的主张。
  **尚未做的**：没有对 `/db/REBR` 本身跑过 POST 对比。该契约依托 `/info` schema 加 `/db/REBC` 先例，并且**明说了这一点**。是 `/db/REBC` 的 round trip 确立了**后果**（拒绝，而非静默错误行为），而该后果在这里是**被假定而非被测**的。
  **chapter 26 的兄弟不受影响，且这是有意的**：`/DESIGN/RC/KDS-41-20-2022/REBR` 是不同 URL，其节内部一致 —— JSON Schema、Parameters 表、Request 与 Response body、Python 示例在 `MAIN_BAR`、顶层 `DO`、字符串 `HOOP_TYPE` 上全部一致。`/info` 不服务 `/DESIGN/*`，所以没有许可来源与之矛盾，而兄弟端点的形状也不是许可来源。它的契约保持不动。`REBC` 已存在同样的分裂：它的两章对两个不同 URL 描述同名数据的方式不同，而只有 `/db/*` 那个有 live 证据。
  > **这是怎么发现的，以及为什么它比发现本身更重要**：该契约当天早些时候从手册写出、promote、并审查了它生成的 npm diff —— 那个审查本该正好抓住这个。它没有，也不可能：手册的形状生成一个**完全连贯**的 TypeScript 类型。抓住它的是把 2026-09-03 的 `/info` 捕获对每份契约做扫描，问哪些声明属性没有任何契约记录。`/db/REBR` 报了两个，`ITEMS.vMAIN_BAR` 与 `ITEMS.vMAIN_BAR.D0`，那正是从那个角度看一个错误形状的样子。

- **证据来源**: `/info/db/REBR` + `/db/REBC` 先例（REBC 由 live POST 对比定案）；**REBR 本身无 POST 对比**。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 按 `/info` 形状建模；这是 `/db/REBW`、`/db/REBC` 之后第三个同类端点。

### MD-36 — 手册里最显式的嵌套形式，也是唯一没人读的形式

- **端点**: `/db/LCOM-*` 与 `/db/POGD`，成员行。
- **手册原文**: 两章通过**直接命名其父**并把 No. 列留成破折号来标记数组成员：

### MD-37 — `/db/POGD-M1` `ANALYSIS_STOP`，四项主张

- **端点**: `/db/POGD-M1`，`ANALYSIS_STOP`。
- **手册原文**: `AXIAL_YIELD.BEAM`、`SUPPORT_DZ_DIR.UPLIFT`、两个 stop group 中的 `WALL`，以及 `PO_HINGE_OPT.BILINEAR`/`.TRILINEAR` 中标为 Required 的 `SYMMETRIC`。

### MD-43 — `/db/SLANch`，整个记录

- **端点**: `/db/SLANch`。
- **手册原文**: section 8 唯一的 Parameters 表标题为 "Parameters - LANE_ITEMS"，给三行：`NODE`、`OFFSET`、`SPAN_LENGTH`。
- **实际行为**: 这三行是 `LANE_ITEMS` **数组的成员**。记录自己的**八个字段**只出现在 Request Example 与 Python 示例里，**任何地方都没有 Specifications 行**，而 `/info` 还声明**第九个**，`SEQ`。前一个 section 的兄弟 `/db/SLAN` 把全部九个都正确列表了。
  这是本批最糟、也最清楚地陈述问题的一个：其契约的整个字段列表就是 `NODE`、`OFFSET`、`SPAN_LENGTH` —— `LANE_ITEMS` 数组的三个成员，被发布在根上，仿佛它们就是那条记录。因此 npm 上的 `TrafficSurfaceLanesChinaPayload` **没有命名该记录实际持有的任何东西**，而 Python 里的 `TrafficSurfaceLanesChinaPayload` 拥有全部八个已文档化字段加那个数组。**同一个包名、同一个版本号、两个 registry，其中一个描述的是另一个端点。**
  原因是**一个提取器盲点有五种面孔**（MD-43 ~ MD-45 合计六个端点）：这些节**都**陈述了其成员；**没有一节**把它们陈述为解析器所读的那张表里的编号行：

  | 端点 | 成员在哪里 | 发布出去的是什么 |
  | --- | --- | --- |
  | `/db/SLANch` | 一张为数组而设的子表，被误认为主表 | 三个数组成员当作整个 payload |
  | `/db/SLAN` | 第二张表，其行是设计码 | `Array<JsonObject>` |
  | `/db/POLC` | 第二张表，其行是 `LOADPATTERNTYPE` 取值 | `Array<JsonObject>` |
  | `/db/ACTL-M1` | 一个子表标题一次命名三个子项 | 两个字段高了一层 |
  | `/db/NLNK`、`-M1` | 一句话，以 "(NLNK와 동일)" 结尾 | `Array<JsonObject>` |

  其中两个现在可以表达了。`extraction.prose` 接过那句话 —— MD-42 需要的同一机制。`/db/POLC` 的分支表变成了 `LOADPATTERNTYPE` 上真实的 `appliesWhen`，因为那个值是同一记录的字段。`/db/SLAN` 的不能：它的行是设计码，而码是**模型级设置而非本 payload 的属性**，所以手册没有命名 wire 判别符，契约只能用文字记录该条件而无结构化门。**"兄弟字段上的条件"与"世界上的条件"这个区分，是值得保持清楚的。**
  **一个生成器缺陷从修复中掉出来**：给 `/db/NLNK` 的 `POINT_VALUES` 加上其 `{VALUE}` 成员后，`[JsonObject, JsonObject, JsonObject]` 变成了普通的 `Array<...>` —— 保留恰好有界数组的 tuple 规则只存在于标量数组的路径上，所以一个数组在**同一次改动中既获得了**被描述的 item 类型**又丢失了**它已文档化的长度。两条路径现在都走同一个 helper。这是本批第二次"让一个类型更精确"这件事本身暴露了别处的不精确。
- **证据来源**: 同节示例 + `/info` + `/db/SLAN` 对照。
- **状态**: open。归属方：手册仓库转写（注：MD-43 ~ MD-45 批次发现**八个端点中有六个**在 `src/midas_nx/` 里早已正确，**只在 `contracts/` 里错** —— 而 npm 从契约生成、PyPI 不生成，所以 npm 发布了损害，PyPI 没有）。
- **对我们的影响**: 不要把数组成员当成整个 payload；子表标题命名的目标必须作为嵌套层级处理。

- **状态**: open。归属方：手册仓库转写。

### MD-46 — `products: [civil, gen]` 从来不是关于记录的主张

- **端点**: 十个 `/db/*` 节，73 个字段。
- **手册原文**: 每节用一张 Specifications 表记录一个端点，**对两个产品只字不提**。
- **实际行为**: 两个产品声明的**记录不同**。`/db/SPLC` 差 15 个字段、`/db/POSL` 差 11、`/db/POGD` 差 20、`/db/SBDO` 差 16、`/db/IEHC` 差 9，`/db/ACTL`、`/db/BCCT`、`/db/EPSE`、`/db/POLC`、`/db/THGC` 各差一到四个。多数是产品自身的特性集 —— Gen NX 有墙与纤维铰，Civil NX 有桥梁抗震参数 —— **不是转写失误**。
  契约的 `products` 列表说的是哪些产品应答该路由。它一直被生成器与所有下游读成**仿佛它也说两个产品的记录相同**。对十个端点而言并非如此。`scripts/info_baseline.py --divergence` 对全部 **177** 个在两产品上都应答 `/info` 的配对提问：**十个不同**。`docs/live_verification_notes.md` 在 2026-09-03 得出结论说 `/db/POGD` 是"扫描中唯一两个 schema 不同的配对"、其他每个双产品端点返回逐字节相同的 schema —— 那对那次扫描覆盖的九个端点成立，而这正是那句话值得重新审视而非信任的原因：**十个中有九个对它是不可见的**。那里已经写下了处方："`/db/POGD` 的契约必须按产品标记那些成员；单一形状会在其中一个上出错。" 这就是本条目所做的，对全部十个：**45 个字段获得 `products` 标签，8 个此前完全没被任何契约记录的字段带标签加入。**

### MD-47 — `/db/TDMT` `TCODE` 与 `bSILICA`（以及发现它的那个检查）

- **端点**: `/db/TDMT`，`TCODE` 与 `bSILICA`。
- **手册原文**: section 6 的 "Specifications (공통 키 + CEB-FIP)" 表记录两个码分支，CEB-FIP 与 ACI，而其 `CODE` 值表列出 **33** 个码。
- **实际行为**: `CODE="EUROPEAN"` 是**第三个分支**，带两个该表从未命名的专用字段。两者都是 2026-07-30 从一个真实 PSC 桥梁模型的 C40/50 混凝土上读出的，且 `GET /info/db/TDMT` 在两个产品上都声明它们。**缺口比这两个更宽**：`/info` 在此声明约**七十**个字段，横跨值表列出了而字段表随后忽略的多个码。
  **发现它的检查**：MD-43 ~ MD-45 都以同样方式开始 —— 一份契约发布的字段比两个目录之外的 Python TypedDict 少，而每个自动门都是绿的。那不是运气不好：`validate_contracts.py` 的 parity 检查比较端点的路由、动词、`products` 列表与可执行安全规则，**从未比较过字段名**。`/db/ELNK` 就在这个洞上把四个字段与一个十二键 TypedDict 并排发布了数月。
  `check_field_parity` 补上了这个洞：它把每份契约的 `surface.payloadTypeName` 解析到**该端点资源所在模块中**同名的 Python TypedDict（名字本身不唯一 —— RC 与钢设计章都有 `SRDF` 和 `LENG` 且 payload 不同），沿注解跟踪嵌套 TypedDict，并在 SDK 发布了契约任何地方都没记录的 wire 名时失败。**它只强制一个方向**：契约命名多于 TypedDict 是**预期状态**（TypedDict 是文档，npm 从契约生成 payload 类型，契约本应领先）。
  它第一次运行就发现**十二个端点上 73 个键**。四个归结为上述名字冲突，是假阳性。其余都是真的，分成三类：
  **一个错误形状，四次。** `/db/LLAN`、`/db/LLANch`、`/db/LLANid` 发布了扁平记录。服务器接受 `{COMMON: {...}, LANE_ITEMS: [...]}` 且**一直如此** —— 手册的 Request Example、Python 示例、`scripts/live_crud_check.py` 的已确认 round trip 与 `GET /info` 全都一致，第二张表的标题也直说了。契约自己的 `extraction.table` 自 draft 起就记录着 `Parameters – COMMON`。promote 把一个**命名目的地**的标题读成了命名记录。`/db/LLANop` 在根上确实是扁平的，且有一个空的 `LANE_ITEMS`。
  **一个第二后果，也是这类错误昂贵的原因。** `/db/LLAN` 的十个 common 字段全部带 `safeToOmit: true`，并附一句命名已确认 live payload 的省略证据。那个 payload 发送其中九个。该主张来自把 payload 的顶层键与一个**扁平**的字段列表比较，而 payload 不是扁平的，于是 `COMMON` 的每个成员都被读成缺失。**一个错误形状不会停留在形状问题上；它会在安全规则所读的那条轴上制造假主张。**
  **一个空对象，五次。** `/db/MVLDbs` 的六个 `LCDATA_*` 对象与设计端点 `/DESIGN/RC/KDS-41-20-2022/REBW` 的六个**完全没有成员**。两节都陈述了它们 —— MVLDbs 用第二张表以 `SUBLOADDATA[].FIELD` 路径记法和一张 주요 필드 汇总表，REBW 用它自己的 JSON Schema 与一张 하위 객체 필드 요약 表 —— 而解析器只读编号行。
  **一个缺失分支，一次。** `/db/TDMT` 的 `CODE="EUROPEAN"`，即上文登记的那条。
  **以及一个 SDK 缺陷，那正是该检查名义上的目标。** `/db/HHCT-M1` 的 `ITEM` 有一个该端点没有的 `M_GENERAL`。Python 在 `/db/HHCT` 与 `/db/HHCT-M1` 之间共享一个 item TypedDict；手册只在 `/db/HHCT` 的表里记录 `M_GENERAL`，而 `GET /info/db/HHCT-M1` 只声明 `TYPE`、`CREEP_CALC_METHOD` 与 `M_EFF_MOD`。两个来源都反对 SDK，所以**变的是 SDK** —— 十二个中唯一一个契约是对的情形。
  **drift checker 不得不学的东西**：把 LLAN 字段放回标题所说的地方后，`scripts/extract_contracts.py --check` 报告**每一个**成员都是凭空发明的：它把每节的表压平成一个命名空间，于是它在正确契约持有 `COMMON.LL_NAME` 的地方持有 `LL_NAME`。把这些当字符串比较会**通过错误形状而失败于正确形状**。`extraction.structuralTables` 早已存在，用来记录一张表的标题命名了其目的地；drift 检查只是从未咨询它。现在它在两个方向上都咨询，且只对手册表格实际陈述的叶子 —— 所以手册从未提及的成员仍会被报告。
- **证据来源**: 2026-07-30 真实生产 PSC 桥梁模型（C40/50 混凝土）+ `/info` 双产品；`check_field_parity` 首次运行。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 按 `CODE` 分支建模；不要以为值表列出的每个码都有对应的字段文档；字段名 parity 检查必须存在。

### MD-48 — `/db/MVHL` `VEH_EUROCODE`（以及第二个盲点）

- **端点**: `/db/MVHL`，`VEH_EUROCODE`，48 个字段。
- **手册原文**: section 10 的 Specifications 表记录 `VEH_DEFAULT`，**完全没有 country 对象**。
- **实际行为**: `GET /info/db/MVHL` 多声明**十一个** —— `VEH_FR`、`VEH_CN`、`VEH_IN`、`VEH_CA`、`VEH_BS`、`VEH_EUROCODE`、`VEH_RU`、`VEH_KSCE_LSD15`、`VEH_AU`、`VEH_PL`、`VEH_ZA` —— 且 2026-07-30 读到的真实 Eurocode "Load Model 1" 车辆用的是 `VEH_EUROCODE` 而非 `VEH_DEFAULT`，并省略了该表标为 Required 的 `STANDARD_CODE`。十一个中有四个有自己的手册表；**`VEH_EUROCODE` 没有**。
  **第二个盲点**：MD-47 关上了"没有门比较字段名"的洞，同时却留下第二个洞：`check_field_parity` **跳过任何带 `extraction.unmergedTables` 条目的契约**，理由是这种契约已经承认其字段列表不完整。**二十份契约**带一个。这个跳过值 **214 个 wire 名**是 SDK 发布了而没有任何门看过的 —— 是该检查刚发现的 73 个的三倍，藏在一个**真实但过于宽泛**的承认后面。
  **修复是逐项化，不是更宽的网。** 一个 `unmergedTables` 条目现在记录 `fieldNames`：其表持有的 wire 名，按表序。`fields` 一直只给计数，而计数恰恰不能用作豁免 —— 它说存在空白却不说空白里有什么。名字写下来后豁免就是**按名**的：表能说明的名字是已声明空白，契约与那些列表里都没有的名字才是检查报告的缺陷。`scripts/extract_contracts.py` 为新 draft 输出该列表，`--check` 验证它仍与表一致，所以一次新增行的章节编辑不能静默扩大豁免。
  这使盲点从 214 个名字降到 **84 个，而这 84 个全是真的**：
  * **`/db/THIS-M1` 发布了一个服务器不接受的形状。** 手册标题在一行里命名两个对象及其各自条件 —— `증분 제어 (ANAL_METHOD=2 Static 전용, INC_CTRL)`、`시간 적분 방법 (ANAL_METHOD=1 Direct Integration 전용, TIME_PARAM)` —— 而契约把两者都留作**记录级分支**，在根上提供 `INC_METHOD` 与 `METHOD`。`/info` 声明 `INC_CTRL` 持有 `INC_METHOD`、`SF` 以及它自己的一个 `DISP_CTRL`。与 MD-47 的 `/db/LLAN` 同种，被同一个检查在深一层处发现。
  * **`/db/MVLD` 没有荷载工况。** `TYPE` 在 `DEFAULT`、`PERMIT_LOAD`、`AUTO_OPTIMIZE` 之间选择，该节为每个值带一个 worked Request Example，而契约只发布了 `LCNAME`、`DESC`、`TYPE`，别的没有。澳大利亚的 `ASL` 使其为四个。
  * **四个空对象**：`/db/SDIS` 与 `/db/SDST` 的 `COMMON`（在隔壁一节的 `/db/SDVI` 里列表）、`/db/NLCT-M1` 的 `CONV_CRITERIA`（三个子对象在一句话里命名，那句话在给出它们两个成员的表上方）、`/db/SDST` 的四个滞回对象（在一个单元格里命名）。
  * **`/db/MVHL` 的 `VEH_EUROCODE`**，上文已登记。
  **以及一个名字自身暴露的解析器缺陷。** 记录下来的名字中有 **64 个**回来是 `bSD" / "iSDOPT" / "SDCONST` 或 `SFI(STR)` 或 `_3_LANE_FACTOR_1" ~ "_3_LANE_FACTOR_4` 这样的东西。**一个 Key 单元格可以一次命名多个属性**，而表格解析器把整个单元格当作一个键返回。当该单元格只喂给计数时这是不可见的；名字一写下来，它就是"一个豁免说明三个字段"与"一个豁免什么都没说明"的区别 —— 这也是为什么 `/db/STCT` 的十六个"缺失"名字**从来就不缺失**。`_unpack_key_cell` 转写出现的三种形式，且**仅用于 `fieldNames`**：合并字段的路径仍走 `_REVIEWED_SHARED_COMPACT_KEYS`，它要求逐行具名审查，因为合并的行会成为一个已发布字段，而被豁免的不会。**没有任何契约字段携带打包名** —— 381 个中唯一的非标识符键是 `/ope/GSBG` 的 `7TH_DOF_TYPE`，那是服务器自己的拼写。
- **证据来源**: `/info/db/MVHL` + 2026-07-30 真实 Eurocode "Load Model 1" 车辆；`check_field_parity` 逐项化后的 84 个真名。
- **状态**: open。归属方：手册仓库转写。
- **对我们的影响**: 补十一个 country 对象；不要无条件要求 `STANDARD_CODE`（另见 MD-16 与 MD-61）。

### MD-49 — 数手册自己的陈述，定了一个字符串却坏了另一个

- **端点**: `/post/TABLE`，面弹簧反力 `TABLE_TYPE`。
- **手册原文**: JSON Schema 与 Specifications 表给 `REACTIONSURFACESPRING`；**只有 Request Example** 给 `REACTIONLSURFACESPRING`（多一个 L）。两个 `/post/TABLE` 的 `TABLE_TYPE` 取值有同一种问题形状：手册各自陈述三次，而三次中有一个不一致。两份契约都声明了多数拼写，且都在一个 `resolved: false` 的 `manualDefects` 条目里**明说没人问过服务器**。
- **实际行为**: 2026-09-04 在 Gen NX 2026 v2.1 与 Civil NX 2026 v2.2（build 09/02/2026）上问了两者：

  | 发送的值 | 服务器 |
  | --- | --- |
  | `BEAMFORCESTP`（表 + 示例） | 识别 |
  | `BEAMFORCESIP`（JSON Schema enum） | 拒绝 |
  | `REACTIONSURFACESPRING`（表 + JSON Schema enum） | **拒绝** |
  | `REACTIONLSURFACESPRING`（仅 request example） | **识别** |

  该探针读的是本仓库别处已依赖的一个区别：`[empty] Cannot generate table data as there is no analysis result` 是产品**知道但填不出**的 `TABLE_TYPE`，而 `there was an error creating utbl` 是它**不知道**的。两个产品、两对都稳定。

- **证据来源**: live 双产品双 SDK 探测 2026-09-04（build 09/02/2026），含上述两种响应形状的区分。
- **状态**: **open upstream；本 SDK 已修正**。归属方：**MIDASIT 文章**（schema 与表），本 SDK 把两者都跟进到了两个包里。
- **对我们的影响**: 用 `REACTIONLSURFACESPRING`；`BEAMFORCESTP` 已确认；不要用多数决定 wire 值。

### MD-50 — 一张有两个 Key 列的表，以及一个写在它上方句子里的字段

- **端点**: `/db/MVCTch`，`FREQ`、`BRIDGE1.BTYPE`、`BRIDGE2.BTYPE`，9 个字段。
- **手册原文**: section 10 **把它们全都记录了** —— `FREQ` 的 25 个键横跨一张两个 Key 列并排的表，而每个 `BTYPE` 在引入其字段表的**粗体句**里，enum 也包括。
- **实际行为**: **本仓库两者都没读到**，两种不同方式，而 `/info` 扫描说出了这一点 —— 九个服务器声明而没有任何契约记录的属性，在一个其章节陈述了每一个的端点上。
  **`FREQ` 表有两个 Key/설명 列对并排**，这是把 25 个键的对象塞进一页的方式：
  ```text
  | Key | 설명 | Key | 설명 |
  | `"USER_F"` | f [Hz] | `"SBEM_L"`/`"SBEM_E"`/... | 단순보 L/E/Ic/mc |
  | `"CBEM_A"`/`"CBEM_B"`/... | 연속보 a/b/L/E/Ic/mc | `"iARCH_TYPE"` | 아치교 형식 |
  ```
  第一个 Key 列里的**一切**都提取出来了，**打包单元格也包括** —— 契约拥有全部六个 `CBEM_*`、全部六个 `ARCH_*`、全部五个 `SUSP_*`。第二个里的**整列被丢弃**。诊断就是这个：**不是 MD-48 的打包 Key 单元格**（这张表恰好证明那个是可用的），**而是一个解析器只读一半的表形状**。七个键：`SBEM_L`、`SBEM_E`、`SBEM_IC`、`SBEM_MC`、`iARCH_TYPE`、`CABL_A`、`CABL_L`。
  **每个 `BRIDGE` 对象的 `BTYPE` 写在引入其表的粗体句里**，不在表的行里：
  > **BRIDGE1 객체 — `"BTYPE"`(Bridge Type: `"RC"` / `"STEEL"` / `"MBRG"`(Old Urban Bridge) / `"TRAIN"`(Train·Subway))별 필드:**
  那句话携带该字段**及其 enum**，而 `BTYPE` 是决定该表 34 行中哪些适用的**选择器** —— 所以缺了它，两个语言里该对象都不可用。两者现在都带 enum 转写，并记在 `extraction.prose` 下、引用了该句 —— 与 `/db/MVCT` 的 Russia-code 句子得到的处理相同。
  **是什么发现的**：不是对章节的审查 —— 是 `/info`-到-契约的扫描，在其小计数尾部。`/db/SECT` 是 995 个未记录属性、毫无意义；`/db/MVCTch` 是 9 个，意味着一个本仓库只读了一半的章节。这正是该扫描的用途，现在它是 **CI 上限**而非某人记得去跑的东西。
  **解析器保持不修，而扫描正是理由。** 全部 27 章里每张表都被扫描过，找表头行携带两个或更多 Key 列的情况。**恰好只有一个：这张表。** 教提取器第二个 Key 列会是为整本手册里唯一一张表写的代码，而只运行一次的代码是没人会正确维护的代码。
  这次测量换来的是一条**守卫**：`scripts/report_dropped_manual_rows.py` 现在统计第三种原因 —— **第二个 Key 列被忽略** —— 计 3 行，即三个其第二个 Key 单元格命名了属性的 `FREQ` 行。它与另外两种原因一起在 CI 中运行，所以一次引入第二张此类表的手册同步会让构建失败，某人会去读那一节，而不是几个月后从一次 `/info` 扫描里发现。如果那个计数增长，解析器改动就不再是为一表而写，而变得值得写。
- **证据来源**: `/info`-到-契约扫描（9 个未记录属性）+ 全 27 章表头扫描（只有一张表有两个 Key 列）。
- **状态**: **fixed here**（本 SDK extractor）；**解析器有意不修**（全手册只有一张这样的表），由 CI 计数守护。归属方：**本 SDK** 的 extractor。
- **对我们的影响**: 从粗体引导句取 `BTYPE` 及其 enum；双 Key 列表需人工核对。

- **手册原文**: `/ope/MEMB` 的官方文章把该选择类型键陈述了三次。其中两次 —— 两个 Input JSON 格式示例 —— 说 `"SELECTION_TYPE"`。**Specifications 表说 `"SELETION_TYPE"`**（少一个 C）。

### MD-52 — 一个文章 id，两个 locale，两个不同的请求示例

- **端点**: `/ope/MEMB` 请求示例，`ko` vs `en-us`。
- **手册原文**: **同一个文章 id** `49514964272665`、**同一个 `updated_at`**，按 locale 提供**不同**的 Input JSON 示例：`ko` 发 `"AELEM": [1, 2]`，`en-us` 发 `"ELEM_LIST": [640, 692]`。两个 locale 的 Specifications 表都说 `ELEM_LIST`。
- **实际行为**: 这一条让与兄弟手册仓库的一次 round trip 付出了代价，而**双方都没有误读**。他们引用 `/ope/MEMB` 的官方请求示例为 `"AELEM": [1, 2]`。本仓库记录的是 `"ELEM_LIST": [640, 692]`，重新 fetch 文章后确认了自己的读法，并把他们的报告为误引。**两次 fetch 都是真的**：

  | | `en-us` | `ko` |
  | --- | --- | --- |
  | Input JSON example | `"ELEM_LIST": [640, 692]` | `"AELEM": [1, 2]` |
  | Output JSON example | `"AELEM": [640, 692]` | `"AELEM": [1, 2]` |
  | Specifications row 3 | `"ELEM_LIST"` | `"ELEM_LIST"` |
  | body counts | ELEM_LIST 2、AELEM 1 | ELEM_LIST 1、AELEM 5 |

  所以 `en-us` 内部一致，而 `ko` **与它自己的表矛盾**。live 运行定了谁对：`ELEM_LIST` 在两个产品上都能指定成员，而 `AELEM` 产生与"完全不发元素列表"相同的 HTTP 200 错误。**`ko` 示例是错的。**
  由此得出两点，第二点比这个端点更大：
  **一个 vendored 引用必须说明它的 locale。** `docs/manual/*.md` 记录了一个来源 URL 却没记录它是用哪个 locale 读的，所以两个人可以忠实地转写同一个 id 却得到不同的字段名。本仓库做过的每一次"取了一个 locale"的手册-对-文章比较都带同样的盲点。
  **"我重新 fetch 了文章，你错了"本身不成立。** 这就是这里善意地、手持原始正文所报告的东西。缺的那一步是问：**一个仔细的人为什么会读到不同的东西** —— 一旦问了，它恰好有一个便宜的答案可查。
- **证据来源**: 两次真实 fetch（`en-us` 与 `ko` 正文对照，同 id 同 `updated_at`）+ 双产品 live。
- **状态**: **open upstream；vendored 手册带正确的 `ELEM_LIST`**。归属方：**MIDASIT 文章**（`ko` locale）。
- **对我们的影响**: 引用手册必须注明 locale；不要把"重新 fetch 过"当作充分证据。

## 附：原文中贯穿性的方法论要点（对下游转写项目有用）

这些不是 MD 条目，而是原文反复强调、对"照抄手册建端点注册表"的项目直接适用的规则：

1. **手册某一节可以对自己端点的字段名说错，不只是枚举值错。** 已确认案例：`/db/REBW`（2026-07-29，live PUT round trip 定案）、`/db/REBC`（2026-08-27，live POST 对比定案）、`/db/REBR`（MD-34，`/info` + 先例）。**每一节的 Specifications 表应独立视为可能出错**，在建契约前用 `/info/db/...` 对照真实有数据的模型交叉核对。
2. **`/info` 既不是服务器所接受内容的超集，也不是子集。** 反例两侧都有：`/info/db/POSL` 在**两个**产品上都声明 `CODE`，而 Civil NX 对它（即使作为空字符串）答 `Wrong Field`；`/info/db/STBK` **不**声明 `LCNAME`，而 `live_crud_check.py` 的已确认 create-read-update-delete round trip 在两个产品上都发送它并通过。**两者不一致时，round trip 胜出。** 实用形式：`/info` 声明而手册不声明 → 加字段，记 `unstated`；`/info` 不声明而手册声明 → **保留字段**，加注记，**绝不**仅凭这一点删除（MD-37 的 `WALL`）；两者命名不同 → 用服务器的名字并登记缺陷（MD-34、MD-37、MD-38）；live round trip 与 `/info` 矛盾 → round trip 胜出并写明。
3. **"Wrong Field" 通常意味着值错，而不是字段名错。** 在 `/db/TDMT` 与 `/db/TDME` 上确认：未识别的 `CODE`/`CODENAME` 答 `Wrong Field`，而**已识别**的码配错伴随字段答 `[Error] ... input data contain errors.` —— **先变枚举值**。
4. **手册的 worked example 是起点猜测，不是权威。** MD-53、MD-54、MD-55、MD-60 都是照印的示例无法运行。而且**在官方文章被读过之前，一个文档缺陷是未证明的**（MD-54 原先归因文章、重读后发现是章节转写引入的；MD-51/MD-52 是规范化 vendored 副本隐藏了上游问题）。
5. **多数决不是证据。** 三份文档一致是同一个来源的三次转写（MD-49）。
6. **手册与自己不一致，比手册与自己一致更有价值**（MD-37 的 `BEAM`/`BEAM_COLUMN`）。
