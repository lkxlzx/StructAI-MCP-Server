# P149-A · 端点方法集**实测修正**与写路径分母重算 v1.0

> 权威来源：`docs/07` §16 **R4 / R14** · §16.1 **R108（本批新增）** ·
> `registry/README.md` §2.3 / §8.9（⑩）· 证据 = `registry/live/live_methods.json` ·
> 工具 = `registry/tools/sync_endpoint_methods.py` · 可执行判定 = `tests/test_midas_endpoint_methods_p149.py`。

---

## 0. 一句话结论

用**只读** `OPTIONS`（`Allow` 响应头 = 该路由真实支持的方法集，**零副作用**）对 **636** 个端点做了一次扫描，
发现 registry 的 `methods` **系统性少声明**：

* `registry == live` **513** 个；
* **少声明 90 个**（+`DELETE` 88 · +`PUT` 80 · +`GET` 62 · +`POST` 6；DB 9 · DESIGN 80 · OPE 1）；
* **多声明 0 个**（registry 只漏不夸）；
* **72 个端点在本 build 上路由不存在**（`OPTIONS`/`HEAD` 均 404）—— **不**改它们的 `methods`，只如实记录。

按实测修正后：**写路径分母 `609 → 633`**（`model_write 410 → 434` · `write_only 368 → 306` ·
`result_query` 仍 `199`）—— 即 registry 原来把 **24 个写路径端点整个漏出分母**。
候选集**不变**（GEN NX `58` / CIVIL NX `49` / CD `0`），因为它们仍**缺数据侧模板**；
被阻塞数随之 `495 → 515` / `443 → 451` / `31`。

## 1. 方法（只读、零副作用）

```powershell
$env:PYTHONUTF8 = '1'
. .\scripts\load-midas-env.ps1 -Instance gen        # 凭据只经环境变量
$ErrorActionPreference = 'Continue'
# ① 只读探测（只发 OPTIONS，无 Allow 时补一次 HEAD）→ 写证据文件
.\.venv\Scripts\python.exe registry/tools/sync_endpoint_methods.py --probe
# ② 预演（逐条列出「改动前 → 改动后」，不写盘）
.\.venv\Scripts\python.exe registry/tools/sync_endpoint_methods.py
# ③ 写回（只改端点定义里的 methods 一行）
.\.venv\Scripts\python.exe registry/tools/sync_endpoint_methods.py --write
# ④ 断言（CI：已落盘 == 机械结果）
.\.venv\Scripts\python.exe registry/tools/sync_endpoint_methods.py --check
```

**为什么 `OPTIONS` 是可信来源**：`GET /POST/TABLE` → `405` 且带 `Allow: POST`；`OPTIONS /DB/REBB`
→ `200` 且 `Allow: POST,GET,HEAD,PUT,DELETE`；而 registry 当时只声明 `POST`，`GET /DB/REBB` 实测 **200**
⇒ 少声明**确凿**。`Allow` 里出现的 `HEAD` 一律剔除（框架自动方法，非契约方法）。

**上游交叉验证**：`E:\MCP\MIDAS-API-Online-Manual\manual\midas Gen API 使用手册.md`（12 MB）的
`**Active Methods**` 与 live `Allow` 在 **541** 个可比端点里 **532** 个完全一致（98.3%）。差异 **9** 条：

| 端点 | 手册 `Active Methods` | live `Allow` |
| --- | --- | --- |
| `DB.BNGR` / `DB.GRUP` | `GET,POST,PUT` | `+DELETE` |
| `DB.REBC` | `POST` | `+GET,PUT,DELETE` |
| `DESIGN.RC.KDS-41-20-2022.MEMB` | `DELETE,GET,PUT` | `+POST` |
| `DESIGN.RC.KDS-41-20-2022.SRDF` | `DELETE,GET,PUT` | `GET,PUT`（**少** `DELETE`） |
| `DESIGN.SRC.AIK-SRC2K.DSRC` | `DELETE,PUT` | `+GET` |
| `DESIGN.SRC.AIK-SRC2K.MEMB` / `DESIGN.STEEL.KDS-41-30-2022.MEMB` | `DELETE,GET,PUT` | `+POST` |
| `OPE.SECTPROP` | `GET` | `+POST` |

⇒ 真值取 **live `OPTIONS`**（手册与实测不一致时以实测为准；上表 9 条**逐条留证**）。

## 2. 逐条差异（90 条，改动前 → 改动后）

`registry/tools/sync_endpoint_methods.py`（预演）逐条打印，摘要：

| 命名空间 | 条数 | 典型「改动前 → 改动后」 |
| --- | --- | --- |
| `DB` | 9 | `DB.REBB`/`REBC`/`REBR`/`REBW`：`POST` → `POST, GET, PUT, DELETE`；`DB.BNGR`/`GRUP`/`IFGS`：`GET,POST,PUT` → `+DELETE`；`DB.KFAC`：`GET,PUT` → `POST,GET,PUT,DELETE`；**`DB.SWIND`：``（空）→ `POST,GET,PUT,DELETE`** |
| `DESIGN` | 80 | 多数 `POST` → `POST,GET,PUT,DELETE`；`DESIGN.*.DCO`/`DCTL`/`LLRF`/`LMRR`/`MATD`：`GET` → `GET,PUT,DELETE` |
| `OPE` | 1 | `OPE.SECTPROP`：`GET` → `POST,GET` |

**连带效果**（同一批、非人工）：

* `write_path_keys()` **609 → 633**：新增 **24** 个写路径端点进分母（20 个 `DESIGN.*` 由「只有 `GET`」
  变为「`GET,PUT,DELETE`」⇒ 有了写方法 `PUT`；`DB.SWIND` 由「无方法」变为四方法齐全；`OPE.SECTPROP` 由
  `GET` 变为 `POST,GET`；其余为 DESIGN.SRC / DESIGN.STEEL 同类项）。
* `write_only_keys()` **368 → 306**：这些端点原来「连 `GET` 都没有」，现在有了读路径。
* `model_write_keys()` **410 → 434**。
* `midas_api_mappings` / 9 Tool Contract **未改**（方法集不是契约的一部分）；`AppContainer` / Settings /
  表结构 **一行未动**。
* `sync_manifest.py` 预演 **90** 处字段差异 → `--write` → 再预演 **0**（幂等）。

## 3. 72 个「本 build 路由不存在」的端点（如实记录，**不**改数据）

`OPTIONS` 无 `Allow` 且 `HEAD` 亦 `404` ⇒ 该路由在本实例上**不存在**。按命名空间：
`DB 45` · `OPE 11` · `DOC 9` · `OPRT 6` · `DESIGN 1`。其中 **21** 个是 `-M1` 变体
（`DB.ACTL-M1` / `BCGA-M1` / `BCGD-M1` / `EIGV-M1` / `EPMT-M1` / `HHCT-M1` / `IEHG-{BEAM,GL,PSS,TRUSS}-M1` /
`IMFM-M1` / `MATL-M1` / `NLCT-M1` / `NLNK-M1` / `POGD-M1` / `POLC-M1` / `STCT-M1` / `STYP-M1` / `THGC-M1` /
`THIS-M1` / `THOO-M1`），另有 `DB.SPAN`（P138c 已从 `GEN_NX` 摘除 `products`）、`DB.LCOM`、`DB.UFTR` /
`DB.UTBL`（P136a 已摘除）、`OPE.IBFD`/`IBSD`/`IDSD`/`IELD`/`IGLD`/`IPLD`/`IRED`/`ISSD`/`ITRD`（CIVIL NX 侧）、
`OPRT.*`（Civil Designer）、`DOC.*` 若干。

**处置（本批裁决）**：**不**改 `methods`、**不**改 `products` / `availability` ——
它们是**有据可查**的端点定义（手册里确有条目），只是**本 build 不可得**；如实记录在证据文件
（`live_methods` 为空）与本文 §3，供后续按实例/版本逐条收口。**不**把它们算作「欠账」。

### 4.1 一处**新事实**（如实记录，**不**放宽任何判定）

`DESIGN.SRC.AIK-SRC2K.DSRC` 的方法集由 `[PUT]` 实测修正为 `[GET, PUT, DELETE]` ⇒ 它成为契约写端点里
**唯一**「三步链形态齐备（有写方法 + `GET` + `read_root` + `DELETE`）却**既无** Transformer
**又无**数据侧模板」的端点。P142 的判定 8「契约内不再有『仅缺 Transformer』的写端点」因此**不再成立**
（该行标注的是 **P142 时**的事实，**保留原文**，此处如实记录变化）。
可执行判定 = `tests/test_midas_write_coverage_p142.py` 的 `BLOCKED_CONTRACT_WRITE_KEYS`
（`("DESIGN.SRC.AIK-SRC2K.DSRC",)`）+ 两条断言（`blocked == {...}`、`blocked & candidates == ∅`）。

## 5. 下一步（P149-B 及以后，已量化）

用同一份实测真值复算「已具备**可判形态**（写 ∧ 读回 ∧ `DELETE` ∧ 本 build 存在）但**缺数据侧模板**」的端点
= **226** 个（DB 150 · DESIGN 76）。其模板来源可得性（逐条可复算）：

| 来源 | 可得条数 |
| --- | --- |
| 旧来源 `MIDAS_API_Online_Manual_数据_v1.0.json` 的可用示例 | **123** |
| 新手册 `midas Gen API 使用手册.md` 的 `**Request Examples**` | **70** |
| 数据侧请求 Schema 文件（字段白名单可判） | **213** |
| **完全无示例**（旧 + 新都没有） | **33**（22 个 `-M1` + `DB.GALD` / `DB.NUCS` + 10 个 `DESIGN.*`） |

⇒ P149-B 起：① 把新手册抽成**第二个模板来源**（可复算）；② 为 226 个端点逐批补模板（每批 20~40）；
③ 33 个完全无示例的按**规格表 / Schema** 机械构造或如实留缺；④ 之后才是
**R106**（`POST.TABLE.*` 195~199 个取报表判据）与 **R107**（单例 / 设置表：live 只有 `GET,PUT` 的端点，
判据 = 「读回 → `PUT` 改 → 读回确认 → 还原」，单独子桶报告）。
