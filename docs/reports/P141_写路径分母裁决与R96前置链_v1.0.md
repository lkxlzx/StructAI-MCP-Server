## 3. R96：非空项目上的前置链（实现 + 实测）

### 3.1 原状与机制

原状：模板的前置编号从 `1` 起（`DB.NODE#1` …），目标 body 里也写死同样的编号；而空项目闸门
**按设计**只允许空项目 → 非空项目上「编号即引用」的假定不成立。

现在**编号一律重新分配**（`docs/07` §16 R96 行）：

| 机制 | 数据侧声明 | 语义 |
| --- | --- | --- |
| 前置编号 | （缺省） | 该端点**既有编号**的 `max + 1`（同一端点的多个前置依次 `+1`） |
| 编号写回 | `prerequisites[].references` | `[{in, path}]`：该前置编号出现在**哪个 body 的哪个路径**（`in` = `owner` 或同一模板里另一个前置的 `<key>#<id>`） |
| 目标自身编号 | `self_references` | 目标编号在**自身 body** 里的路径（`[["ITEMS", 0, "ID"]]`） |
| **反向依赖** | `target_id_source` | **目标自身**编号取某个前置分配到的编号（`DB.CONS` / `DB.CNLD` 的 `Assign` 键**就是**它那个节点号） |

**逐条可判**（`registry/tools/check_write_templates.py` 新增第 4 / 5 条校验）：
`references[].path` / `self_references[]` 必须**存在**且当前取值**恰好**等于声明的编号；
`target_id_source` 必须指向本模板里的一个前置，且被指向的前置**不得**又用 `id_source = "target"`
（循环依赖）。**不**做「body 里每个像编号的整数都必须被声明」这类判定 —— 同一个整数可能同时是
材质号 / 截面号 / 节点号 / 枚举值，无从机械区分，硬判只会制造假阳性。

数据侧声明量：`references` **14** 条 / `self_references` **4** 条 / `target_id_source` **2** 条。

### 3.2 闸门语义（**不**绕过）

| 模式 | 判据 |
| --- | --- |
| **默认**（`allow_non_empty=False`） | 专用项目**必须为空**（`STRUCTAI-3000 dedicated_test_project_not_empty` + **零**写请求）—— 不变 |
| 显式 `allow_non_empty=True` | 写前记下**被触碰端点**的既有编号集合 → 清理后**逐端点**核对**一字未变**；变了即如实 `FAILED`（`detail = existing_id_set_changed`） |

后者是**更强**的「只碰自建 ID」判据：空项目闸门只是它的**充分**条件（空集显然不变）。

### 3.3 真实实测（门控用例，专用项目）

**空项目（回归，**未**回退）**：GEN NX 的 **10** 个可探候选 → **10 / 10 `PASSED`**；
`live.write_path_coverage()` = **`10 / 609`**（P139 不变）；`model_write_ratio` = **`10 / 410`**。

**非空项目（R96 新证据）**：先**预置**最小模型 `MATL#1` / `SECT#1` / `NODE#1` / `NODE#2`，再跑
`DB.ELEM` + `DB.CONS`（`allow_non_empty=True`）：

| 端点 | 四态 | 自建编号 | 前置（**实分配**） | 读回 | 已删 |
| --- | --- | --- | --- | --- | --- |
| `DB.ELEM` | **`PASSED`** | `1` | `DB.MATL#2` · `DB.SECT#2` · `DB.NODE#3` · `DB.NODE#4` | `True` | `True` |
| `DB.CONS` | **`PASSED`** | `3` | `DB.NODE#3`（`target_id_source`：目标的 `Assign` 键 = 该节点号） | `True` | `True` |

清理后 `MATL` / `SECT` / `NODE` 的既有编号集合与写前**逐条相等**（`['1']` / `['1']` / `['1','2']`）。

**首次实测暴露的真实缺陷（已修）**：`DB.CONS` 的前置曾用 `id_source = "target"`（前置取**目标**编号），
于是目标按自己端点的 `max + 1`（`CONS` 空表 → `1`）取号，前置就去建 `DB.NODE#1` —— **已存在** →
`400`，`detail = prerequisite_failed:DB.NODE#1:software_api_error`。根因是**依赖方向反了**：
`CONS` / `CNLD` 的 `Assign` 键**就是**节点号，故必须**目标取前置**编号（`target_id_source`）。
修复后同一场景 **`PASSED`**。

## 4. 裁决⑤：写路径分母（**不挪**，另报子桶）

| 项 | 值 |
| --- | --- |
| **正式**分母（R4 / R14） | `live.write_path_keys()` = **609**（**不挪**） |
| 子桶：结果表 / 文本查询 | **199**（`namespace == "POST"`：`/POST/TABLE` · `/POST/TEXT` · `/POST/PM` · `/POST/STEELCODECHECK`） |
| 子桶：模型写 | **410**（其余） |
| 同时报出的两个比率 | `ratio` = `<分子> / 609`（**原口径**）· `model_write_ratio` = `<分子> / 410`（**子桶**） |

**为什么单列**：结果表端点用 `Argument.TABLE_TYPE` **取表**，**不创建 / 不修改 / 不删除**任何模型对象
⇒ L5 三步链（创建 → 读回 → 按路径 key 删除）**结构上不适用**（没有「自建 ID」）。

**为什么**不**挪分母**：① 换分母会**放宽**判定（把结构上不适用的一部分排除出统计）；② 分母是
`docs/07` §16 R4 / R14 的口径，改它需要**显式裁决**并写明影响面；③ 单列子桶已能说明问题，
且**原口径照旧报出**。

**不隐藏（可执行）**：`test_p141_the_sub_bucket_never_hides_an_uncovered_endpoint` 给一条
`POST.TABLE` 的 L5 `PASSED` 行 → `covered = 2`（原口径**不**过滤）、`model_write_covered = 1`。

`WriteCoverage` 新增字段：`result_query` / `model_write` / `model_write_covered` / `model_write_ratio`
（`as_dict()` 一并给出，**不含**凭据）。

## 5. ② `CONCURRENT_JOINT_FORCE` 的判别（**更正** P140 的措辞）

### 5.1 实测（GEN NX，专用项目，只碰自建 ID）

模型：`SECT#1` · `STLD#1` · `MATL#1` · `NODE#1-2` · `ELEM#1` · `CONS#1` · `BMLD#1` → `POST /DOC/ANAL`（空体）
→ 结果已生成（`WEIGHT_IRREGULARITY_X` 取到 `200` 即为证）。**不带** `EXPORT_PATH` ⇒ **不**落任何文件。

| 请求 | 状态 | `error creating utbl` 标记 | 原始消息 |
| --- | --- | --- | --- |
| 伪 token `STRUCTAI_NOT_A_TABLE_TYPE`（对照） | `400` | **有** | `MIDAS GEN NX there was an error creating utbl. (ex PostMode ...)` |
| `WEIGHT_IRREGULARITY_X` | `200` | 无 | `{}` |
| `STORY_SHEAR_FORCE_COEFFICIENT` | `200` | 无 | `{}` |
| `PLANESTRAINFL` | `200` | 无 | `{}` |
| `PLANESTRESSFL` | `200` | 无 | `{}` |
| `PLANESTRAINSG` | `200` | 无 | `{}` |
| `CONCURRENT_JOINT_FORCE`（**完整**必填体：`TABLE_TYPE` + `LOAD_CASE_NAMES` + `ADDITIONAL.SET_REACTION_PARAMS`） | `400` | **有** | 与伪 token **逐字相同** |

**对照组说明**：无结果时（只建节点、不建单元）`WEIGHT_IRREGULARITY_X` 会得到
`400 Cannot generate table data as there is no analysis result.` —— **不带** `error creating utbl` 标记。
因此该标记的含义是**建表规格没被认出来**（`ex PostMode`），与「有没有结果」**正交**。

### 5.2 结论（**如实**）

1. `CONCURRENT_JOINT_FORCE` 在本 build 上与**伪 token 同形** → **不接受**；它与
   `PLANESTRAINFL` 等「已登记但本模型无该结果」的 token **不同**（后者照样 `200`）。
2. ⚠️ **更正 P140 的措辞**：「需移动荷载 / 后处理模式的模型」**不成立** —— 同一模型、同一时刻，
   同样缺所需结果的 `PLANESTRAINFL` 得到 `200` ⇒ 差异**不在**「模型缺某类结果」。
3. **残余假设（未排除）**：该表要求某个**分析模式开关**（`PostMode`）在模型里打开。若要证伪，
   需**移动荷载模型**（lane `DB.SLAN` / `DB.LLAN` + vehicle `DB.MVHC` / `DB.MVHL` → `DB.MVLD`），
   成本高（要建桥梁模型），**不建议**优先。
4. **入账口径**：无论哪一种解释，它**没有取得 `200`** ⇒ R5 账上仍记「**未正向验证**」
   （`verification_status` 保持 `PARTIAL`），**不**记为已判别为接受；手册来源的 Schema **保留**
   （它记录的是**上游规格** `TABLE_TYPE.enum`，与「本 build 是否实现」是两件事）。
