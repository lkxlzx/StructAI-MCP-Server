## 0. 一句话结论

在 **GEN NX 空项目**上按同一机制（数据侧模板 + 真实 L5 三步链）推进第五批：**13 个端点 → 12 个跑通**
（`DB.EXLD` / `DB.LDSQ` / `DB.HHCT` / `DB.MVCTBS` / `DB.MVCTCH` / `DB.MVCTID` / `DB.MVCTTR` /
`DB.POSL` / `DB.STOR` / `DB.EFCT` / `DB.NMAS` / `DB.TDNT`），**1 个如实留缺**
（`DB.IMFM`：手册**两个**条目都被本 build 拒绝 `400 software_api_error` → **R105**）。
覆盖率 **`46 / 609` → `58 / 609`**（`model_write_ratio` **`46 / 410` → `58 / 410`**）；
跑前 / 跑后哨兵（**20** 个端点）**全空、0 不可读** ⇒ **零残留**。

本批的**新内容**：① 3 个端点的请求体**引用荷载工况名** ⇒ 用**既有**的 `DB.STLD` 前置链（**不**改判据、
**不**在数据侧硬凑）救回；② `DB.NMAS` 用 R96 的 `target_id_source` 让 `Assign` 键取自建节点号；
③ `DB.TDNT` 用 `prerequisites[].references` 把自建材质号写回 body 的 `MATL`。

## 1. 本批推进：13 个候选 → **12 个通过**（+12）

### 1.1 选点原则

从「有写方法 ∧ 有读路径（`GET` + `read_root`）∧ 有 `DELETE` ∧ 非危险 ∧ 产品可得 ∧ **无**模板 ∧
无 Transformer」的 **155** 个端点里（P147 收尾后的池子；其中同一 `input_uri` 口径下 **132** 个有
**可用**手册示例条目 —— 判据 = `check_write_templates.manual_item()` 能取到「包装键恰好 1 个 +
条目是对象」），只取**定义类独立表**。

落盘**前**的**只读**闸门（沿用 P147）：

1. 用上游手册的**同一条**示例条目（`input_uri` 大小写与手册一致）取出 body；
2. `GET /info/db/<CODE>` 取本 build 的**接受字段集**（递归含嵌套 `properties`），
   逐字段核对「手册示例字段 ⊆ 接受字段」⇒ 本批 13 个端点 `unknown` = **0**；
3. 才写入 `registry/live/write_templates.json`。

> ⚠️ 第 2 步是 **R101** 教训的制度化：`DB.ACTL` 的 `CLATS` 在**数据侧 Schema 里存在**，但本 build
> **不接受**（自省字段是 `ACWC`）⇒「Schema 声明」**不足以**判定是否被接受。

**批量口径**：

- 第一次有界批量（13 个 key）：`counts = {PASSED: 10, FAILED: 3, NO_PAYLOAD_TEMPLATE: 0, NO_READBACK: 0}`
  —— `DB.EXLD` / `DB.LDSQ` / `DB.IMFM` 为 `400 software_api_error`；
- 补 `DB.STLD` 前置 + 换 `DB.IMFM` 手册条目 8 后，第二次有界批量（仍 13 个 key）：
  `counts = {PASSED: 12, FAILED: 1, ...}`；
- 最终**一次**全量批量（**58** 个候选，`pytest` 门控用例内）：
  `counts = {PASSED: 58, FAILED: 0, NO_PAYLOAD_TEMPLATE: 0, NO_READBACK: 0}`；
  `write_path_coverage()` = **`58 / 609`**（`model_write_ratio` **`58 / 410`**）。

**脱敏后的请求形态**（12 条同形，以 `DB.EFCT` 为例）：

```text
POST /DB/STLD            # 前置 1：工况名 = 目标请求体 LCNAME 引用的名字
{"Assign": {"1": {"NAME": "DL", "TYPE": "D", "DESC": "DeadLoads"}}}      -> 200
POST /DB/STLD            # 前置 2：COMB_LIST 第二个工况名
{"Assign": {"2": {"NAME": "LL", "TYPE": "D", "DESC": "DeadLoads"}}}      -> 200
POST /DB/EFCT            # 目标：body 原样照抄手册示例；编号 = 既有编号 max + 1 = 1
{"Assign": {"1": {"bADDLC": false, "LCNAME": "DL", "bUSECOMB": true, ...}}} -> 200
GET  /DB/EFCT            # read_root = EFCT；自建编号 1 出现在编号集合里 -> read_back = True
DELETE /DB/EFCT/1        # 必带路径 key                                -> 200
DELETE /DB/STLD/2        # 前置**逆序**删除
DELETE /DB/STLD/1
GET  /DB/EFCT            # 收尾时编号集合不再含 1                       -> 零残留
```

### 1.3 纪律核对

- **只碰自建编号**：每条都是「`GET` 既有编号（空）→ `max + 1` 创建 → 读回 → `DELETE <路径 key>`」；
- **跑前哨兵**：4 个默认哨兵（`DB.NODE` / `DB.ELEM` / `DB.MATL` / `DB.SECT`）**全空** ⇒ 空项目闸门放行；
- **跑前 / 跑后哨兵**：**20** 个端点（4 哨兵 + `DB.STLD` / `DB.FBLD` / `DB.BMLD` + 13 个候选）逐个**只读**
  `GET` → `non_empty = 0`、`unreadable = 0`（两次实测逐字相同）⇒ **零残留**；
- **失败尝试零残留**：`DB.IMFM` 被拒（`400`）时**没有**创建任何对象（`created_id` 为空），
  收尾 `GET` 复核哨兵仍全空；
- **绝不**放宽「创建 → 读回 → 按路径 key 删除」三步判定；**绝不**在云端生产项目上跑。

## 3. 新裁决 **R105**：`DB.IMFM` **如实留缺**（带原生证据）

原生判别（`gen-local`，**有界批量**；每个条目**只**发一组「创建 → 读回 → 删除」）：

| 端点 | 实测证据 | 为什么数据侧无法表达 | 处置 |
| --- | --- | --- | --- |
| `DB.IMFM` | 手册**条目 7**（`{"STEEL_NAME": "Inealstic_Steel"}`）→ `POST /DB/IMFM` = **`400 software_api_error`**；**条目 8**（`{"CONC_NAME": "Inelastic_Conc", "CONFINED_CONC_NAME": "Inelastic_Conc", "REBAR_NAME": "Inealstic_Steel"}`）→ **`400 software_api_error`**；`GET /DB/IMFM` 始终为空 | 本 build **拒绝**手册的**两个**取值形态；`adjustments` **只**能改**值**（且必须命中原值）、**不能**改结构 / 加字段 ⇒ 数据侧无从推出可接受形态 | **留缺**（模板**已撤**）；恢复条件 = 上游手册 / 新 build 给出可接受示例 |

**同时证明这不是数据侧缺陷**（可执行断言，`tests/test_midas_write_coverage_p148.py`）：该端点仍
`enabled = true`、`availability = verified`、`methods` 含 `POST` / `GET` / `DELETE`，且**两个**手册
条目的**每个**字段都在数据侧请求 Schema 里声明（`set(body) <= accepted`），落盘前的**只读**自省
`unknown` = **0**。

> ⚠️ 该端点**没有**模板 ⇒ **不**入候选 ⇒ 不会污染 `limit`、不会产生假的 `FAILED` 记录。
> 本批**没有**放宽任何判定：`PASSED` 仍要求「创建 → 读回 → 按路径 key 删除」三步全成立。
> 与 R103（`DB.SKEW`：手册示例被拒）/ R104（`DB.MVCT` / `DB.TDMF` / `DB.THGC`）**同形**。
