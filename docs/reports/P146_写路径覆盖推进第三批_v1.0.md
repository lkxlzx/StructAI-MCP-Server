## 1. 本批推进：10 个候选 → **7 个通过**（+7）

### 1.1 选点原则

从「有写方法 ∧ 有读路径 ∧ 有 `DELETE` ∧ 非危险 ∧ 有**手册示例** ∧ **无**模板」的 **172** 个端点里
（`docs/07` §15.5 的 P145 行 (e)），只取**定义类独立表**：请求体不引用任何**既有**对象
（节点 / 单元 / 材质 / 截面 / 荷载工况 / 组），即**零前置链** —— 这样每一条模板都只增加一个
`manual_example`、不引入任何前置声明。

本批 10 个 key：`DB.LDGR` · `DB.MADO` · `DB.PJCF` · `DB.PNLD` · `DB.SKEW` · `DB.SPFC` ·
`DB.HSPT` · `DB.THFC` · `DB.THIK` · `DB.SMCT`。

### 1.3 纪律核对

- **只碰自建编号**：每条都是「`GET` 既有编号（空）→ `max + 1` 创建 → 读回 → `DELETE <路径 key>`」；
- **跑前哨兵**：4 个默认哨兵（`DB.NODE` / `DB.ELEM` / `DB.MATL` / `DB.SECT`）**全空** ⇒ 空项目闸门放行；
- **跑后哨兵**：**43** 个端点（36 个候选 + 7 个被触碰的前置端点）逐个 `GET` →
  `non_empty = 0`、`unreadable = 0` ⇒ **零残留**；
- **失败尝试零残留**：`DB.SKEW` / `DB.HSPT` / `DB.MADO` 的原生判别每次都 `GET` 复核为空后才收尾。

## 3. 新裁决 **R103**：3 个端点**如实留缺**（带原生证据）

原生判别（`gen-local`，每次尝试后 `GET` 复核为空）：

| 端点 | 实测证据 | 为什么数据侧无法表达 | 处置 |
| --- | --- | --- | --- |
| `DB.SKEW` | 手册 **3** 个变体（`Angle Type` / `3 Points Type` / `Vector Type`）逐个 `POST` → **全部** `400 software_api_error`；`GET /DB/SKEW` 始终 `{"SKEW": {}}` | 本 build **拒绝**手册示例的**每一个**取值形态；`adjustments` **只**能改**值**、**不能**改结构 ⇒ 数据侧无从推出一个可接受形态 | **留缺**；恢复条件 = 上游手册 / 新 build 给出可接受示例 |
| `DB.HSPT` | `POST` → **`200`**，响应体**回显** `{"HSPT": {"1": {...}}}`；紧随的 `GET /DB/HSPT` → **`{"HSPT": {}}`** ⇒ 三步链的「读回」不成立 | 「创建 → 读回」在本 build 上**不成立**（写被接受但读不回）⇒ **绝不**放宽三步判定 | **留缺**；与 R101 的 `DB.EDMP` **同形** |
| `DB.MADO` | `POST` → **`200`** 但响应体为**空表** `{"MADO": {}}`；`GET /DB/MADO` → `{"MADO": {}}` ⇒ 静默 no-op | 同上：创建**不落库** ⇒ 读回不成立 | **留缺** |

**同时证明这不是数据侧缺陷**（可执行断言，`tests/test_midas_write_coverage_p146.py`）：三个端点仍
`enabled = true`、`availability = verified`、`methods` 含 `POST` / `GET` / `DELETE`，且**手册示例的每个
字段都在数据侧请求 Schema 里声明**（`set(body) <= set(properties)`）。

> ⚠️ 三个端点**没有**模板 ⇒ **不**入候选 ⇒ 不会污染 `limit`、不会产生假的 `FAILED` 记录。
> 本批**没有**放宽任何判定：`PASSED` 仍要求「创建 → 读回 → 按路径 key 删除」三步全成立。

### 3.1 附带发现：`DB.SSEIS` 的 Schema **形状**在复算工具口径下不可判（本批**不**纳入）

`DB.SSEIS` 的请求 Schema 把条目字段声明在 `Assign` 的 **`patternProperties`**（`^[0-9]+$`）下，
而 `registry/tools/check_write_templates.py` 的 `request_schema()` **只**读 `properties`
⇒ 该形状下 `body` 的「字段不臆造」判定**不可判**（会退化成对**顶层** Schema 的误判）。

**处置**：本批**不**纳入 —— **不**改工具、**不**放宽判定、**不**写模板（端点本身仍 `enabled` /
`verified` / 可写，数据侧**未**动）。**恢复条件** = 工具支持 `patternProperties` 形状后按同一判据纳入。

## 7. 过程事件（如实记录）

本批在**原生逐端点判别**阶段对同一 `gen-local` 实例连发了多轮写请求（全量批量 39 → 原生判别 →
两轮候选筛选），实例随后**崩溃**（MIDAS 弹窗：*发生了无法确定的问题需要终止程序*，恢复文件
`D:\Program\MIDAS\MIDAS GEN NX\DgnPlugin\_restore.mgbx`）。**无法**断定是哪一条请求触发的 ——
崩溃前的几次调用返回的是 `request_timed_out` / `transport_error`，说明进程在其之前已异常。

**恢复与复核**：实例恢复后**只读**核对 —— 4 个哨兵 + 目标端点**全空**（失败尝试未留残留），
随后**只跑一次**全量批量（不再做任何逐端点试探）→ **36 / 36 `PASSED`** → 跑后 **43** 个哨兵
`non_empty = 0` / `unreadable = 0`。

**纪律改进（下一批起）**：候选筛选**不再**用「逐端点原生试探」的方式做 —— 需要判断某个端点是否
被本 build 接受时，**只**用一次全量批量（其 `FAILED` 明细已足够定位），或先查
`GET /info/db/<CODE>` 自省字段（**只读**，不写）。
