## 3. P138b —— R5：20 个无 Schema 端点按实测分类

**不**臆造、**不**新增文件（`registry/schema/**` 仍 **616** 个）。判据全部来自数据文件本身：

| 类 | 条数 | 端点 | 判据（可执行） |
| --- | --- | --- | --- |
| `no_request_body` | **4** | `DB.LCOM` / `OPE.PROJECTSTATUS` / `OPE.SECTPROP` / `VIEW.SELECT` | `methods` 不含 `POST`/`PUT`/`PATCH` |
| `manual_has_no_json_schema` | **5** | `OPE.MEMB` / `OPE.STOR` / `OPE.STORPROP` / `OPE.STORY_IRR_PARAM` / `OPE.STORY_PARAM` | 手册**有同一个 URI** 的条目，但 `json_schema` 为空 |
| `uri_differs_in_manual` | **1** | `OPE.BMLD` | 手册没有该 URI，只有同名 code 的 `db/BMLD` |
| `post_table_key_without_manual_table_type` | **3** | `POST.TABLE.{CONCURRENT_JOINT_FORCE, STORY_SHEAR_FORCE_COEFFICIENT, WEIGHT_IRREGULARITY_X}` | 手册条目的 `table_types` 为空 |
| `absent_from_nx_manual` | **7** | `DOC.CLOSEALL` / `DOC.EXIT` / `OPE.CP{CREATE,EXPORT,UPDATEMODEL,UPDATERESULT}` / `OPE.STORYPROP` | 手册完全没有该 URI，也没有同名 code |

⚠️ **与旧提示词分组不同的两处**（以实测为准）：

1. `OPE.MEMB` / `OPE.STOR` / `OPE.STORPROP` / `OPE.STORY_*_PARAM` 的手册条目**就是同一个 URI**
   （`ope/MEMB` / `ope/STOR` / `ope/STORPROP` / `ope/STORY_*`）—— 不是「手册有同名端点但 URI 不同」；
   它们是「手册有该 URI 但没有 `json_schema`（只有参数表）」。
2. `OPE.STORPROP` 在手册里**有**同 URI 条目 —— 旧提示词把它归入「手册完全没有」不成立。

### 3.1 顺带裁决：`request_schema_confirmed` 对**无请求体**端点「不适用」

`methods` 不含 `POST` / `PUT` / `PATCH` 的端点**没有请求体**，把「没有请求 Schema」判成缺口是**类别错误**
（会让这类端点**永远** `PARTIAL`）→ 该项**视为满足**，由 `live.not_applicable_items()` **如实**报出
（`has_request_body()` / `not_applicable_items()` 是可执行判定）。

| 端点 | 改动前缺项 | 改动后缺项 | `verification_status` |
| --- | --- | --- | --- |
| `OPE.PROJECTSTATUS` | `request_schema_confirmed` + `response_schema_confirmed` | **`response_schema_confirmed`**（真实缺口：没有 Schema 文件 → 没有 `response` 块） | `PARTIAL`（**未**升级） |
| `OPE.SECTPROP` / `VIEW.SELECT` | 同上 | 同上 | `PARTIAL`（**未**升级） |
| `OPE.STORY_PARAM` / `OPE.STORY_IRR_PARAM` / `OPE.MEMB` / `OPE.STOR`（带 `POST`） | 缺 `request_schema_confirmed` | **仍缺**（裁决只覆盖无请求体端点） | 不变 |

判定口径**未改**：`verification_status` 仍只由 `availability` 机械映射（`docs/07` §7.2 / §16 R78）。

## 4. P138c —— L5 空项目闸门 + 批量覆盖 + R4 / R14 重算

### 4.1 空项目闸门（代码化，不再手工核对）

`MidasLiveWriteProbe.assert_project_empty()`：发**任何**写请求**之前**，对 `EMPTINESS_GATE_KEYS`
（`DB.NODE` / `DB.ELEM` / `DB.MATL` / `DB.SECT`）各做一次**只读** `GET`，用数据侧解包链读既有编号：

| 情形 | 行为 | 离线证据 |
| --- | --- | --- |
| 任一哨兵**非空** | `STRUCTAI-3000 dedicated_test_project_not_empty`（`details` = `endpoint` / `existing`）+ **零**写请求 | `test_p138c_a_non_empty_project_is_refused_with_zero_write_requests`（`transport.write_calls == []`） |
| 全部哨兵**为空** | 放行，三步链只碰自建编号 | `test_p138c_an_empty_project_passes_the_gate_and_the_three_step_chain_runs`（`GET…` 全在 `POST` 之前；清理后项目**再次为空**） |
| 哨兵**全不可读** | `STRUCTAI-3000 dedicated_test_project_emptiness_unverified` + **零**写请求（**不**盲写） | `test_p138c_an_unreadable_sentinel_set_is_refused_instead_of_writing_blind` |

顺带修复：批量路径不再因「Transformer 名可派生但**未注册**」抛 `KeyError`，而是如实归入
`NO_PAYLOAD_TEMPLATE`（**零**写请求）—— 该缺陷在 P138c 的批量用例里首次暴露（`candidate_keys()` 会返回
`DB.ACTL` 等尚未注册 Transformer 的端点）。

### 4.2 R4 / R14 覆盖重算（**唯一**可执行口径）
