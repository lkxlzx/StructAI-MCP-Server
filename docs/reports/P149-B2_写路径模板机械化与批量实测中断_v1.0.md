## 2. 复算工具的真缺陷（本批修掉）

`check_write_templates.py::request_schema()` 旧版**只**认「包装节点带 `properties`」这一种形状；
对 `Assign.patternProperties["^[0-9]+$"]`（`ID → 条目` 键控对象）**退化为「拿根 Schema 判条目」**
⇒ `unknown_fields()` 把条目字段**全部**误判为「未声明」：本批 **192** 条模板里 **71** 条报假错
（`DESIGN.*` 与 `DB.REBB`/`DB.SSEIS` 等）。

**修**：新增 `_item_schema()`，把包装节点剥到**条目** Schema（`properties` 直连 **或**
`patternProperties['^[0-9]+$']`）⇒ 判定**变强**（条目字段按条目 Schema 复算），
假错 **71 → 0**，并**立刻**暴露 **2** 条**真**缺口（见 §3）。

## 3. 新裁决

| 裁决 | 内容 | 证据 |
| --- | --- | --- |
| **R109** | **手册示例字段在数据侧请求 Schema 里未声明** ⇒ 如实留缺（**不**改 Schema、**不**改示例、**不**放宽判定） | `DESIGN.RC.KDS-41-20-2022.DCREM`：`SELECTED_MEMBERS` / `SELECT_ALL`；`DESIGN.RC.KDS-41-20-2022.REBB`：`ITEMS[0].BAR_SECTOR_I.SKIN_BAR_NAME` 等 **9** 个路径 |
| **R110** | **本 build 原生拒绝 / 读不回 / 求解器不支持** ⇒ 留缺（与 R101–R105 同形，模板**撤**） | **49** 条 `400 software_api_error` · **10** 条 `POST 200` 读不回 · **1** 条 `solver_unsupported`（`DB.GALD`）；逐条见 `registry/live/write_batch_p149b2.json` |
| **R111** | **`availability: untested` 的端点无法进入写路径实测**：三步链的第 1 步（只读 `LIST`）就需要**已验证**的读路径映射，未验证 ⇒ `registry_mapping_not_verified`（**49** 条 `DESIGN.*`） | 恢复条件 = 先跑**只读** L4 探针验证映射（零副作用），再纳入写路径实测 |
| **R112** | **`request_schema()` 对「按端点代码键控」的根仍不可判**（`{"NODE": {...}}`）⇒ 该形状下字段白名单检查是**空判** | 实测：**60/60** 当前模板该形状下 `properties` 为空；若把 `request_schema()` 扩到该形状，**53/60** 变成可判并**立刻**暴露 **1** 处既有 Schema 缺口（`DB.SECT.SECT_BEFORE.{DATATYPE,SECT_I}`，而 `DB.SECT` 实测已 `PASSED` ⇒ **缺口在数据侧**）⇒ 本批**不**改（不顺手改数据侧），改为**钉住现状**的测试 + 本裁决 |
