## 0. 一句话结论

**普查发现了一件比「某个枚举太窄」严重得多的事**：`spec_guard`（**R140**）对
**104 / 225** 个「带枚举约束」的 Schema 文件**一个字段都不检查** —— 因为 `registry/schema/**`
的文件有**两种根形态**，而闸门的下钻约定 `schema["properties"][包装键]` 只认其中一种：

| 根形态 | 文件数 | `schema["properties"]` | 闸门 |
| --- | ---: | --- | --- |
| `{"properties": {"Argument": …}}` | **228** | **非空** | ✅ 可下钻 |
| `{<包装键>: {"properties": …}}`（**根键 = 包装键**） | **393** | **缺失** | 🛑 **盲**（一个字段都不查） |

修法 = **核心 1 行**（**用户已授权**）：`adapter._build` 由 `registry.schema_json(key)`
改用 `registry.effective_schema(key)`（= P09 就有的 `unwrap_schema()`，
`request_schema_fields()` **一直**用它）⇒ **225 / 225** 可下钻（**104** 个由盲变可见，
已可见的 **121** 个**零回归**）。

⚠️ **但可见性一恢复，这些枚举立刻生效** ⇒ 若枚举**缺**合法取值，就**会**把合法调用拦死
（**R151 的镜像事故**）。普查的「**拦住手册自己的示例**」标志正好抓到 **5** 处（**4** 个端点），
其中 **6** 个变体端点的 `TABLE_TYPE` 枚举**连自己的登记 token 都没有** ⇒ **先补枚举、再恢复可见性**
（本批在同一批次内完成，最终状态 = **合法放行 + 非法拦截**）。

⇒ 本批收口 **7** 项（`CURRENT_MODE` **36** 个取值 + **6** 个变体 token）、
**如实留缺 9** 项（**逐条**写明「向谁问什么」）、**主指标不变**（`68 / 71`）——
本批的价值在**防事故**（R140 的目的），**不**在抬主指标。

## 1. 普查（`registry/tools/check_spec_enums.py`，**零请求**）

### 1.1 口径（**机械扫描，无人工取值**）

`registry/schema/**` 的**每一个**枚举约束（`enum` **639** 条 + `oneOf[].const` **115** 条 =
**754** 条，覆盖 **625** 个文件）逐条分类**来源**：

| 分类 | 判据 | 规模 |
| --- | --- | ---: |
| **`manifest`（登记表）** | 取值 ⊆ `registry/manifest.json` 的**登记词汇**（key 的每一段 · `table_type` · Schema 文件名 · `uri` 末段） | **101** |
| **`manual`（手册声明）** | 取值 ⊆ 上游手册**全部**条目 `json_schema` 里**同名字段**的 `enum` / `oneOf[].const` 并集，且声明该字段的文章 **≥ 2** 篇 | **227** |
| **`single_article`（单篇文章）** | 同上，但只有 **1** 篇 ⇒ ⚠️ **来源太窄**（**R151** 的形态） | **158** |
| **`untraceable`（无法追溯）** | 既不在登记表词汇、也不在手册声明的并集里 | **268** |

⚠️ **口径**：「手册声明」**只**取 `json_schema` 的 `enum` / `oneOf[].const`，
**不**含**示例体**取值 —— 这正是 **R151 的教训**（「**不**按手册**示例体**硬凑」）。
示例体 / 规格表 / 仓库内上游文档 / 自省证据只作**弱来源**（把 `untraceable` 再分档；
本批**真·无法追溯** = **0** 条）。

### 1.2 三个**可执行**标志

| 标志 | 判据（**可复算**） | 规模 |
| --- | --- | ---: |
| **`narrow`（来源太窄 ⇒ 会拦住合法调用）** | 枚举 **⊊** 「该端点**自身**的可复算词汇」（`TABLE_TYPE` 取该端点及**后代端点**的 `table_type`；其余字段取**同 URI 同形状**的手册声明并集）∧ 该端点**自己的 token 不在**枚举里 ∧ **大小写归一**后仍缺 | **1** |
| **`missing_enum`（缺枚举 ⇒ 非法取值抓不到）** | 同 URI 的**多篇文章**的示例体在该字段上给出**有限取值集合**（取值数 ≥ 2 且 ≥ 文章数的一半）∧ 该 URI 下**任何** Schema 都**没有**为该字段声明枚举（自由文本 / 路径 / 布尔 / 纯数值按**机械规则**排除） | **4** |

它比静态分析更硬：**1990** 条里只有 **13** 条违例（**2** 条仅大小写差异），**11** 个端点。

### 1.3 顺带的三个**假阳性**教训（**逐条**留在工具里）

| 假阳性 | 成因 | 修法（工具里的判据） |
| --- | --- | --- |
| `items` / `VALUE_TYPE` 满天飞 | **JSON Schema 结构键**（`items`）与**同名不同义**（`ISO_SURFACE.VALUE_MODE.VALUE_TYPE` vs `APPLIED_LOADS.VALUE_TYPE`）被当成同一张词汇表 | 字段名 = **最近一个非结构键**；来源按**形状路径**（去包装根键）归并 |
| 变体端点全被标「太窄」 | 194 个 `POST.TABLE.*` 共享 URI `POST/TABLE` ⇒ 每个变体的枚举都比「URI 级并集」窄，但它们**只**接受自己的 token | 「自己的 token 已在枚举里」⇒ **不算**（拦不住自己的合法调用） |
| 收窄分支被当成取值表 | `allOf[i].if` 里的枚举是**条件收窄**（`GEO_NONL_TYPE: [1,2]` ⊂ `[0,1,2]`） | `if` / `then` / `else` 里的枚举**不**参与来源与标志 |

## 2. 可见性修复（**R161** 的核心 1 行；**用户已授权**）

+            registry.effective_schema(resolved.definition.key),

## 8. 本批的教训

1. **「闸门没拦住」有两种成因：枚举太窄，或者闸门**根本看不见**。** 前两个批次（P167 / P166）
   都在修**枚举内容**，而没人问过「这个枚举**真的**被读到了吗」。普查第一次把这个问题
   变成**可执行判据**（`schema["properties"]` 是否非空 + 与 `effective_schema` 的对比）
   ⇒ 一次就抓到 **104 / 225** 的盲区。
2. **修「看不见」必须与「枚举够不够」**同时**交付。** 可见性是**放大器**：恢复前，窄枚举**无害**
   （拦不住任何东西）；恢复后，同一个窄枚举**立刻**变成**拦住合法调用**的事故（R151 的镜像）。
   ⇒ 本批的顺序判据 = **先补枚举、再恢复可见性**（同一批次内闭环），
   并用 `example_blocked`（**手册自己的示例**）当**前置检查**。
3. **假阳性要当成一等公民**：首轮普查跑出 **94** 条「来源太窄」，逐条复核后**只有 7 条**是真的
   —— 三类假阳性（结构键 / 同名不同义 / 条件收窄）**都**写进了工具（而不是「人肉记住别信」）。
   工具里的每一条规则都对应一次**实测的假阳性**。
4. **「拦住手册自己的示例」是最硬的离线判据**：它**不**依赖我们自己的调用形状，
   直接把**上游的合法调用**喂进**同一个函数**（`guard_spec_values` + `effective_schema`）。
   1990 条里 13 条违例 ⇒ 信噪比足够高，且**每一条**都能落到一个端点 / 一篇文章 / 一个示例名。
5. **探针的护栏也是判据的一部分**：首跑把一次**鉴权失败**（`MAPI Key is invalid.`）记成了
   「原生 `400`」—— 若不识别，证据里会留下一条**看似业务级**的拒绝，**结论会被误判**。
   ⇒ 探针**识别即中止**（**不**写证据）+ 原生调用**重试**；**坏证据不进仓**。
