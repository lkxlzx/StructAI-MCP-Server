## 0. 一句话结论

在 **GEN NX 空项目**上按同一机制（数据侧模板 + 真实 L5 三步链）推进第四批：**13 个端点 → 10 个跑通**
（`DB.POGD` / `DB.POSP` / `DB.SDHY` / `DB.SDIS` / `DB.SDST` / `DB.SDVE` / `DB.SDVI` /
`DB.TDGR` / `DB.TDME` / `DB.TDMT`，全部**零前置链**），**3 个如实留缺**（`DB.MVCT` / `DB.TDMF` /
`DB.THGC`：手册示例被本 build 拒绝 `400 software_api_error` → **R104**）。
覆盖率 **`36 / 609` → `46 / 609`**（`model_write_ratio` **`36 / 410` → `46 / 410`**）；
跑前 / 跑后哨兵（**49** 个端点）**全空、0 不可读** ⇒ **零残留**。

本批与 P146 的差别（**纪律升级**）：**先**对 13 个端点逐个做**只读**自省
`GET /info/db/<CODE>`（核对「手册示例字段 ⊆ 本 build 接受字段」），**再**落模板，
然后**只跑一次**全量批量 —— **没有**任何逐端点原生试探（P146 §7 的崩溃教训已落实）。

## 1. 本批推进：13 个候选 → **10 个通过**（+10）

### 1.1 选点原则

从「有写方法 ∧ 有读路径（`GET` + `read_root`）∧ 有 `DELETE` ∧ 非危险 ∧ 产品可得 ∧ **无**模板」的
**165** 个端点里（P146 收尾后的池子），只取**定义类独立表**：请求体**不引用**任何**既有**对象
（节点 / 单元 / 材质 / 截面 / 荷载工况 / 组），即**零前置链**。

落盘**前**的**只读**闸门（本批新增）：

1. 用上游手册的**同一条**示例条目（`input_uri` 大小写与手册一致）取出 body；
2. `GET /info/db/<CODE>` 取本 build 的**接受字段集**（`Argument.properties`，递归含 `items.properties`），
   逐字段核对「手册示例字段 ⊆ 接受字段」⇒ 本批 13 个端点 `unknown` = **0**；
3. 才写入 `registry/live/write_templates.json`。

> ⚠️ 第 2 步是 P144 的 **R101** 教训的直接制度化：`DB.ACTL` 的 `CLATS` 在**数据侧 Schema 里存在**，
> 但本 build **不接受**（自省字段是 `ACWC`）⇒「Schema 声明」**不足以**判定是否被接受。
> 本批 13 个端点**无一**命中该形态（可执行对照见测试文件）。

**脱敏后的请求形态**（10 条同形，以 `DB.TDGR` 为例）：

```text
POST /DB/TDGR            # 包装键 Assign（数据侧 wrapper.write），编号 = 既有编号 max + 1 = 1
{"Assign": {"1": {"NAME": "TGR1"}}}                      -> 200
GET  /DB/TDGR            # read_root = TDGR；自建编号 1 出现在编号集合里 -> read_back = True
DELETE /DB/TDGR/1        # 必带路径 key                        -> 200
GET  /DB/TDGR            # 收尾时编号集合不再含 1                -> 零残留
```

### 1.3 纪律核对

- **只碰自建编号**：每条都是「`GET` 既有编号（空）→ `max + 1` 创建 → 读回 → `DELETE <路径 key>`」；
- **跑前哨兵**：4 个默认哨兵（`DB.NODE` / `DB.ELEM` / `DB.MATL` / `DB.SECT`）**全空** ⇒ 空项目闸门放行；
- **跑前 / 跑后哨兵**：**49** 个端点（4 哨兵 + 46 候选去重）逐个**只读** `GET` →
  `non_empty = 0`、`unreadable = 0`（两次实测逐字相同）⇒ **零残留**；
- **失败尝试零残留**：3 个留缺端点被拒（`400`）时**没有**创建任何对象（`created_id` 为空），
  收尾 `GET` 复核哨兵仍全空；
- **绝不**放宽「创建 → 读回 → 按路径 key 删除」三步判定；**绝不**在云端生产项目上跑。

## 3. 新裁决 **R104**：3 个端点**如实留缺**（带原生证据）

原生判别（`gen-local`，**一次**批量；每个端点**只**发一组「创建 → 读回 → 删除」）：

| 端点 | 实测证据 | 为什么数据侧无法表达 | 处置 |
| --- | --- | --- | --- |
| `DB.MVCT` | 手册示例 `General`（条目 1）→ `POST /DB/MVCT` = **`400 software_api_error`**；`GET /DB/MVCT` 仍为空 | 本 build **拒绝**该示例的取值形态；`adjustments` **只**能改**值**（且必须命中原值）、**不能**改结构 / 加字段 ⇒ 数据侧无从推出可接受形态 | **留缺**；恢复条件 = 上游手册 / 新 build 给出可接受示例（另有 `Russia` 条目**未试**，见 §6） |
| `DB.TDMF` | 手册示例 `Creep Coefficient`（条目 1）→ **`400 software_api_error`** | 同上 | **留缺**；另有 `Shrinkage Strain` / `Relaxation` 两个条目**未试** |
| `DB.THGC` | 手册示例 `Time History Global Control`（条目 1）→ **`400 software_api_error`** | 同上；该端点手册**只有 1 个**示例条目 | **留缺**；恢复条件 = 上游手册给出可接受示例 |

**同时证明这不是数据侧缺陷**（可执行断言，`tests/test_midas_write_coverage_p147.py`）：三个端点仍
`enabled = true`、`availability = verified`、`methods` 含 `POST` / `GET` / `DELETE`，且**手册示例的每个
字段都在数据侧请求 Schema 里声明**（`set(body) <= set(properties)`）。

> ⚠️ 三个端点**没有**模板 ⇒ **不**入候选 ⇒ 不会污染 `limit`、不会产生假的 `FAILED` 记录。
> 本批**没有**放宽任何判定：`PASSED` 仍要求「创建 → 读回 → 按路径 key 删除」三步全成立。
> 与 R103（`DB.SKEW`：手册示例被拒）**同形**，区别在于本批**先**用只读自省筛过一轮、且**只**发了一组写请求。

## 7. 过程事件（如实记录）

- 本批**未**出现实例崩溃：先做 13 次**只读** `GET /info/db/<CODE>` 自省，再落模板，
  然后**只跑一次**全量批量（49 个候选，46 `PASSED` / 3 `FAILED`）。
- 为**定位**那 3 个 `FAILED`，另跑**一次**「仅本批 13 个新端点」的**有界批量**
  （`only=(13 个 key)`，13 组三步链）→ `{PASSED: 10, FAILED: 3, NO_PAYLOAD: 0, NO_READBACK: 0}`，
  逐条给出 `status_code` / `read_back` / `deleted`（即 §1.2 / §3 的原生证据）。
  这**不是**逐端点原生试探：**两轮都是有界批量**，且此后**只**跑最终全量批量（在 `pytest` 门控用例内）。
- 全量批量与哨兵核对全部在**专用空项目**上完成；跑前 / 跑后哨兵（**49** 个端点）**全空、0 不可读**。
