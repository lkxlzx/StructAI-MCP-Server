## 0. 一句话结论

**接口层三条路径走通了。** 经**既有 9 个 MCP Tool 契约** —— `MCP Tool → OperationPlan
（`operations.py`）→ Adapter（intent 分派）→ `MidasHttpClient`（护栏 + 包装键）→ MIDAS 实例` ——
在**专用空项目**上实测 **13** 条路径：**4** `PASSED` + **9** `FAILED`；其中
**添加**（`MODEL.NODE.CREATE` → `POST /DB/NODE`）· **编辑**（`MODEL.NODE.UPDATE` → `PUT /DB/NODE`，
`x` `1.0 → 2.0` 读回**确认生效**）· **删除**（`MODEL.NODE.DELETE` → `DELETE /DB/NODE/1`，
带**路径 key**、再读**确认消失**）**各取得端到端证据**，另有 `MODEL.GROUP.DELETE`
（`DELETE /DB/GRUP/1`）`PASSED`。跑前 / 跑后只读哨兵（**6** 个端点）**全空** ⇒ **零残留**、
**未**中止、**未**崩溃。

**9** 个 `FAILED` **全部**是同一个成因：**接口层的 canonical → native 变换产出的请求体缺
原生必填字段**（原生 `400 Wrong Field` / `Unknown Error`），而**同一端点**在数据侧用
**手册示例**是**已实测可用**的（R118 的 4 个 `PASSED`）⇒ 缺口在**契约（canonical 字段集）**，
不在端点、也不在护栏。**如实留缺**并立 **R126**（恢复条件 = `docs/04` §20–§31 的
canonical 字段集显式裁决）。

**映射缺口**（本批任务 2）：GEN NX 上**可写**且**已启用 / 非破坏性**的端点 **576** 个，
其中形态齐备（有 `GET` + `read_root`）**301** 个；`operations.py` 的 **69** 个 Operation
共映射 **61** 个端点 ⇒ **缺口 517** = **271**「契约外」+ **246**「无读回」，逐条进证据、
**离线可复算**。

## 1. 接口层端到端判据与实测（本轮任务 1）

### 1.1 判据（**先写清楚再动手**）

| 步 | 判据 |
| --- | --- |
| ① | **只读侦察**：对目标端点发 `OPTIONS`（核对 `Allow` 含该 Operation 声明的方法）+ `GET`（核对解包链 `read_root`）—— 映射**必须**由实测确认 |
| ② | 跑前只读哨兵（**全部**被触碰的端点）必须为空；非空 ⇒ **一个写请求都不发**（`aborted`） |
| ③ | **添加** = 经接口层创建（`2xx`）→ 读回该编号**在** |
| ④ | **编辑** = 创建 → `PUT` **改动过的值** → 读回确认**改动生效** |
| ⑤ | **删除** = 创建 → `DELETE {uri}/{id}`（**必带路径 key**）→ 再读**确认该编号不在**（R119：本 build 的 `DELETE` 会返回 `200` 并**回显被删记录**却**不真正删除**） |
| ⑥ | **清理**：每行的自建编号（含前置）**一律**尝试删除并以再读确认为准；失败 ⇒ 该行降级 `FAILED` 并如实进哨兵 / `residue` |
| ⑦ | 分块 ≤ **5** 条 + 块间**只读**健康检查 `GET /DB/NODE`（非 `200` ⇒ 立即中止）；**只碰自建编号**（= 既有编号的 `max + 1`） |

**工具侧的三处「判定点唯一」**：Operation → 端点的编排**只**读
`app/infrastructure/adapters/midas/operations.py` 的 `OPERATION_PLANS`（工具**不**另写映射规则）；
请求体**只**由接口层的 Transformer 产出（工具只给 **canonical 参数**）；
`--check` 用同一判定点**离线**复算证据的每一行。

**两个接口层事实（本批实测）**：

1. **R119 在接口层同样成立**：删除的返回体**回显被删记录**，例如
   `{"delete_node": {"NODE": {"1": {"X": 2.0, "Y": 2.0, "Z": 3.0}}}}` —— 只看状态码 / 返回体
   会把「删掉了」当成结论；判据**必须**以「再读确认不在」为准（本批 **4/4** `PASSED` 行的
   删除都做了再读确认）。
2. **写步骤的结果键是 `intent`**：接口层把每步结果按 `intent` 落进 `data`
   （写 = `write_node`，读 = `read`）⇒ `MODEL.NODE.QUERY` 的规范化结果是
   `data["read"]`（**不是** Mock Adapter 的 `data["items"]`）。本工具的读回**两种键都接受**，
   判定点**未**新增第三处。

### 1.4 `FAILED` 行的成因：**canonical 字段集覆盖不全**（新裁决 **R126**）

**对照**：同一端点在**数据侧**用**手册示例**是**已实测可用**的
（`registry/live/write_templates.json` 的模板 + `registry/live/put_edit_probe.json` 的
`PASSED` / `LEFT_OUT` 行 —— 后者要求「创建 → 读回 → 删除」三步全成立）。

| 端点 | 接口层产出的 body（本批实测） | 数据侧**手册示例**的 body（**已实测可用**） | 差在哪 |
| --- | --- | --- | --- |
| `DB.ELEM` | `{"Assign": {"1": {"NODE": [1, 2], "TYPE": "BEAM"}}}` | `{"TYPE":"BEAM","MATL":1,"SECT":1,"NODE":[1,2],"ANGLE":0}` | canonical 有 `material_id` / `section_id`，但**专用空项目**里没有任何材质 / 截面可引用（而材质 / 截面**建不出来**，见下两行）⇒ 缺 `MATL` / `SECT` |
| `DB.MATL` | `{"Assign": {"1": {"PARAM": [{"DEN": 7850.0, "ELAST": 2.1e11, "POISN": 0.3}], "NAME": "P152M1", "TYPE": "STEEL"}}}` | `{"TYPE":"STEEL","NAME":"DB_Steel","HE_SPEC":0,"HE_COND":0,"PLMT":0,"P_NAME":"","bMASS_DENS":false,"DAMP_RAT":0.02,"PARAM":[{"P_TYPE":1,"STANDARD":"EN05(S)","CODE":"","DB":"S450","bELAST":false,"ELAST":210000000}]}` | canonical **无法表达** `HE_SPEC` / `HE_COND` / `PLMT` / `P_NAME` / `bMASS_DENS` / `DAMP_RAT` / `PARAM[0].{P_TYPE,STANDARD,CODE,DB,bELAST}` |
| `DB.SECT` | `{"Assign": {"1": {"SECT_NAME": "P152S1", "SECTTYPE": "DBUSER"}}}` | `{"SECTTYPE":"DBUSER","SECT_NAME":"LT_Const","SECT_BEFORE":{"OFFSET_PT":"LT","HORZ_OFFSET_OPT":0,"VERT_OFFSET_OPT":0,"USE_SHEAR_DEFORM":false,"USE_WARPING_EFFECT":false,"SHAPE":"SB","DATATYPE":2,"SECT_I":{"vSIZE":[1,1]}}}` | `SectionTransformer` 的字段表**只**覆盖 `shape` → `SECT_BEFORE.SHAPE` 与 `offset_point` → `SECT_BEFORE.OFFSET_PT`；`DATATYPE` / `SECT_I` / 三个开关**无 canonical 对应** |
| `DB.CONS` | `{"Assign": {"ITEMS": [{"ID": 1, "CONSTRAINT": "111000"}]}}` | `{"ITEMS":[{"ID":1,"GROUP_NAME":"","CONSTRAINT":"1111000"}]}` | 缺 `GROUP_NAME`；`CONSTRAINT` **6** 位 vs 手册 **7** 位（canonical **只**覆盖 `ux..rz` 六自由度，`RW` 按 `transforms.py` §31 **明确不臆造**） |

**原生拒绝（逐条进证据的 `native_error`，前 200 字）**：
`DB.ELEM` / `DB.MATL` / `DB.CONS` → `{"error":{"message":"Wrong Field"}}`；
`DB.SECT` → `{"error":{"message":"Unknown Error"}}`（**全部** `400`）。

⇒ **成因判定**：不是端点坏、不是护栏误拦、不是数据侧模板错 —— 是**接口层的 canonical
模型覆盖不到原生必填字段**。**如实留缺**（**不**硬凑、**不**放宽），立 **R126**（§5）。
⚠️ 任务型失败的**两层**结构也据实记进证据：外层 `STRUCTAI-2200 task_not_completed`
（`stage=execution`），内层 `task_error.details = {endpoint, reason=software_api_error,
status_code=400, stage=midas_adapter}` —— 只看外层无法定位。
