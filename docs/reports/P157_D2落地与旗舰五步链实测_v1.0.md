（只有由**编号键**补的 `id` 有值）。

**实测**（写路径证据的 `readback.observed`）：

```text

                                               "ux": null, "uy": null, "uz": null,
                                               "rx": null, "ry": null, "rz": null, "rw": null}}
DB.NODE  add  → {"present": true, "observed": {"id": "1", "x": 1.0, "y": 2.0, "z": 3.0}}     ← 对照：有值
DB.MATL  add  → {"present": true, "observed": {… 全部有值 …}}                                ← 对照：有值
```

**离线可复算**：`_items_of({"1": {"ITEMS": [<叶子>]}})` == `[("1", {"ITEMS": [<叶子>]})]`。

- **影响面** = **4** 个 `ITEMS` 形态端点（`DB.CONS` · `DB.CNLD` · `DB.BMLD` · `DB.PRES`）。
- ⚠️ **不**影响写路径**判定**（判定 = 「该编号**在**读回里」，键来自编号、**不**依赖叶子字段），

  **不**是「canonical 取值可回读」。
- **未修**（属 `app/**` 的 `_read` / `_items_of`，**未**获授权）。
- ⚠️ P153 的读路径证据在**空项目**上测得 `empty_block` ⇒ 该退化**当时不可见**（本批因写路径的

## 8. 本批的**教训**（写给下一批）

1. **「前置未满足就不硬跑」是对的，但「前置」要先问清楚**：本轮原以为旗舰链要等 **D4 的第二个项目**，
   用户澄清「MIDAS 自身可建模分析，第二个项目只作扩展」⇒ 立刻可跑。**澄清一次**比**猜一整个批次**便宜。
2. **数据侧的一个字段改动会**连锁**到多个钉住计数**：`products` 补一个产品 ⇒
   写路径分母 +1 · 读路径成因前移 · 取报表目标集 +1 · blocked +1。**改数据前先跑全部 `--check`**，
   否则会在收尾时才发现 11 个测试要同步。
3. **A/B 必须只改一个变量**（P156 的教训）在本批**再次**应验：旗舰链的**阶段 A 与阶段 B**
   把「规格链失败」与「②–⑤ 的未知面」**分开**记录，才看清「① 是材质路线混用、② 是工况缺失」
   是**两个独立**成因 —— 若只跑阶段 A，会误判为「旗舰链整体不可用」。
4. **`2xx` 不等于成功**（R128）：② 的判据**必须**以**再读**为准；本批的 `readback.observed` 全 `None`
   也**不**影响判定（键在 = 在），但**暴露**了 **R130** —— **判据的**证明力**也要如实写清**。
5. ⚠️ **本批最大的教训：先查上游手册与软件的**对话框**，再下"契约缺口"的结论。**
   R131 初稿把"我们发不出可被接受的 body"归因到"canonical 少 11 个字段"，**方向就错了**：
   手册 `db/MATL` **自带 3 个示例**（`Standard` / `Isotropic - User Defined` / `Orthotropic - User Defined`），
   一眼就能看出 **`TYPE` + `P_TYPE` 决定哪一组属性有效**；用户的一张对话框截图进一步证明
   **钢材的属性由规范库带出、不能自定义**。⇒ **"缺字段"与"用错路线"是两回事**；
   **归因错了，授权请求也会错**（本批为此**撤回**了一次 `app/**` 授权请求）。
6. **单位也要当判据看**：`ELAST` / `DEN` 在 UI 上是 `kN/m²` / `kN/m³`，而探针发的是 Pa / kg·m⁻³；
   原生**不**校验量级 ⇒ `200` 掩盖了 **1000×** 的偏差。**"能过"不等于"值对"**（立 **R133**）。
