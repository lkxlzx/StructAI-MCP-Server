## 5. `PARTIAL` 逐条解释（**不是**失败）

- **CIVIL NX 164 条**：响应为 `{"message": ""}` —— 该实例当前打开的模型里**这些数据块为空**（同一端点在 GEN NX 上有数据时返回正常信封）。这是**模型状态事实**，不是注册表缺陷。
- **GEN NX 1 条**：`OPE.SECTPROP` 返回 `{}`（空对象）—— 同族事实；该端点在 CIVIL NX 上返回 `{"SECTPROP": {...}}`，故 `read_root = SECTPROP` 已按实测补齐。
- **Civil Designer 1 条**：`DB.CAPSIZE` 的 `result.return_value` 为 `null`（空块）。

## 7. R83 修复：两种响应信封

| 产品 | 解包链 | 数据侧落点 |
| --- | --- | --- |
| `GEN_NX` / `CIVIL_NX` | `(read_root,)` | `wrapper.read_root` |
| `CIVIL_DESIGNER` | `("result", "return_value")` | `product_overrides.CIVIL_DESIGNER.wrapper.read_root_path`（14 个只读端点全覆盖） |

- 修复前：Designer 的读路径取不到 `read_root` → **退回整包** → 转换器字段全 `None`（静默降级）。
- 修复后：`_unwrap()` 按链逐层取；**取不到即明确报错**（`STRUCTAI-2200 response_envelope_mismatch`）；数据侧**未声明**链则 `STRUCTAI-3000 endpoint_read_path_undeclared`。
- 顺带修正：`guard_shape()` 不再把「**没有**请求体」判成「形态不符」—— 旧实现会让 Designer 的**读路径**整体 `STRUCTAI-1200`（实测发现）。
- 两种信封都有 contract test 固定：`tests/test_midas_live_p134.py`。

## 8. `verification_status`：7 项 AND 判定（`docs/04` §8；`docs/07` §16 R78）

实测通过 L4 的端点（如 `DB.NODE` / `DB.MATL` / `DB.SECT` / `DB.UNIT` / `DB.GRUP`）：

```
satisfied: official_endpoint_confirmed · http_method_confirmed · request_schema_confirmed
           · product_scope_confirmed · version_range_confirmed · live_contract_test_passed
missing:   response_schema_confirmed        ← 数据侧**没有** response 方向 Schema
→ status:  PARTIAL（如实保持，**不**升级）
```

`OPE.PROJECTSTATUS` 另缺 `request_schema_confirmed`（数据侧无请求 Schema）→ 缺 **2** 项，同样 `PARTIAL`。

**结论**：L4 记录**不**升级任何端点的 `verification_status`；唯一缺口是「Response Schema 已确认」，属**数据侧**待补项。

## 9. L5（业务效果）：**未执行**，如实标注

- `docs/04` §72 的四要素里，**专用测试项目**（第 3 要素）在本次环境中**未声明**（`MIDAS_LIVE_PROJECT` 为空）。
- 实测两实例均已打开**非空模型**（GEN NX 的 `GET /DB/NODE` 返回 12 个节点）→ 在其中创建 / 删除节点会**触碰真实项目**，违反「绝不触碰任何生产项目」。
- 因此 `MidasLiveBusinessEffect` **直接拒绝**执行（`STRUCTAI-3000 dedicated_test_project_not_declared`），L5 用例 `pytest.skip`。
- 三步链（列出既有编号 → 只挑**未被占用**的编号创建 → 读回 → 按路径 key 删除）已在**离线 Mock Transport** 下逐条断言（含 `DELETE` 必带路径 key），只等一个专用测试项目声明即可执行。
