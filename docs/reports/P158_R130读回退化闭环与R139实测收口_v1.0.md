## 1. R130：`ITEMS` 形态端点的读回退化（主）

### 1.1 缺陷形态（P157 定位）

MIDAS 对 `ITEMS` 形态端点的读响应是**编号键 + 包装体**：

```json
GET /DB/CONS  →  {"CONS": {"1": {"ITEMS": [{"ID": 1, "GROUP_NAME": "", "CONSTRAINT": "1111110"}]}}}
```

`MidasAdapter._read` 用 `_items_of(read_root 块)` 解包，原先对编号键映射返回
`("1", {"ITEMS": [<叶子>]})` —— 即**包装体**、**不是**叶子
⇒ `BoundaryTransformer.from_native` 在包装体这一层找不到 `ID` / `GROUP_NAME` / `CONSTRAINT`
⇒ **7 个自由度全 `None`**（只剩由**编号键**补的 `id`）。

⚠️ **它不**影响写路径的判定（判定 = 「该编号**在**读回里」，键来自编号）—— 但**限制**了证明力：
`DB.CONS` 的 `PASSED` 只证明「**建成且可按编号读回**」，**不**证明「canonical 取值可回读」。

### 1.2 修复（`app/infrastructure/adapters/midas/adapter.py`，**1** 个文件）

- `_items_of`：编号键下若值是 `{"ITEMS": [<条目>, …]}` ⇒ **逐元素**展开（`_explode_items`）；
- 外层**编号不丢**：仍作为该条的**兜底 `id`**（元素自带 `ID` 时以元素为准）；
- **一个编号键下多条**也正确展开（`DB.CNLD` 一个节点可以有多条荷载）。

**未改动**：顶层 `ITEMS` 数组、普通编号映射（`DB.NODE` 形态）、单对象三种形态**逐条回归**（见测试）。

### 1.3 实测（真机）

## 5. 本批的教训

1. **"通了"不等于"取回来了"**：P157 的链虽然 `PASSED`，但设计结果与 `ITEMS` 读回**都没真正取到值**
   —— 两处都是**用户先看出来的**（R142 / R130）。**判定必须落到"值"上**，不能只落到"状态码"上。
2. **升级一个端点的 `availability` 会牵动"把它当样本"的用例** —— 这是**好事**（说明样本被复用），
   但换样本时要选**同形**的（同方法 / 同包装 / 同 `availability`）。
3. **`app/**` 的改动要连带刷新证据**：改完读回逻辑后，**重跑**写路径探针，否则证据仍是旧行为
   （本批已刷新：`observed` 从"只有 `id`"变成"全字段有值"）。
