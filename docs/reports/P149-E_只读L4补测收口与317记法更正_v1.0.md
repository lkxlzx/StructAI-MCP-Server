## 1. 为什么先更正记法（**不**美化）

P149-D 的 `docs/07` §15.5 ⑦ 与 `docs/reports/P149-D_*.md` §7 都写了「其余 **317** 个未验证的
**只读**端点」——**该记法偏松**：`317` 是 `untested` 的**总数**（P149-D 前），其中 **197** 个是
`POST.*`（**没有** `GET`，已由 **R106** 处置），剩下的**也大多不是**「只读」。

**据实复算**（`availability != verified` 的全部 **155** 个）：

| 构成 | 条数 | 能否只读收口 |
| --- | --- | --- |
| 有 `GET` ∧ 有 `read_root` ∧ 已启用 | **35** | ✅ 可探（**12** `untested` + **23** `unverified`） |
| 同上但**没有** `GET` | **119** | ❌ 只读探针**完全**覆盖不到（写路径 / `POST` 形态） |
| 已禁用（`enabled: false`） | **1** | ❌ 客户端直接拒绝 |
| **合计** | **155** | — |

> ⚠️ 更正**不**改任何判定：`availability` 的语义（`registry/README.md` §4）与「只升不降」
> 纪律**一行未改**；本批只把**可探范围**说清楚，并把**能收口的收掉**。

## 2. 工具加固（P149-B2 的教训落到本工具）

`registry/tools/sync_availability.py` 原先一次连发全部目标（P149-C 只有 49 个，尚可）。本批目标
**35** 个且未来可能更多，故按 P149-B2 的教训加固（**只**改工具，**不**改判定）：

| 加固 | 说明 |
| --- | --- |
| **分块** | 新增 `--chunk-size`（默认 `CHUNK_SIZE = 20`）；每块之间做**只读**健康检查 `GET /DB/NODE` |
| **健康检查失败即中止** | 非 `200` ⇒ **立即中止**（**不**继续发请求），并把 `aborted` 如实写进证据 |
| **实例不可达不冒充失败** | 传输失败 / `The project is not opened` ⇒ `SKIPPED`（**不**计入任何收口；续跑时重测） |
| **累积** | 既有证据里的行**逐字节保留**（不重测），本批只补新目标 ⇒ 同一份证据可**多批**增长（P149-C 的 49 行**一字未改**） |
| **错误形态留痕** | 非 `200` 的行记 `detail`（原生 `error.message` 前 200 字），便于事后复核 |
