## 3. ⚠️ 新发现：`DELETE` 语义**按路由族不同**（**推翻了初版结论**）

### 3.0 初版错在哪（如实记录）

初版写的是：

> ❌「设计规范代码（`DGNCODE`）是单例且必须存在的设置：一旦选过就**无法回到未选**」

**这是错的**，错在两处：

1. **只测了别名路由就下结论** —— 我测的 `/DESIGN/RC/DRC` 是**未编入索引**的别名路由，
   而手册索引里「RC Design Code」的端点是 **`/db/DCON`**（`en/Design/README.md` 第 1 条）。
2. **没有去查手册** —— 项目里就有抓下来的官方手册（`E:\MCP\MIDAS-API-Online-Manual`），
   一查就知道路由分两族、且 `/db/*` 的 `Active Methods` 含 `POST, GET, PUT, DELETE`。

### 3.1 手册怎么说的（证据）

| 来源 | 内容 |
| --- | --- |
| `en/Design/README.md`（**索引**） | `1 \| /db/DCON \| RC Design Code` · `11 \| /db/DSTL \| Steel Design Code` |
| `en/Design/RC-Design-Code.md` | End Point `/db/DCON`；Active Methods **`POST, GET, PUT, DELETE`**；值表 **64** 条 |
| `en/Design/Steel-Design-Code.md` | End Point `/db/DSTL`；Active Methods **`POST, GET, PUT, DELETE`** |
| `en/Unindexed/DESIGN/RC/DRC-RC-Design-Code/…md` | Input URI `/DESIGN/RC/DRC`；Active Methods **`PUT, GET, DELETE`**；enum **`["KDS 41 20 : 2022"]`**；**响应根键 = `DCON`** |
| `en/Unindexed/DESIGN/SRC/AIK-SRC2K/…DSRC-…md` | Input URI `/DESIGN/SRC/AIK-SRC2K/DSRC`；Active Methods **`PUT, DELETE`**；enum **`["AIK-SRC2K"]`** |

⇒ **`/DESIGN/RC/DRC` 的响应根键是 `DCON`** —— 说明它与 `/db/DCON` **写的是同一份数据**。
**两族路由**：**编入索引的 `/db/*`**（模型表）与 **未编入索引的 `/DESIGN/<族>/<模块>`**（设计模块配置）。

### 3.2 实测：两条路由共用一份数据，但 `DELETE` 语义不同

**决定性实验**（`registry/live/design_config_probe.json` 的 `route_semantics`，本工具可复跑）：

| 步骤 | `/DESIGN/RC/DRC`（别名） | `/db/DCON`（规范） |
| --- | --- | --- |
| baseline | `{}` | `{}` |
| `PUT /DESIGN/RC/DRC  DGNCODE=KDS 41 20 : 2022` | `KDS 41 20 : 2022` | **`KDS 41 20 : 2022`**（立刻可见 ⇒ 同一份数据） |
| `DELETE /DESIGN/RC/DRC` | **`GB/T50010-10`** | **`GB/T50010-10`** |
| `DELETE /DB/DCON` | `{}` | `{}` |

判定（工具产出）：`alias_delete_clears=false` · `alias_delete_writes_default=true` ·
`canonical_delete_clears=true` · `routes_share_storage=true`。

**同族复核（STEEL）**：`DELETE /DESIGN/STEEL/DSTL` → **`GB50017-17`**；`DELETE /DB/DSTL` → `{}`。
**⇒ 这是族级规则，不是个例。**

### 3.3 更正后的结论

| 路由族 | `DELETE` 的真义 |
| --- | --- |
| **`/DESIGN/<族>/<模块>`**（未编入索引） | **把该设计模块的设置写回产品默认值**（≠ 删除）—— 响应体**回显删除前的状态**（所以看响应体也没用） |
| **`/db/*`**（编入索引） | **删除该行**（⇒ `{}`），模型回落到隐式默认 |

**为什么这合逻辑**：设计模块**始终**处于"有一个设计规范在生效"的状态 ⇒ 该族的 `DELETE`
自然被定义为「**重置为默认**」；而 `/db/*` 是**模型表**表面，`DELETE` = 删行。
**SRC 看起来像 no-op 的真正原因**：它**没有** `/db/*` 规范路由（索引里只有 `/db/DSTL` 与 `/db/DCON`，
**无 `/db/DSRC`**）⇒ 只能"重置"；而它的唯一合法值 `AIK-SRC2K` **就是**产品默认值
⇒ **重置与 no-op 不可区分**（不是"清不掉"，是"重置后看不出差别"）。

### 3.4 对项目的含义

1. **清理设计规范必须走 `/db/*` 规范路由** —— 本工具已据此改（`CANONICAL_CLEANUP`），
   清理结果由「清空 2 / 未清空 2」变为「**清空 3 / 未清空 1**」（唯一剩下的就是 SRC，无规范路由）。
2. **我方 registry 的红利**：`DB.DCON` / `DB.DSTL` **已存在**且 `methods` 含 `POST/GET/PUT/DELETE` ✓
   ⇒ 生产路径若需要"清除设计规范"，应走这两个端点，**不要**走 `/DESIGN/...` 别名。
3. **铁律 ⓪ 仍然成立且更强**：`DELETE` 的 `200` **连响应体都不可信**（回显旧状态），
   判据只能是**再读**。本批的 `DELETE` **全部返回 `200`** —— 若只看状态码，4 个都会"看起来成功"。

手上只握着 `registry/` 里的那一份端点定义，就没有去看**手册的索引表**与 **`Unindexed/` 目录**。

**本批学到的（应写进"真机测试"前置清单）**：

1. **动手前先查手册的 `README.md` 路由索引**（每个 Section 一份）——它会直接告诉你
   「哪条路由是**编入索引**的、它的 `End Point` 是什么」，5 分钟就能避免这次两个错误。
2. **`E:\MCP\MIDAS-API-Online-Manual` 是抓下来的官方手册**（`en/` 与 `zh/`），
   且**含 `Unindexed/`** —— 对 `registry/` 里感到可疑的端点，**先在那里查一遍**。
3. **"删不掉"永远先怀疑自己的路由**，而不是先假设 API 语义反常。
   「选过就不能取消」这种结论，**必须有手册或第二来源**才能下。
4. **族级规则要成组验**：一条路由的行为可疑时，立刻在**同族**上验第二例
   （本批 STEEL 的 `GB50017-17` 就是靠这个把单个现象升格为族级规则）。
5. **`DELETE` 的响应体不可作判据** —— 它**回显删除前的状态**；4 条 `DELETE` **全部 `200`**，
   只看状态码会以为都成功了。**铁律 ⓪（判据 = 再读的效果）在本批是唯一有效的判据。**
